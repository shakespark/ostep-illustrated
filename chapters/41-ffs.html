这一章要解决什么

如何组织磁盘上的数据来提高性能？我们需要怎样的数据结构，又需要在其上叠加怎样的分配策略？怎样让文件系统"感知磁盘"（disk aware）？

How can we organize file system data structures so as to improve performance? What types of allocation policies do we need on top of those data structures? How do we make the file system "disk aware"?

上一章的 VSFS 只关心"对不对"：超级块、位图、inode 表、数据区，按顺序往磁盘上一摆就完了。最早的 UNIX 文件系统正是这样，结果它只能发挥磁盘 2% 的带宽。问题不在接口，而在于它把磁盘当成了随机访问内存：数据东一块西一块，每次访问都要付出昂贵的寻道和旋转。

伯克利的快速文件系统（Fast File System，FFS）保持 open()/read()/write() 等接口完全不变，只改内部布局和分配策略，就让性能大幅提升。它的核心口诀只有一句：相关的东西放在一起，无关的东西分开放。本章承接第 37 章（磁盘的定位代价）和第 40 章（文件系统的基本结构），后面的日志（第 42 章）、LFS（第 43 章）都会继续围绕"怎样让磁盘少寻道"做文章。

核心概念速览

局部性（locality）

一起被访问的数据若在磁盘上也挨着，就能省掉寻道和旋转等待。

柱面组 / 块组

FFS 把磁盘切成若干组（cylinder group / block group），组内访问只需短距离寻道。

组内结构

每组都有：超级块副本 S、inode 位图 ib、数据位图 db、inode 表、数据块。

目录放置

新目录放进"已分配目录少、空闲 inode 多"的组，把目录均匀摊开。

文件放置

文件的数据块与其 inode 同组；同一目录下的文件与目录本身同组。

大文件例外

大文件按 chunk 分散到多个组，避免一个文件塞满一组、挤走"相关"文件。

分摊（amortization）

每次寻道后多传一点数据，让寻道开销占比变小；chunk 要够大。

子块与参数化布局

512 字节子块减少小文件浪费；跳块布局避免错过下一块、多转一圈。

老 UNIX 文件系统：把磁盘当内存用

Ken Thompson 写的第一个 UNIX 文件系统结构极其简单：超级块（S）记录卷大小、inode 数量、空闲块链表的表头等信息；接下来是所有 inode；剩下的大部分都是数据块。

它的性能问题来自三方面：

  1. inode 与数据相距很远：读一个文件几乎总是"先读 inode、再读数据"，两者之间是一次长寻道。
  2. 碎片化（fragmentation）：空闲空间没有被认真管理，空闲链表很快就指向散落在全盘的块，新文件"拿下一个空闲块"，逻辑上连续的文件在物理上来回跳。
  3. 块太小（512 字节）：小块减少了块内浪费（内部碎片），但每传一小块都可能要付一次定位开销，传输效率很低。

组织结构：柱面组与块组

FFS 的第一步是改变磁盘上的结构。柱面（cylinder）是不同盘面上与盘心距离相同的一组磁道；FFS 把连续 N 个柱面合成一个柱面组（cylinder group），于是整块磁盘就是一串柱面组。同一组内的两次访问，磁头最多只需在 N 个柱面之间短距离移动。

现代磁盘不会向文件系统暴露真实几何结构，只提供一个逻辑块地址空间。因此 ext2/ext3/ext4 等现代文件系统改用块组（block group）：每个块组只是磁盘地址空间中连续的一段。叫柱面组还是块组都无所谓，关键在于：把两个文件放进同一组，就能保证先后访问它们不会导致长距离寻道。

  • 超级块副本 S：挂载文件系统必须读超级块。每组放一份，某一份损坏了还能用其他副本挂载——这是为了可靠性，不是性能。
  • 每组的 inode 位图 ib 和数据位图 db：记录本组 inode 和数据块是否已分配。位图很容易找出一大段连续空闲块分给文件，从而避开老系统空闲链表造成的碎片。
  • inode 表和数据块：和 VSFS 一样，只是每组各有一份，大部分空间仍是数据块。

创建 /foo/bar.txt（1 个 4KB 块）：新文件要一个 inode → 写 inode 位图和 inode；文件有数据 → 写数据位图和数据块。这已经是对当前组的至少 4 次写（可能先在内存里缓冲一会儿）。还没完：父目录 foo 的数据块要加一个目录项（可能还得分配新块，连带数据位图），foo 的 inode 要更新长度和修改时间。

放置策略：相关的放一起

有了组，FFS 还要决定"什么和什么相关"。它用了几条朴素的启发式规则（原书打趣说：CS 不就是 common sense 的缩写吗）：

目录：找一个已分配目录数少（让目录在各组间均衡）且空闲 inode 多（之后能在这里放一批文件）的组，把目录的 inode 和数据放进去。

文件：① 数据块和它的 inode 放在同一组（避免老系统那样的 inode→数据长寻道）；② 同一目录下的文件放进该目录所在的组。

// 简化的 FFS inode 放置（本页模拟器与 labs/41-ffs/ffs_sim.c 使用的规则）
int pick_group(bool is_dir, path) {
    if (is_dir)                       // 目录：空闲 inode 最多的组（并列时取目录少的）
        return group_with_most_free_inodes();
    int g = group_of(parent(path));   // 文件：父目录所在的组
    while (free_inodes(g) == 0)       // 那一组的 inode 用完了，就往后找
        g = (g + 1) % NUM_GROUPS;
    return g;
}
// 数据块：从 inode 所在组开始找空闲块；大文件每 L 块换到下一组（大文件例外）

两个度量（来自 ffs.py 的作业题）：把磁盘看成一条线，组 g 占地址 g·(I+D) 到 (g+1)·(I+D)−1，其中先是 I 个 inode、后是 D 个数据块。filespan = 一个文件的 inode 与所有数据块之间的最大距离；dirspan = 一个目录（inode + 数据）与它所有直接子项（inode + 数据）之间的最大距离。数值越小，访问时寻道越短。

大文件例外

一般规则有一个重要例外。如果不做特殊处理，一个大文件会把它的第一个块组整个填满（甚至溢出到别的组），之后与它"相关"的文件就没地方放了，反而破坏局部性。原书用每组 10 个 inode、40 个数据块、一个 30 块的文件 /a 演示：

FFS 的做法：先在第一个组里分配若干块（比如 12 块，即 inode 中直接指针的个数），然后把下一个"大"chunk（比如第一个间接块指向的那些块）放进另一个组（可以选利用率低的），再下一个 chunk 放进又一个组，依此类推。

细心的你会发现：把文件拆散到各处，顺序读整个文件时不就要在 chunk 之间寻道了吗？没错！解决办法是把 chunk 选得足够大：只要每次寻道后传输足够多的数据，寻道时间占比就很小。这种"每付一次开销就多干点活"的技巧叫分摊（amortization），是计算机系统里的常用手法。

原书的计算：平均定位时间（寻道 + 旋转）10 ms，传输速率 40 MB/s。想让一半时间定位、一半时间传输（达到峰值带宽的 50%），每次定位后就要传输 10 ms：

40 MB/s × 1024 KB/MB × 10 ms ÷ 1000 ms/s = 409.6 KB

一般地，要达到峰值带宽的比例 p，传输时间须为定位时间的 p/(1−p) 倍：

chunk = 速率 × T定位 × p / (1 − p)

90% 需要约 3.6 MB（3686.4 KB，原书图 41.2 中标为 3.69M），99% 需要 39.6 MB！越接近峰值，chunk 越大。

FFS 的 4 MB chunk 可达带宽

不过 FFS 并没有用这种计算来决定怎么拆大文件，而是直接依据 inode 的结构：前 12 个直接块和 inode 放在同一组；之后每个间接块以及它指向的所有块放进另一个组。块大小 4KB、磁盘地址 32 位时，一个间接块能装 1024 个地址，于是除了前 48KB，文件每 1024 块（4MB）换一个组。

还要注意一个趋势：磁盘的传输速率提升很快（厂商擅长在同样的盘面上塞进更多比特），而与寻道相关的机械部分（磁臂速度、转速）进步很慢。于是机械开销的相对代价越来越高，要摊销它，每次寻道之间就得传输更多数据——在计算器里把速率调到 400 MB/s 试试。

FFS 的其他创新

子块（sub-block）

当时很多文件只有 2KB 左右。用 4KB 块传输效率好，但对这种小文件，内部碎片会浪费大约一半的磁盘。FFS 引入了 512 字节的子块：1KB 的文件只占 2 个子块，不必浪费一整个 4KB 块。文件继续增长时继续分配子块，直到凑满 4KB，这时 FFS 找一个完整的 4KB 块，把子块内容拷过去，并释放子块。

这个过程需要额外的拷贝 I/O，效率不高。所以 FFS 通常修改 libc：库先缓冲写操作，再以 4KB 为单位交给文件系统，大多数情况下就完全绕开了子块的特殊处理。

参数化布局（parameterized placement）

那个年代（SCSI 等现代接口出现之前）磁盘很"笨"，主机 CPU 得亲自控制它。FFS 发现：如果文件放在连续扇区上（下图左），顺序读时先读块 0，等读完、FFS 再发出块 1 的请求时已经来不及了——块 1 已经从磁头下转过去，只能再等将近一整圈。

FFS 的办法是跳块布局（下图右）：每隔一块放一个逻辑块，给主机留出发下一个请求的时间。FFS 还能针对具体磁盘测出应该跳几块，这就叫参数化（parameterization）。

这种布局的代价是：你最多只能拿到峰值带宽的 50%，因为读完一圈磁道上的所有块要转两圈。好在现代磁盘聪明多了：它们在内部把整条磁道读进磁道缓冲区（track buffer），之后对这条磁道的读请求直接从缓存返回。文件系统不用再操心这些底层细节——设计得当的抽象和高层接口是好东西。

让系统好用

FFS 最基本的经验不只是"感知磁盘的布局"，还在于它加了不少单纯让系统更好用的功能：

  • 长文件名：不再局限于传统的固定长度（例如 8 个字符）。
  • 符号链接（symbolic link）：硬链接不能指向目录（怕形成环），也不能跨卷（inode 号只在本卷有意义）；符号链接可以给任何文件或目录起"别名"，灵活得多。
  • 原子的 rename()：重命名要么完成、要么没发生。

这些功能很难写成研究论文（想象一篇 14 页的《符号链接：硬链接失散多年的表亲》），但它们让 FFS 更实用，也更可能被采用。让系统可用，往往和深刻的技术创新同样重要。

先预测再验证

在 FFS 模拟器里设置：组数 10、每组 inode 10、每组数据块 40，命令只有一行 file /a 40。先预测大文件例外 L=4 时的布局，再运行验证。（原书作业第 1 题）
看答案
40 块被切成 10 个 chunk，每个 4 块。第一个 chunk 与 inode 同在 0 号组（紧跟在根目录的数据块后面），之后每个 chunk 依次放到 1、2、…、9 号组，每组数据区开头都是 aaaa。
同上的设置，比较 L=4、L=10、L=100 三种情况下 /a 的 filespan。L 从小变大时，filespan 会怎么变？（原书作业第 2、3 题）
看答案
本页的地址模型下依次是 462、168、59。L 越小，文件被切得越碎、跨越的组越多，filespan 越大；L=100 超过文件大小，相当于关闭例外，整个文件挤在 0 号组（最后 1 块溢出到 1 号组开头），filespan 最小。对单个文件来说 filespan 小是好事，但代价是占满一个组——这就是例外要权衡的地方。
载入"多目录交错创建"：三个目录 /src /doc /bin 的文件是交替创建的。预测 FFS 与 spread 策略下 /src 的 dirspan 各大约是多少量级，再切换策略验证。（原书作业第 4、5 题）
看答案
FFS 下每个目录和它的 6 个文件都在同一组（1、2、3 号组），dirspan 只有 18~28；平均 dirspan（含根目录）约 50。spread 下每个新 inode 都去找空闲 inode 最多的组，同一目录的文件被撒到全部 8 个组，/src 的 dirspan 变成 255，平均约 233。交错创建的顺序对 FFS 没有影响，因为它只看"父目录在哪"。
仍用"多目录"示例，把每组 inode 数改成 5（FFS 策略）。预测：哪些文件会被挤到别的组？dirspan 会怎么变？（原书作业第 6 题）
看答案
每组只有 5 个 inode，目录自己占 1 个，只能再放 4 个文件。每个目录的第 5、6 个文件（lex.c parse.c、x.md y.md、who zsh）找不到空闲 inode，只好往后找组：它们大多落在 4 号组，最后的 /bin/zsh 落到 5 号组。平均 dirspan 从约 50 增加到 97，与父目录同组的比例从 86% 降到 57%。inode 表太小会直接破坏 FFS 的局部性。
载入"碎片化"示例：根目录下 8 个 2 块的文件，删掉 a、c、e、g 后再创建 8 块的 /i。预测 C=1 时 /i 的布局；再预测 C=2 和 C=3 时会不会变。（原书作业第 8、9 题）
看答案
C=1：/i 填进 4 个 2 块的空洞，被拆成 4 段，与老 UNIX 文件系统的问题一模一样。C=2：每个空洞恰好有 2 个连续空闲块，满足要求，布局不变。C=3：空洞都不够 3 块，于是 /i 被连续放在 h 之后的空闲区，8 块完全连续；代价是 4 个空洞暂时空着，filespan 从 23 变成 33（离 inode 远了一点）。
在 chunk 计算器里保持 10 ms 定位，先预测：把传输速率从 40 MB/s 提高到 400 MB/s，要拿到 90% 峰值带宽的 chunk 会变成多大？这说明了磁盘发展趋势对文件系统的什么要求？
看答案
chunk 与速率成正比：3686.4 KB × 10 = 36864 KB = 36 MB。传输越快、机械定位不变，同样的 4MB chunk 能拿到的带宽比例就从约 91% 跌到约 50%。所以文件系统必须在每次寻道之间传输越来越多的数据。

该观察到什么：

  • 同一目录下的文件拿到几乎连续的 inode 号，都在同一个 inode 块组里——"同目录放一起"的 FFS 思想还在。测试目录不是根目录的直接子目录，ext4 的 Orlov 分配器只把"顶层目录"分散到不同组，更深的子目录留在父目录附近，所以 a、b、c 也在同一组。
  • 小文件的数据块一个挨一个（首块号每次只差 2~3 块）：ext4 的"局部性组预分配"把小文件打包在一起。
  • 64MB 的大文件只由 1~3 个大区段（extent）组成：现代文件系统用尽量大的连续区段来分摊寻道，而不是像 FFS 那样每 4MB 换一个组。
  • 数据所在的组与 inode 所在的组并不相同：ext4 默认启用 flex_bg（把 16 个组的元数据集中存放），而且 WSL2 的"磁盘"本身是虚拟磁盘文件，块组早已不对应真实柱面。块组这个组织方式延续了下来，具体策略则复杂得多。

自测题

伯克利的测量显示，老 UNIX 文件系统最终只能发挥磁盘总带宽的多少？
原书："to the point where the file system was delivering only 2% of overall disk bandwidth"。根源是它把磁盘当作随机访问内存，不考虑定位代价。
FFS 在每个柱面组里都放一份超级块副本，主要目的是什么？
原书明确说是 "for reliability reasons"。挂载必须读超级块，多份副本防止单点损坏。本组的空闲情况由组内位图记录。
FFS 为一个新目录选择柱面组时，依据的是什么？
目录要在各组之间摊开（目录少），并且之后还要在该组放一批文件（空闲 inode 多）。"放在父目录所在的组"是文件的规则，不是目录的。
用户依次创建 /a/b、/a/c、/a/d、/b/f，FFS 会怎样放置？
同一目录下的文件放进该目录所在的组。C、D 描述的是本页的 spread 那类对照策略，它保住了"数据靠近 inode"，却丢掉了名字空间局部性。
定位时间 10 ms、传输速率 40 MB/s。要达到峰值带宽的 50%，每个 chunk 至少多大？
50% 意味着传输时间等于定位时间 10 ms：40 × 1024 KB/s × 0.01 s = 409.6 KB。4MB 大约对应 90%。
FFS 为什么需要"大文件例外"？
拆散大文件其实会损害顺序读（D 是反的），所以才要用足够大的 chunk 来分摊。目的在于保护其他文件的局部性。
参数化布局"每隔一块放一个逻辑块"时，顺序读一整条磁道最多能达到峰值带宽的多少？
读完一圈上的所有块需要转两圈，所以最多 50%。现代磁盘用磁道缓冲区（track buffer）整条磁道读入缓存，解决了这个问题。
用原书的路径距离度量，先打开 proj/src/foo.c 再打开 proj/obj/foo.o，距离是多少？
共同祖先是 proj，从 src 往上走一层到达 proj，距离为 2。SEER 迹线中约 25% 的访问属于这一类，FFS 的策略捕捉不到。
块大小 4KB、磁盘地址 32 位时，FFS 对大文件的实际拆分规则是？
FFS 没有用分摊公式，而是按 inode 结构：12 个直接块（48KB）同组，每个间接块及其指向的 1024 个块放进另一个组。
关于子块（sub-block），下列哪项正确？
子块（512B）解决的是小文件的内部碎片（空间效率），不是速度问题；拷贝开销则由修改 libc 的缓冲策略来规避。

常见误区与小结

  • "FFS 改变了文件系统接口"：没有。open/read/write/close 完全不变，只改内部实现——这也是之后几乎所有文件系统的做法。
  • "每组的超级块副本是为了加速"：是为了可靠性。
  • "把 inode 均匀摊到各组就是好的放置"：这样能保证数据靠近自己的 inode，却把同目录文件撒到各处，丢掉名字空间局部性。
  • "大文件例外是为了让大文件更快"：恰恰相反，拆散会引入额外寻道；它保护的是其他文件的局部性，靠大 chunk 把代价摊薄。
  • "现代文件系统还要跳块布局"：不需要，磁盘自带磁道缓冲区。现代磁盘也不暴露柱面，所以 ext 系列用的是逻辑上的块组。

本章小结

  • 老 UNIX 文件系统把磁盘当内存用：inode 与数据相距远、空闲链表导致碎片、512B 小块，只能发挥 2% 的带宽。
  • FFS 把磁盘分成柱面组/块组，每组包含超级块副本、inode 位图、数据位图、inode 表和数据块。
  • 放置启发式：目录去"目录少、空闲 inode 多"的组；文件的数据与 inode 同组；同目录文件与目录同组。SEER 迹线表明这种名字空间局部性确实存在（距离 ≤1 的访问近 40%）。
  • 大文件例外：按 chunk 把大文件分散到多个组；chunk 必须足够大才能分摊寻道（10ms / 40MB/s 下 50%、90%、99% 分别需要 409.6KB、3.6MB、39.6MB）。
  • 子块节省小文件空间；参数化布局避免多转一圈；长文件名、符号链接、原子 rename 让系统更好用。
  • 最重要的一课：把磁盘当磁盘对待（treat the disk like it's a disk）。ext2/ext3 是 FFS 的直系后代。下一章讨论另一个大问题：写到一半断电了，这些分散在各处的结构如何保持一致？
