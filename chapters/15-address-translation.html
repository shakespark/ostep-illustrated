1一句话 + 关键问题

如何高效、灵活地虚拟化内存？怎样才能高效地实现内存虚拟化？怎样提供应用程序需要的灵活性？怎样保持控制——决定一个应用能访问哪些内存位置，保证它的访问被正确限制？而且这一切都要高效。

原文：How can we build an efficient virtualization of memory? How do we provide the flexibility needed by applications? How do we maintain control over which memory locations an application can access, and thus ensure that application memory accesses are properly restricted? How do we do all of this efficiently?

虚拟化 CPU 时我们用了受限直接执行（limited direct execution, LDE）：大部分时间让程序直接在硬件上跑，只在系统调用、时钟中断等关键时刻让 OS 介入。虚拟化内存沿用同样的思路，追求效率和控制，再加上灵活性。本章给出的通用技术叫基于硬件的地址转换（hardware-based address translation），简称地址转换：硬件在每一次内存访问（取指、load、store）时把虚拟地址换成物理地址。

第 13 章提出了"每个进程一个私有地址空间"的目标，这一章给出第一种、也是最简单的实现：基址 + 界限（base and bounds），又叫动态重定位（dynamic relocation）。它的缺点（内部碎片）将直接引出第 16 章的分段。

2核心概念速览

地址转换（address translation）

硬件把指令给出的虚拟地址变成数据真正所在的物理地址，每次访问都做。

硬件 + OS 分工

硬件提供快速转换的底层机制；OS 在关键时刻设置硬件、管理哪些内存空闲/在用。

基址寄存器（base register）

物理地址 = 虚拟地址 + base。OS 把进程放在哪，就把 base 设成哪。

界限寄存器（bounds / limit）

检查虚拟地址是否 < bounds（且非负）；越界就抛异常，实现保护。

MMU（内存管理单元）

处理器中负责地址转换的那部分电路；每个 CPU 一对 base/bounds。

动态 vs. 静态重定位

静态：装载程序（loader）改写指令里的地址，没有保护，也难再移动。动态：运行时由硬件加 base。

特权指令与异常

只有内核态能改 base/bounds；越界访问或用户态改寄存器都会触发异常，交给 OS 处理。

内部碎片（internal fragmentation）

整个地址空间连续放进物理内存，堆和栈之间没用的空间也被占着，浪费在"分配单元内部"。

3图解：从一条指令说起

3.1 先做几个（可笑的）简单假设

  • 用户的地址空间必须连续地放在物理内存中；
  • 地址空间不太大，小于物理内存；
  • 每个地址空间大小完全相同。

这些假设不现实，后面会逐一放宽。

3.2 一个例子：x = x + 3

void func() {
    int x = 3000;   // thanks, Perry.
    x = x + 3;      // 我们关心的这一行
    ...

编译成 x86 汇编（Linux 上可用 objdump 反汇编）：

128: movl 0x0(%ebx), %eax   ; 把地址 0+ebx 处的值读到 eax
132: addl $0x03, %eax       ; eax 加 3
135: movl %eax, 0x0(%ebx)   ; 把 eax 写回同一地址

假设 x 的地址已放在 ebx 中。三条指令位于地址空间代码区的 128 处，变量 x 在栈上的 15KB 处，初值 3000。从进程的视角，这三条指令执行时发生了这些内存访问：

  1. 取地址 128 处的指令
  2. 执行它（从地址 15KB load）
  3. 取地址 132 处的指令
  4. 执行它（没有内存访问）
  5. 取地址 135 处的指令
  6. 执行它（向地址 15KB store）

在虚拟化内存中，硬件会插入到每一次内存访问中间，把进程发出的虚拟地址翻译成物理地址。插入是一种通用技术：几乎任何定义良好的接口都可以被插入，以增加新功能或改进系统，而且通常不需要改动客户端——这又带来了透明。

从程序看，它的地址空间从 0 开始、最大 16KB。但 OS 想把它放到物理内存的别处，而不一定是 0。问题来了：怎样把这个进程重定位到内存中别的地方，同时对进程透明？下图是放置后的物理内存：OS 用第一个槽，进程被重定位到从物理地址 32KB 开始的槽，另外两个槽（16–32KB、48–64KB）空闲。

3.3 动态（基于硬件的）重定位：基址 + 界限

20 世纪 50 年代末第一批时分共享机器引入了一个简单想法：每个 CPU 里放两个硬件寄存器，基址寄存器（base）和界限寄存器（bounds，也叫 limit）。程序按照"从地址 0 开始"编写和编译；程序开始运行时，OS 决定把它放在物理内存的哪里，并把 base 设为这个值（上例是 32KB）。之后进程产生的每个内存引用都由处理器这样翻译：

physical address = virtual address + base　　（前提：0 ≤ virtual address < bounds）

跟踪一次指令执行：PC 为 128，硬件取指时先把它加上 base 32KB（32768），得到物理地址 32896，从那里取指令；执行时进程发出从虚拟地址 15KB 的 load，处理器再加上 base，得到物理地址 47KB，取出想要的内容。因为重定位发生在运行时，而且进程开始运行后还可以移动地址空间，所以叫动态重定位。

界限寄存器用于保护：处理器先检查访问是否在界限内；上例中 bounds 总是 16KB。如果进程产生的虚拟地址大于或等于界限，或者是负数，CPU 抛出异常，进程很可能被终止。

方式一（本书默认）：bounds 存地址空间的大小，硬件先拿虚拟地址和它比较，再加 base。方式二：bounds 存地址空间末尾的物理地址，硬件先加 base，再检查物理地址是否在界内。两种方式逻辑等价。模拟器里可以切换这两种方式对比。

在有硬件支持之前，一些系统用纯软件做粗糙的重定位：装载程序（loader）在运行前把可执行文件里的地址改写成期望的物理偏移。比如指令 movl 1000, %eax，程序被装在 3000 处，loader 就把它改写成 movl 4000, %eax。问题：(1) 没有保护，进程可以生成坏地址去访问别的进程或 OS 的内存；(2) 放好之后很难再移动地址空间。

3.4 例子：4KB 地址空间装在 16KB

一个大小 4KB（不现实地小）的地址空间，装在物理地址 16KB 处（base = 16KB，bounds = 4KB）：

虚拟地址界限检查物理地址
00 < 4096 ✓→16KB（16384）
1KB1024 < 4096 ✓→17KB（17408）
30003000 < 4096 ✓→19384
44004400 ≥ 4096 ✗→Fault（越界）

可以把虚拟地址看成地址空间内的偏移量，加上 base 就是物理地址。只有地址"太大"或为负时才会出错。

3.7 基址/界限的问题：内部碎片

基址/界限很高效（只多了一点加法和比较的硬件逻辑），也提供了保护。但它有低效之处：看图 15.2，重定位的进程占用 32KB–48KB，可栈和堆都不大，它们之间的空间全都浪费了。这种浪费叫内部碎片（internal fragmentation）——分配单元内部的空间没用上。按目前的方案，即使物理内存还够放更多进程，我们也只能把地址空间放进固定大小的槽里。

5先预测，再验证

（原书作业 1）用种子 1、2、3 生成题目（点"作业：-s 1/2/3"），对每个虚拟地址先判断是否越界、合法的算出物理地址，再单步验证。以 -s 1 为例：base = 13884，bounds = 290，第一个地址 782 呢？
看答案
-s 1：base 13884、bounds 290；地址 782、261、507、460、667 中只有 261 合法 → 13884 + 261 = 14145，其余都 ≥ 290，越界。-s 2：base 15529、bounds 500；57 → 15586、86 → 15615，855、753、685 越界。-s 3：base 8916、bounds 316；378、618、640 越界，67 → 8983、13 → 8929。（这些数字和 relocation.py -c 的输出一致。）
（原书作业 2）-s 0 -n 10：bounds（-l）至少设成多少，才能让生成的 10 个虚拟地址全部合法？
看答案
10 个地址是 430、265、523、414、802、310、488、597、929、516，最大是 929。合法条件是 VA < bounds，所以 bounds 至少为 930。在模拟器里把 bounds 填 930 验证（注意：手动指定 -l 后，随机数不再用于生成 limit，地址序列会变！relocation.py 也是这样。想保持同一组地址，就把上面 10 个数填进"手动虚拟地址"）。
（原书作业 3）-s 1 -n 10 -l 100，物理内存默认 16KB。base 最大能设成多少，地址空间仍能整个放进物理内存？
看答案
地址空间占用 [base, base + 100)，要求 base + 100 ≤ 16384，所以 base 最大为 16284。在模拟器里填 base = 16284 可以生成；填 16285 会提示放不下。
（原书作业 5）随机生成的虚拟地址中，合法的比例和 bounds 是什么关系？先猜，再在 -a 1k、-n 40 下把 bounds 设成 256、512、768 看"合法比例"。
看答案
虚拟地址在 [0, asize) 上均匀随机，合法当且仅当 VA < bounds，所以合法比例 ≈ bounds / asize，是一条从 0 到 1 的直线（bounds ≥ asize 时为 100%）。样本少时会有波动，n 越大越接近。
在"时间线"模拟器中，进程 A 取指和 load 时 OS 有没有参与？哪几步 CPU 处在内核态？
看答案
A 运行期间的取指、load/store 转换全部由硬件完成，OS 不参与——这正是效率的来源。内核态出现在：启动阶段全部、创建 A 直到 return-from-trap、时钟中断到 return-from-trap（切换到 B）、B 越界触发异常之后。return-from-trap 把 CPU 切回用户态。

7自测题

base = 32KB，bounds = 16KB。进程取地址 128 处的指令，硬件访问的物理地址是？
32768 + 128 = 32896，原书原话。
4KB 地址空间装在 16KB（base = 16384，bounds = 4096）。虚拟地址 4400 会怎样？
合法条件是 0 ≤ VA < bounds。4400 ≥ 4096，CPU 引发异常，交给 OS。
为什么修改 base/bounds 的指令必须是特权指令？
原书："Imagine the havoc a user process could wreak if it could arbitrarily change the base register while running."
上下文切换时，OS 对 base/bounds 做什么？
每个 CPU 只有一对 base/bounds，而每个进程的值不同，所以必须保存/恢复（图 15.6 中 switch() 的 "including base/bounds"）。
相比静态重定位（loader 改写地址），动态重定位的关键优势是？
静态重定位的两大问题：没有保护、难以再移动。动态重定位由硬件在运行时加 base、查 bounds，两个问题都解决了。它并不能消除内部碎片。
进程被停下（不在运行）时，OS 想把它的地址空间搬到别处，需要哪些步骤？
原书 15.5：deschedule → copy → update saved base。进程恢复时新的 base 被载入，它对搬家毫无察觉。
基址/界限方案中的"内部碎片"指的是？
浪费发生在"已分配单元的内部"，所以叫内部碎片。B 描述的是外部碎片（第 16、17 章）。

页表是分页（第 18 章）的东西。图 15.3 列出的是：特权模式、base/bounds 寄存器、转换与检查电路、更新 base/bounds 的特权指令、注册异常处理程序的特权指令、引发异常的能力。

8常见误区与小结

误区 1："地址转换由 OS 软件逐条完成。"不对。每次访问的转换由硬件（MMU）完成；OS 只在创建、切换、终止、异常这些时刻介入。如果每次都要 OS 参与，就太慢了。

误区 2："bounds 是最后一个合法地址。"按本书的约定，bounds 是地址空间大小，合法范围是 0 ≤ VA < bounds，VA = bounds 已经越界。

误区 3："每个进程都有自己的 base/bounds 硬件寄存器。"每个 CPU 只有一对；每个进程的值保存在它的 PCB 里，切换时装入。

误区 4："基址/界限能省内存。"它要求整个地址空间连续驻留，堆栈之间的空洞也要占物理内存（内部碎片）。

本章小结

  • 地址转换扩展了受限直接执行：OS 设置好硬件，进程直接运行，硬件在每次访问时把虚拟地址转成物理地址，并确保访问不出界。
  • 基址/界限（动态重定位）：PA = VA + base，要求 0 ≤ VA < bounds；越界引发异常。硬件简单、快速，并提供保护，对进程完全透明。
  • 硬件要提供：特权模式、base/bounds 寄存器、转换与检查电路、修改它们和注册异常处理程序的特权指令、引发异常的能力。
  • OS 要做：创建时找空闲槽（free list）、终止时回收、切换时保存/恢复 base/bounds、安装并处理异常。
  • 缺点：内部碎片。下一章的分段为代码、堆、栈各配一对 base/bounds 来解决它。
