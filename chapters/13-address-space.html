1一句话 + 关键问题

如何虚拟化内存？操作系统怎样在一块物理内存之上，为多个同时运行的进程各自构建一个私有的、可能很大的地址空间这一抽象？

原文：How can the OS build this abstraction of a private, potentially large address space for multiple running processes (all sharing memory) on top of a single, physical memory?

前面几章我们把 CPU 虚拟化了：每个进程都以为自己独占处理器。本章开始虚拟化内存：每个进程都以为自己独占一大片从 0 开始的内存。这一章只做一件事——定义这个抽象，叫做地址空间（address space），并说清楚实现它要达到的三个目标。

具体"怎么做"留给后面的章节：第 15 章的基址/界限（base and bounds）、第 16 章的分段（segmentation）、第 18 章起的分页（paging）。可以把本章看成整个内存虚拟化部分的"需求说明书"。

2核心概念速览

地址空间（address space）

运行中的程序"看到"的内存：代码、栈、堆等全部内存状态。它是 OS 提供的抽象，不是物理事实。

虚拟地址（virtual address）

程序使用、打印出来的地址。由 OS + 硬件翻译成真实的物理地址（physical address）。

代码 / 堆 / 栈

代码（code）静态不变；堆（heap）存 malloc 的数据，向高地址长；栈（stack）存局部变量、参数、返回值，向低地址长。

多道程序（multiprogramming）

内存里同时放多个就绪进程，一个做 I/O 时切换到另一个，提高 CPU 利用率。

时分共享（time sharing）

多个用户交互式地共用一台机器。让进程常驻内存、快速切换，才能高效实现。

透明（transparency）

程序感觉不到内存被虚拟化，好像独占一块私有物理内存。

效率（efficiency）

时间上不能让程序变慢太多，空间上不能为虚拟化浪费太多内存；需要硬件（如 TLB）帮忙。

保护 / 隔离（protection / isolation）

一个进程不能读写别的进程或 OS 的内存；一个出错不会殃及其他。

3图解：从"没有抽象"到"地址空间"

3.1 早期系统：内存里只有 OS 和一个程序

最早的机器几乎不提供内存抽象。物理内存就像图 13.1：OS 是一组例程（其实更像一个库），放在从物理地址 0 开始的位置；唯一正在运行的程序放在 64KB 处，用掉剩下的所有内存。程序用的地址就是物理地址，没什么"幻觉"可言——用户也不指望 OS 做更多。

3.2 多道程序与时分共享：内存里同时住着好几个进程

机器太贵（动辄几十万甚至上百万美元），于是出现了多道程序（multiprogramming）：多个进程同时处于就绪状态，一个进程发起 I/O 时 OS 就切换到另一个，CPU 利用率因此提高。后来人们又要求交互性——程序员受够了批处理漫长的"提交—调试"循环，于是有了时分共享（time sharing）：很多用户同时使用一台机器，每人都期待及时响应。

实现时分共享，一个"笨办法"是：让一个进程独占全部内存跑一小会儿，然后把它的全部状态（包括整块物理内存）存到磁盘，再从磁盘装入另一个进程……问题是太慢了。保存/恢复寄存器（PC、通用寄存器等）很快，但把整块内存写到磁盘"慢得残忍"（brutally non-performant），而且内存越大越慢。

所以我们更愿意让所有进程都留在内存里，切换时只换寄存器。图 13.2 就是这样：512KB 的物理内存里，OS 占 0–64KB，进程 A、B、C 各自分到一小块。单 CPU 下 OS 选择运行其中一个（比如 A），B 和 C 在就绪队列中等待。

内存里同时住着多个程序，保护（protection）就成了大问题：你肯定不希望一个进程能读，更不用说写，别的进程的内存。

3.3 地址空间：程序眼中的内存

为了照顾"讨厌的用户"，OS 需要为物理内存造一个易用的抽象，这就是地址空间：运行中程序所看到的系统内存。理解它是理解内存虚拟化的关键。地址空间包含运行程序的全部内存状态，目前我们只关心三块：

  • 代码（code）：程序的指令必须放在内存某处，所以在地址空间里。
  • 栈（stack）：记录函数调用链走到了哪里，分配局部变量，传递参数和返回值。
  • 堆（heap）：动态分配、由用户管理的内存，比如 C 的 malloc()、C++/Java 的 new。

（还有静态初始化的变量等，暂且忽略。）原书用一个只有 16KB 的"玩具"地址空间来画图——作者直言：画 32 位地址空间太痛苦，数学也更难，"我们喜欢简单的数学"。

为什么这样摆？代码是静态的，大小不变，放在最上面最省事。堆和栈都可能在运行时增长（和收缩），把它们放在两头、相向增长，中间的空闲区就能被两者按需分享。不过这只是一种约定，你完全可以换一种排法；后面讲多线程时会看到，多个线程共存于一个地址空间时，这种"一头一尾"的划分就不再适用了。

3.4 "幻觉"与真相：虚拟地址 vs. 物理地址

我们描述地址空间时，描述的是 OS 提供给程序的抽象。程序实际上并不在物理地址 0–16KB 处；它被装载到某个任意的物理地址。看图 13.2 的 A、B、C，各自都在不同位置。于是问题来了：当进程 A 对地址 0 做一次 load（这个 0 称为虚拟地址），OS 必须和硬件配合，保证这次 load 实际访问的是物理地址 320KB（A 被装载的地方），而不是物理地址 0。

当 OS 做到这一点，我们就说 OS 在虚拟化内存（virtualizing memory）：运行的程序以为自己被装载在某个特定地址（比如 0），并拥有一个可能非常大的地址空间（比如 32 位或 64 位）；而现实完全不同。这是当今世界上每一台计算机内存虚拟化的基础。

3.5 虚拟内存（VM）系统的三个目标

① 透明（transparency）程序不应察觉内存被虚拟化，表现得就像拥有自己私有的物理内存。幕后由 OS 和硬件完成把内存"复用"给许多作业的全部工作。
注意：这里的"透明"是"看不见"，不是"公开透明"。透明的系统是让你难以察觉的系统。
② 效率（efficiency）时间上不让程序跑得慢很多，空间上不为支持虚拟化的数据结构耗费太多内存。要做到时间高效，OS 必须依赖硬件支持，比如以后要学的 TLB。
③ 保护（protection）保护进程彼此不受影响，也保护 OS 不受进程影响。一个进程的 load、store、取指令不能访问或影响任何其他进程或 OS 的内存（即它地址空间以外的任何东西）。保护带来隔离（isolation）。

隔离是构建可靠系统的关键原则。OS 力求让进程彼此隔离；借助内存隔离，OS 还能保证运行的程序影响不到底层 OS。有些现代 OS 走得更远，把 OS 的各部分也彼此隔开——这类微内核（microkernel）可能比典型的宏内核（monolithic kernel）更可靠。

3.6 你看到的每个地址都是虚拟的

写过打印指针的 C 程序吗？打印出来的那个（通常很大、十六进制的）数就是虚拟地址。代码在哪里？也能打印出来——同样是虚拟地址。事实上，作为用户态程序员你能看到的任何地址都是虚拟地址。只有 OS（和硬件）知道这些指令和数据真正躺在物理内存的哪里。原书的小程序 va.c：

#include <stdio.h>
#include <stdlib.h>
int main(int argc, char *argv[]) {
    printf("location of code : %p\n", main);           // 代码：main 函数的地址
    printf("location of heap : %p\n", malloc(100e6));  // 堆：malloc 返回的地址
    int x = 3;
    printf("location of stack: %p\n", &x);             // 栈：局部变量 x 的地址
    return x;
}

书中在 64 位 Mac 上的输出：

location of code : 0x1095afe50
location of heap : 0x1096008c0
location of stack: 0x7fff691aea64

可以看出：代码最先，然后是堆，而栈远在这个巨大虚拟空间的另一端。这些都是虚拟地址，每次访问都要由 OS 和硬件翻译成物理地址。第 6 节会在 Linux 上亲手跑一遍，还会看到两个进程打印出同一个地址却装着不同的值。

5先预测，再验证

在"虚拟视图 ↔ 物理位置"模拟器中，恢复图 13.2 布局。进程 A 读虚拟地址 15K，物理地址是多少？进程 B 读同一个虚拟地址 15K 呢？先算，再用模拟器验证。
看答案
A 从物理 320KB 开始，所以 PA = 320KB + 15KB = 335KB（343040）。B 从 192KB 开始，PA = 192KB + 15KB = 207KB（211968）。同一个虚拟地址，在不同进程里指向完全不同的物理位置——这正是"每个进程有私有地址空间"的含义。
进程 C（物理起点 128KB）访问虚拟地址 70K，已经超出了它 64KB 的地址空间。如果硬件不做任何检查，只是简单地加上起点，这次访问会落在谁的内存里？
看答案
128KB + 70KB = 198KB，落在 192–256KB 之间，也就是进程 B 的内存！C 如果是写操作，B 的数据就被悄悄破坏了。这就是为什么"保护"必须是 VM 的目标之一；第 15 章会用一个界限寄存器（bounds register）来挡住这类访问。
在"时分共享的代价"模拟器里，选"做法一"，每个进程内存 448KB、磁盘带宽 1000 KB/ms、时间片 10ms。预测 CPU 有效利用率大约是多少？把内存调到 4480KB 再预测一次。
看答案
每次切换要把旧进程的 448KB 写出、新进程的 448KB 读入：896KB ÷ 1000 KB/ms ≈ 0.9ms。每个周期 10ms 有效工作 + 0.9ms 开销，稳态利用率约 10 ÷ 10.9 ≈ 92%（模拟器走完 9 个时间片显示 92.6%，因为最后一片之后还没有切换）。内存变成 4480KB 后，每次切换约 9ms，稳态利用率掉到约 53%（模拟器显示 55.7%）。原书说的正是这个：内存越大，这个办法越慢。而做法二的开销与内存大小无关。
（原书作业 2–4）先运行 free -m 记下 used，再运行 ./memory-user 1000 5，在它运行期间再执行一次 free -m。预测 used 会增加多少？程序退出后呢？
看答案
大约增加 1000MB（本机实测 3417 → 4405，多了 988MB），程序退出后回落（→ 3403）。进程退出时 OS 回收它的整个地址空间。注意：只 malloc 而不去"触摸"数组的话，增加量可能远小于 1000MB——Linux 要等到第一次访问某一页时才真正分配物理内存（后续章节会讲按需分配）。系统里别的进程也会让数字有些噪声。
（原书作业 7）对任意一个进程运行 pmap -x <pid>。除了代码、堆、栈，现代进程的地址空间里还有哪些东西？
看答案
会看到：可执行文件本身被分成好几段（只读头部 r----、代码 r-x--、只读数据、可写数据 rw---）；[ anon ] 匿名映射（brk 堆、大块 malloc 走的 mmap 区域）；共享库 libc.so.6、动态链接器 ld-linux-x86-64.so.2，它们也各有代码/只读/可写几段；[ stack ]；以及内核提供的 vdso 等。原书"代码/堆/栈"三段模型是一个简化。第 6 节有真实的 pmap 输出。

③ va-fork：同一个地址，两个不同的值

[child  pid=343781] &x=0x5f9cf9eac050 x=200 | h=0x5f9d17eb02a0 *h=2
[parent pid=343780] &x=0x5f9cf9eac050 x=100 | h=0x5f9d17eb02a0 *h=1

子进程是父进程的复制品，所以全局变量 x 和堆指针 h 的虚拟地址完全相同；但子进程把它们改成 200 和 2 之后，父进程读到的仍然是 100 和 1。如果这些地址是物理地址，这根本不可能——同一个物理位置只能存一个值。只能说明：相同的虚拟地址，在两个进程里被翻译成了不同的物理地址。

8常见误区与小结

误区 1："指针的值就是内存条上的位置。"不是。用户程序里的指针都是虚拟地址，真实的物理位置只有 OS 和硬件知道。

误区 2："地址空间 = 程序占用的物理内存。"地址空间是一个抽象（程序眼中的内存）。它可以很大、很稀疏（如 64 位），中间大片空洞根本不占物理内存——后面的分段、分页就是为了做到这一点。

误区 3："透明就是公开。"在 OS 语境里，透明意味着"让程序察觉不到"。

误区 4："堆一定在代码后面、栈一定在最高处。"这是常见约定，不是铁律；多线程程序里每个线程都有自己的栈，布局会不同。

本章小结

  • 早期系统没有内存抽象；多道程序和时分共享让多个进程同时驻留内存，保护随之成为关键问题。
  • 地址空间是 OS 提供给运行程序的内存抽象，包含代码、栈、堆等全部内存状态；程序使用的是虚拟地址。
  • VM 系统为每个程序提供大的、稀疏的、私有的地址空间幻觉；OS 在硬件大力帮助下，把每次虚拟内存引用转成物理地址。
  • 三个目标：透明、效率（时间 + 空间，靠硬件）、保护（带来隔离）。
