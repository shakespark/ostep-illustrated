1一句话 + 关键问题

操作系统如何把资源虚拟化？——为了达成虚拟化，OS 实现了哪些机制和策略？如何高效地做到？需要哪些硬件支持？

HOW TO VIRTUALIZE RESOURCES. One central question we will answer in this book is quite simple: how does the operating system virtualize resources?

一句话：操作系统（operating system，OS）是一大块软件，它让程序"容易运行"——让许多程序看起来同时运行、共享内存、与设备打交道。它的主要手段是虚拟化（virtualization）：把 CPU、内存、磁盘这类物理资源变成更通用、更强大、更易用的虚拟形式。

这一章是全书的地图。它用四个小程序分别预告全书的三大主题（three easy pieces）：虚拟化（CPU 与内存，第 4–23 章）、并发（第 26–33 章）、持久化（第 36–45 章），然后讨论 OS 的设计目标和发展简史。本页的四个模拟器分别对应这四个程序——每一个现象你都会在后面的章节里找到完整的答案。

2核心概念速览

冯·诺依曼模型

处理器不断地取指（fetch）、译码（decode）、执行（execute）——程序运行就是这么简单的一件事。

虚拟化（virtualization）

把一个物理资源变成（看起来有很多份的）虚拟资源。因此 OS 有时被称为虚拟机（virtual machine）。

系统调用（system call）

OS 导出的几百个接口，程序靠它们运行程序、访问内存和设备。所以 OS 也被称为提供了标准库（standard library）。

资源管理器（resource manager）

CPU、内存、磁盘都是资源；OS 负责高效、公平地管理它们。

并发（concurrency）

同时处理许多事时出现的一类问题。多线程共享内存时，看似简单的 counter++ 也会出错。

持久化（persistence）

内存断电即失；硬盘、SSD 加上文件系统（file system）让数据长期保存。

机制与策略

机制（mechanism）是底层的"怎么做"，策略（policy）是"做哪个"的决定，如两个程序都想运行时选谁。

设计目标

抽象、高性能（低开销）、保护与隔离、可靠性，以及能效、安全、移动性。

3程序运行时发生了什么

运行中的程序只做一件非常简单的事：执行指令。每秒成百万（如今是数十亿）次，处理器从内存取出一条指令、译码（弄清是哪条指令）、执行（加两个数、访问内存、检查条件、跳转到函数……），然后继续下一条，直到程序结束。这就是计算的冯·诺依曼模型（Von Neumann model）。

4虚拟化 CPU

第一个程序 cpu.c（原书图 2.1）什么正经事也不干：调用 Spin(1)（反复检查时间，直到跑满 1 秒才返回），打印命令行传入的字符串，然后永远重复：

int main(int argc, char *argv[]) {
    if (argc != 2) { fprintf(stderr, "usage: cpu <string>\n"); exit(1); }
    char *str = argv[1];
    while (1) {
        Spin(1);              // 忙等约 1 秒：一直占着 CPU
        printf("%s\n", str);
    }
    return 0;
}

单独运行 ./cpu "A"，它每秒打印一个 A，Ctrl-C 才停。有趣的是同时运行四个（原书图 2.2）：

prompt> ./cpu A & ./cpu B & ./cpu C & ./cpu D &
A
B
D
C
A
B
D
C
A
...

明明只有一个处理器，四个程序却好像同时在运行！这个假象由 OS（在硬件的帮助下）制造：它让系统看起来拥有非常多的虚拟 CPU。把一个（或少数几个）CPU 变成看似无限多个 CPU，从而让许多程序看似同时运行，这就是虚拟化 CPU（virtualizing the CPU），全书第一大部分的重点。

能同时运行多个程序也带来新问题：两个程序都想在某一时刻运行，该运行哪个？回答这类问题的是 OS 的策略（policy）；而"能同时运行多个程序"这种能力本身，是 OS 实现的机制（mechanism）。

5虚拟化内存

物理内存的模型很简单：它就是一个字节数组。读内存要给出地址；写内存要给出地址和数据。程序运行时时刻都在访问内存——数据结构在内存里，每条指令本身也在内存里，所以每次取指都是一次内存访问。

int main(int argc, char *argv[]) {
    int *p = malloc(sizeof(int));                          // a1：分配内存
    assert(p != NULL);
    printf("(%d) address pointed to by p: %p\n", getpid(), p); // a2：打印地址
    *p = 0;                                                // a3：写入 0
    while (1) {
        Spin(1);
        *p = *p + 1;
        printf("(%d) p: %d\n", getpid(), *p);              // a4：加一并打印
    }
    return 0;
}

单独运行 mem，它在地址 0x200000 分配到内存，然后每秒把值加一。同时运行两个（原书图 2.4），每个进程打印时都带着自己的进程标识符（PID，process identifier）：

prompt> ./mem & ./mem &
(24113) address pointed to by p: 0x200000
(24114) address pointed to by p: 0x200000
(24113) p: 1
(24114) p: 1
(24114) p: 2
(24113) p: 2
...

两个进程在同一个地址 0x200000 分配到内存，却各自独立地更新那里的值！就好像每个进程都有自己私有的内存。事实正是如此：OS 在虚拟化内存。每个进程访问的是它自己私有的虚拟地址空间（virtual address space，简称地址空间），OS 以某种方式把它映射到机器的物理内存上。一个进程的内存访问不会影响其他进程（或 OS 自己）的地址空间；而实际上物理内存是由 OS 管理的共享资源。

要让两个进程打印出相同的地址，需要关闭地址空间随机化（address-space randomization）——它是防御某些安全漏洞（如栈溢出攻击）的好手段。现代 Linux 默认开启，本页"动手实验"里用 setarch -R 关闭它。

6并发

本书的另一个主题是并发（concurrency）：同时（并发地）处理很多事情时出现、必须解决的一类问题。它首先出现在 OS 内部——前面的例子里 OS 就在同时周旋于多个进程之间；如今多线程程序也面临同样的问题。原书图 2.5：

volatile int counter = 0;
int loops;

void *worker(void *arg) {
    int i;
    for (i = 0; i < loops; i++) {
        counter++;
    }
    return NULL;
}

int main(int argc, char *argv[]) {
    loops = atoi(argv[1]);
    pthread_t p1, p2;
    printf("Initial value : %d\n", counter);
    Pthread_create(&p1, NULL, worker, NULL);   // 两个线程都执行 worker
    Pthread_create(&p2, NULL, worker, NULL);
    Pthread_join(p1, NULL);                    // 等两个线程结束
    Pthread_join(p2, NULL);
    printf("Final value   : %d\n", counter);
    return 0;
}

可以把线程（thread）想成在同一个内存空间里运行的函数，而且同时有不止一个处于活动状态。两个线程各把共享的 counter 加 loops 次。loops = 1000 时结果是 2000，符合预期；但 loops = 100000 时：

prompt> ./threads 100000
Initial value : 0
Final value   : 143012     // huh??
prompt> ./threads 100000
Initial value : 0
Final value   : 137298     // what the??

不仅错了，而且每次错得不一样（偶尔还会碰巧对）。原因在于指令是一条一条执行的，而 counter++ 这个关键操作需要三条指令：从内存把 counter 加载（load）到寄存器、寄存器加一、存（store）回内存。这三条指令不是原子地（atomically）一起执行的，于是怪事就发生了。

如何构建正确的并发程序？当同一内存空间里有很多并发执行的线程时，如何写出正确工作的程序？需要 OS 提供什么原语？硬件应提供什么机制？如何用它们解决并发问题？

7持久化

第三个主题是持久化（persistence）。DRAM 以易失（volatile）的方式保存数据：一断电或系统崩溃，内存里的数据就没了。硬件上需要输入/输出（I/O）设备，如硬盘或 SSD；软件上，OS 中管理磁盘的部分叫文件系统（file system），负责把用户创建的文件可靠、高效地存到磁盘上。

与 CPU 和内存不同，OS 不会为每个应用创建一个私有的虚拟磁盘——人们通常希望在程序之间共享文件：用编辑器写 main.c，编译器读它生成可执行文件，最后运行这个可执行文件。原书图 2.6 的 io.c 用三个系统调用创建 /tmp/file：

int main(int argc, char *argv[]) {
    int fd = open("/tmp/file", O_WRONLY|O_CREAT|O_TRUNC, S_IRWXU);  // ① 打开（并创建）文件
    assert(fd > -1);
    int rc = write(fd, "hello world\n", 12);                        // ② 写入 12 字节
    assert(rc == 12);
    close(fd);                                                      // ③ 关闭：不再写了
    return 0;
}

这些系统调用被转给 OS 中的文件系统处理。文件系统要做不少活：决定新数据放在磁盘哪里，在它维护的各种结构里记录下来，这就需要向存储设备发 I/O 请求读或更新这些结构。为了性能，多数文件系统会先把写操作推迟一会儿，攒成更大的批次；为了应对写的过程中系统崩溃，多数文件系统采用某种精巧的写协议，如日志（journaling）或写时复制（copy-on-write），仔细安排写入顺序，保证崩溃后能恢复到合理的状态。

如何持久地存储数据？文件系统是 OS 中负责管理持久数据的部分。要正确地做到这一点需要什么技术？要高性能需要什么机制和策略？面对软硬件故障如何实现可靠性？

8设计目标

OS 把 CPU、内存、磁盘这些物理资源虚拟化，处理棘手的并发问题，持久地保存文件。构建这样一个系统时，需要一些目标来指导设计和取舍——找到合适的取舍是构建系统的关键。

目标含义本书中的体现
抽象（abstraction）让系统方便易用；把大问题分解成小而易懂的部分（用 C 写程序时不用想汇编，写汇编时不用想逻辑门……）进程、地址空间、线程、文件……每一部分都讨论主要的抽象
高性能（performance）把 OS 的开销（overhead）降到最低：额外的时间（更多指令）和额外的空间（内存或磁盘）受限直接执行（第 6 章）、TLB（第 19 章）……完美并不总能做到，要学会识别并容忍
保护（protection）应用之间、应用与 OS 之间互相保护；核心原则是隔离（isolation）用户态/内核态、地址空间
可靠性（reliability）OS 一旦失败，其上所有应用都失败；而 OS 代码动辄数百万行崩溃一致性、数据完整性（第 42、45 章）
其他能效（energy-efficiency）、安全（security）（保护的延伸）、移动性（mobility）系统用途不同，目标就不同，实现方式也会有所不同

9简史：OS 是怎么一步步长成今天的样子的

系统调用与过程调用的关键区别：系统调用把控制转移（跳转）进 OS 的同时提升硬件特权级。应用运行在用户模式（user mode）下，硬件限制它能做的事（比如不能直接向磁盘发 I/O 请求、访问任意物理内存页、发网络包）；系统调用通过一条叫 trap 的特殊硬件指令发起，硬件把控制转给 OS 事先设置好的陷阱处理程序（trap handler），同时把特权级提升到内核模式（kernel mode）；OS 服务完请求，再用 return-from-trap 指令回到用户模式、回到应用离开的地方。第 6 章会把这个过程拆开细看。

在并发模拟器中，loops = 1000、时间片 10000，运行 10 次；再把 loops 改成 100000 运行 10 次。结果分别怎样？为什么 loops 小时通常"碰巧"正确？
看答案
loops = 1000 时每个线程只有 3000 条指令，第一个线程往往在一个时间片内就做完了，两个线程根本没有交错，结果是 2000。loops = 100000 时每个线程要执行 30 万条指令，必然被切换许多次；只要切换点落在 load 与 store 之间，另一线程在这段时间里的所有加法都会被旧值覆盖掉，于是结果偏小且每次不同。
在持久化模拟器里（开启日志、不 fsync），在 close() 返回、程序退出之后立刻断电。数据还在吗？勾上 fsync 再试一次。
看答案
不在。write() 和 close() 都成功返回了，但文件系统为了性能推迟了写盘，数据还在内存里。调用 fsync() 会强制文件系统在返回前把数据（经日志）写到磁盘上，此后断电也不丢。

12自测题

1. 本书围绕的三个主题（three easy pieces）是？
原书第 2 章用 cpu/mem 演示虚拟化、threads 演示并发、io 演示持久化。网络、图形和深入的安全话题本书不讲。
2. 两个 mem 进程打印出相同的地址 0x200000，却各自独立计数。最准确的解释是？
每个进程都有自己私有的虚拟地址空间，OS 把它映射到物理内存上。一个进程的内存访问不会影响其他进程。（开启地址随机化后地址会不同，但那是另一回事。）
3. 为什么 threads 100000 的结果常常小于 200000？
若线程 1 load 了旧值后被打断，线程 2 在此期间做的加法会被线程 1 稍后 store 的旧值 + 1 覆盖。200000 远小于 int 上限，不存在溢出。
4. 关于 OS 对磁盘的"虚拟化"，下列说法正确的是？
原书："Unlike the abstractions provided by the OS for the CPU and memory, the OS does not create a private, virtualized disk for each application." 编辑器、编译器、可执行程序之间正是通过文件共享数据。
5. 系统调用与普通过程调用的关键区别是？
trap 指令跳入内核并切换到内核模式；OS 完成后用 return-from-trap 回到用户模式。这一思想由 Atlas 首创。
6. 多道程序（multiprogramming）流行起来的主要动机是？
让一个程序在 CPU 上干等 I/O 是浪费。多道程序把多个作业装入内存并快速切换，同时也带来了内存保护和并发问题。
7. write() 成功返回后立刻断电，数据一定在磁盘上吗？
原书："most file systems first delay such writes for a while, hoping to batch them into larger groups." 为了应对崩溃，文件系统还使用日志或写时复制来保证一致性。
8. 早期 PC 操作系统（如 DOS、Mac OS 9）相对小型机 OS 被称为"大倒退"，主要因为？
DOS 不认为内存保护重要，恶意或有 bug 的程序可以乱写整个内存；Mac OS 9 协作式调度，一个线程死循环就得重启。后来 macOS、Windows NT 才把小型机时代的好想法带回桌面。

13常见误区与本章小结

  • "多个程序同时输出，说明它们在同时运行"：在单 CPU 上，它们是被 OS 快速轮流运行的——这是时分共享制造的假象。
  • "打印出的指针就是物理地址"：程序看到的都是虚拟地址；两个进程的同一虚拟地址通常对应不同的物理内存。
  • "counter++ 是一条语句，所以是一步完成的"：它编译成 load/add/store 三条指令，线程可以在任意两条之间被打断。
  • "小规模测试结果正确，程序就没有并发 bug"：loops=1000 时碰巧正确，loops 大了才暴露问题；并发 bug 与时机相关。
  • "write 返回了，数据就安全了"：文件系统可能还没把它写到磁盘。
  • OS 让系统易于使用：它通过虚拟化把物理资源变成易用的虚拟形式（所以也叫虚拟机），提供几百个系统调用（所以也叫标准库），并管理 CPU、内存、磁盘等资源（所以也叫资源管理器）。
  • 虚拟化 CPU：一个 CPU 看起来像很多个，多个程序看似同时运行；由机制实现，由策略决定运行谁。
  • 虚拟化内存：每个进程有自己私有的虚拟地址空间，OS 把它映射到共享的物理内存上。
  • 并发：多个线程共享内存时，非原子的操作会交错出错，需要 OS 与硬件提供正确的原语。
  • 持久化：文件系统把数据可靠地存到磁盘；为性能会推迟写入，为可靠会用日志或写时复制。
  • 设计目标：抽象、高性能（低开销）、保护与隔离、可靠性，以及能效、安全、移动性。历史上 OS 从"只是库"演进到有保护的系统调用、多道程序、UNIX，再到今天的 Linux/macOS/Windows。
