这一章要解决什么

如何构建一个完整的虚拟内存系统？实现一个完整的 VM 系统需要哪些特性？它们如何提高性能、增强安全性，或以其他方式改进系统？

What features are needed to realize a complete virtual memory system? How do they improve performance, increase security, or otherwise improve the system?

虚拟化内存的部分即将结束。前面各章分别讲了页表设计（第 18、20 章）、TLB（第 19 章）、换页机制与替换策略（第 21、22 章）。本章把零件装成整机，看两个真实系统：

  • VAX/VMS（1970 年代末～1980 年代初，主要架构师 Dave Cutler，后来主导了 Windows NT）：最早的"现代"虚拟内存管理器之一，许多技巧沿用至今，也是"用软件弥补硬件缺陷"的典范。
  • Linux（x86 平台）：从手机到数据中心都要跑得好，特性由真实生产问题驱动，并且在安全上比老系统投入多得多。

核心概念速览

分段 + 分页混合

VAX 把 32 位地址空间分成 P0（代码/堆）、P1（栈）、S（系统），各有页表，省掉中间空洞的页表空间。

第 0 页不可访问

代码从不从地址 0 开始；访问空指针会陷入 OS，便于调试。

内核映射进每个地址空间

OS 像一个受保护的"库"，方便在内核与用户数据之间拷贝，也便于换出内核自己的页。

分段 FIFO + 二次机会

VMS 没有引用位：每进程 FIFO 限制 RSS，被踢的页先进全局干净/脏链表，还能被找回。

按需清零 / 写时复制

两种"懒惰"优化：页真正被用到时才清零；fork 时共享只读页，写时才复制。

内核逻辑地址 vs 内核虚拟地址

kmalloc 的内存与物理内存直接线性映射（可用于 DMA）；vmalloc 的内存只保证虚拟连续。

x86-64 四级页表与大页

48 位虚拟地址 = 4×9 位索引 + 12 位偏移；2MB/1GB 大页减少 TLB 未命中。

页缓存与 2Q

统一页缓存；用 inactive/active 两个链表抵抗大文件循环扫描。

安全：NX、ROP、ASLR、KPTI

防缓冲区溢出注入代码；ROP 绕过 NX；ASLR 随机化布局；KPTI 应对 Meltdown。

VAX/VMS：硬件与真实的地址空间

VAX-11 为每个进程提供 32 位虚拟地址空间，页大小只有 512 字节。于是虚拟地址 = 23 位 VPN + 9 位偏移。VPN 的最高两位用来区分页属于哪个段，所以它是第 16、20 章讨论过的分段与分页的混合：

  • 低半部分是进程空间（process space），每个进程各不相同：前一半 P0 放用户程序和向下增长的堆（按原书图中地址 0 在上的画法），后一半 P1 放向上增长的栈；
  • 高半部分是系统空间（S），只用了一半：受保护的 OS 代码和数据放在这里，并被所有进程共享。

页表太大怎么办

512 字节的小页让线性页表极其庞大：223 个 PTE × 4 字节 = 32 MB，每个进程一份！VMS 的设计者首要目标之一就是别让页表压垮内存，他们用了两招：

  1. 分段：P0 和 P1 各有一个页表（每进程两个），用基址/界限寄存器描述：基址寄存器存该段页表的地址，界限寄存器存页表大小（PTE 个数）。于是栈和堆之间的空洞不占页表空间。
  2. 把用户页表放在内核虚拟内存里：分配或增长页表时，内核从自己的虚拟内存（S 段）中分配；内存紧张时，内核甚至可以把这些页表的页换出到磁盘。

代价是地址转换更复杂：要翻译 P0/P1 中的地址，硬件先要找到该页在 P0/P1 页表中的 PTE；而那个页表本身位于 S 段的虚拟地址上，所以硬件可能先得查系统页表（它在物理内存中）来翻译"页表所在的地址"，最后才能访问目标数据。好在 VAX 有硬件管理的 TLB，通常能跳过这番折腾。

内核在每个地址空间里

上下文切换时，OS 改写 P0、P1 寄存器指向新进程的页表，但不改 S 段的基址/界限寄存器，所以"同一份"内核结构被映射进每个用户地址空间。好处：

  • 用户程序把指针交给内核（比如 write() 系统调用）时，内核可以直接从这个指针拷贝数据；内核代码可以自然地编写、编译，不用操心数据从哪来；
  • 如果内核完全在物理内存里，换出页表的页之类的事就很难做；如果内核有自己独立的地址空间，用户与内核之间搬数据又会很麻烦。

于是内核对应用程序来说几乎像一个库——只不过是受保护的。保护靠页表中的保护位：它规定 CPU 必须处于哪个特权级才能访问该页。用户代码访问系统页会陷入 OS，进程多半被终止。

OS 要支持一大类应用和系统，结果往往哪个都支持得不够好。VMS 要跑在从廉价到高端的一整个 VAX 家族上；今天的 Linux 要在手机、电视盒、笔记本、台式机和跑着上千进程的云服务器上都表现良好。

VMS 的页替换：分段 FIFO 与二次机会链表

VAX 的 PTE 包含：有效位、4 位保护字段、修改（脏）位、5 位 OS 保留字段、PFN。细心的读者会发现：没有引用位（reference bit）！所以 VMS 的替换算法得在没有硬件帮助判断"哪些页活跃"的情况下工作。设计者还担心内存霸占者（memory hogs）：用很多内存、让其他程序难以运行的程序。前面学的多数策略（比如全局 LRU）都不能在进程间公平地分配内存。

Babaoglu 和 Joy 在 1980 年代初证明：可以用 VAX 的保护位模拟引用位。把页表中所有页标为不可访问（把真实权限记在 PTE 的"OS 保留字段"里）；进程访问某页时陷入 OS，OS 检查它本应可访问，就恢复正常权限。替换时，仍标记为不可访问的页就是最近没被用过的。关键是平衡：标得太勤开销太大；标得太少，所有页最终都被"引用"，又分辨不出该踢谁。

VMS 的解法是分段 FIFO（segmented FIFO）：

  1. 每个进程有一个能驻留内存的最大页数，即驻留集大小（resident set size，RSS）；这些页按 FIFO 链起来。进程超过 RSS 时，踢出"先进"的那一页。纯 FIFO 不需要任何硬件支持。
  2. 纯 FIFO 表现不好，于是加两个二次机会链表（second-chance lists）：全局的干净页空闲链表和脏页链表。进程 P 超过 RSS 时，被移出 FIFO 的页若干净就放到干净链表尾部，若脏就放到脏链表尾部。
  3. 另一个进程 Q 需要空闲页时，从干净链表头部取一页。但如果 P 在这页被真正回收前又访问了它，P 可以直接从空闲（或脏）链表找回（reclaim），省掉一次昂贵的磁盘访问。

二次机会链表越大，分段 FIFO 就越接近 LRU。此外，为了弥补小页导致的磁盘 I/O 低效，VMS 使用聚集（clustering）：从全局脏链表中成批取出页，一次写到磁盘（写完它们就变干净了）。因为页可以放在交换空间的任何位置，OS 可以自由地把页分组，做更少、更大的写。

懒惰的技巧：按需清零与写时复制

要懒惰（Be lazy）。推迟工作有两个好处：一是降低当前操作的延迟、提高响应速度（例如 OS 常常立即报告文件写入成功，稍后才在后台写盘）；二是有时根本不必做了（例如写入的文件很快被删除）。不过交作业还是别太懒。

按需清零（demand zeroing）

考虑往堆里添加一页。朴素做法：找一个物理页，清零（为了安全，否则你能看到别的进程以前留在这页上的数据！），再映射进地址空间。如果进程根本没用这页，这些工作就白做了。按需清零的做法：添加页时只在页表里放一个标为不可访问的条目；进程读或写这页时陷入 OS，OS 通过 PTE 的"OS 保留"位发现这是一个按需清零页，这时才找物理页、清零、映射。进程若从不访问，这些工作全省了。

写时复制（copy-on-write，COW）

思想至少可追溯到 TENEX：OS 需要把一页从一个地址空间复制到另一个时，不真的复制，而是把它映射进目标地址空间，并在两边都标为只读。如果双方都只读，就什么也不用做，快速"复制"了而没有搬任何数据。若一方试图写，就陷入 OS；OS 发现这是 COW 页，于是（懒惰地）分配新页、填入数据、映射到出错进程的地址空间，进程继续执行并拥有了私有副本。

COW 对共享库很有用（许多进程以 COW 方式映射同一个库，省内存）。对 UNIX 更关键：fork() 要复制调用者的整个地址空间，又慢又费数据搬运；而多数情况下紧接着的 exec() 会把地址空间整个覆盖掉。COW 版的 fork() 保留了正确语义，又避免了大部分无谓的复制。

Linux 的地址空间

和其他现代系统（以及 VAX/VMS）一样，Linux 虚拟地址空间分为用户部分（代码、栈、堆等）和内核部分（内核代码、内核栈、内核堆等）。上下文切换时用户部分改变，内核部分在各进程间相同；用户态程序不能访问内核页，只有陷入内核、切到特权模式才行。（原书脚注：这是 KPTI 出现之前的情况，见后文。）

经典 32 位 Linux 在 0xC0000000（地址空间的 3/4 处）划分：0 ～ 0xBFFFFFFF 是用户虚拟地址，0xC0000000 ～ 0xFFFFFFFF 属于内核。64 位 Linux 有类似的划分，只是位置不同。

两种内核地址

  • 内核逻辑地址（kernel logical addresses）：内核"普通"的虚拟地址空间，用 kmalloc 获取。页表、每进程内核栈等大多数内核数据结构都在这里，并且不能被换出到磁盘。它与物理内存的开头部分直接映射：逻辑地址 0xC0000000 对应物理 0x00000000，0xC0000FFF 对应 0x00000FFF……于是两者互相转换极其简单（常被当成物理地址看待）；逻辑上连续的内存物理上也连续，适合需要物理连续内存的操作，比如设备的直接内存访问（DMA）。
  • 内核虚拟地址（kernel virtual addresses）：用 vmalloc 获取，只保证虚拟连续，每个页可以映射到不连续的物理页（因此不适合 DMA），但更容易分配，适合大缓冲区。在 32 位 Linux 里它还有一个作用：让内核能使用超过（大约）1 GB 的内存。64 位 Linux 中内核不再局限于最后 1 GB 虚拟空间，这个需求就不那么迫切了。

x86-64 页表：四级，48 位

x86 提供硬件管理的多级页表，每进程一个；OS 在内存中建好映射，把一个特权寄存器（CR3）指向页目录的起点，其余交给硬件。OS 只在进程创建、删除和上下文切换时介入，确保 MMU 用的是正确的页表。

从 32 位 x86 到 64 位 x86 是近年最大的变化：32 位地址空间终于不够用了。64 位 x86 使用四级页表，但目前只用虚拟地址的低 48 位：

内存继续变大，更多地址位会被启用，于是有了五级、将来也许六级页表——仅仅为了找出某个数据在内存哪里，就要走六级查找。（Linux 各级名称：P1 = PGD，P2 = PUD，P3 = PMD，P4 = PTE。严格说硬件要求第 48～63 位都等于第 47 位，这叫"规范地址（canonical address）"，否则访问会出错。）

大页（huge pages）

Intel x86 支持多种页大小：除 4KB 外，近来的设计在硬件上支持 2MB 甚至 1GB 的页。Linux 逐渐允许应用使用这些大页（huge pages）。大页能减少页表中需要的映射数量，但这不是主要动力；主要动力是更好的 TLB 行为：

  • 进程大量使用内存时，很快就把 TLB 填满。如果翻译都是 4KB 页的，不引起 TLB 未命中就能访问的内存非常少。对运行在数 GB 内存上的"大内存"负载，性能代价明显：有研究表明某些应用 10% 的 CPU 周期花在处理 TLB 未命中上。
  • 大页用更少的 TLB 槽位覆盖大片内存；此外 TLB 未命中路径更短（少走一级），分配在某些场景下也更快。

TLB 覆盖范围（TLB reach）计算器

TLB 能"覆盖"的内存 = 条目数 × 页大小。对比工作集大小，看 4KB 页和大页的差距。

Linux 对大页的支持是渐进的：起初开发者认为只有少数应用（比如有严苛性能需求的大型数据库）需要，于是只允许应用通过 mmap() 或 shmget() 显式申请大页，大多数应用不受影响。后来越来越多应用需要更好的 TLB 行为，Linux 加入了透明大页（transparent huge pages，THP）：开启后 OS 自动寻找机会分配大页（通常 2MB，有些系统 1GB），应用无需修改。

大页也有代价：最大的是内部碎片（页很大却只用了一点点），会让内存被大而少用的页填满；换页与大页配合不佳，有时会大大放大 I/O；分配开销在某些情况下也可能很糟。总之，4KB 这个服务多年的页大小已不再是万能解。

考虑渐进主义（incrementalism）。人们常鼓励"想大事、改变世界"。但很多时候，慢一点、渐进的方式才对：Linux 没有宣称"大页才是未来"，而是先提供专门的支持，了解利弊，等真有理由了再加通用支持。渐进常带来缓慢但深思熟虑、合乎情理的进步。

页缓存与 2Q 替换

为降低访问持久存储的代价，Linux 和其他系统一样使用激进的缓存。Linux 的页缓存（page cache）是统一的，保存三类来源的页：内存映射文件、来自设备的文件数据和元数据（通常通过 read()/write() 访问文件系统）、组成每个进程的堆和栈页（叫匿名内存（anonymous memory），因为下面没有具名文件，只有交换空间）。这些页放在一个页缓存哈希表中以便快速查找。

页缓存记录每页是干净还是脏（被修改）。脏数据由后台线程（pdflush）定期写回后备存储（文件数据写回文件，匿名数据写到交换空间）：要么过了一段时间，要么脏页太多（两个参数都可配置）。

内存不足时，Linux 使用修改版的 2Q 替换算法。动机：标准 LRU 很有效，但会被某些常见访问模式破坏。比如一个进程反复读一个很大的文件（接近或超过内存大小），LRU 会把其他所有文件都踢出内存；更糟的是，留着这个大文件的部分页也没用，因为它们在被再次访问前就被踢掉了。

Linux 的 2Q 保持两个链表并在它们之间划分内存：页第一次被访问时放进一个队列（原论文叫 A1，Linux 叫 inactive 链表）；再次被访问时提升到另一个队列（原论文 Aq，Linux 叫 active 链表）。替换时从 inactive 链表选牺牲者。Linux 还会周期性地把 active 链表底部的页移到 inactive 链表，使 active 链表约占页缓存的 2/3。理想情况下两个链表都按完美 LRU 排序，但那太贵，实际用的是类似时钟算法的近似。

LRU vs 2Q：一次大文件扫描的冲击

同一访问序列同时喂给容量相同的 LRU 缓存和 2Q 缓存（active 最多占 2/3）。先反复访问热页 A、B、C，再顺序扫描一个大文件（页 1…8，只读一次），最后回到热页。看谁还留着热页。

内存映射早于 Linux 就有了。对一个已打开的文件描述符调用 mmap()，进程得到一个指向虚拟内存区域开头的指针，文件内容"好像"就在那里；之后用普通的指针解引用就能访问文件的任意部分。访问尚未调入内存的部分会触发页错误，OS 调入相应数据并更新页表（即按需分页）。每个普通 Linux 进程都在用内存映射文件，即使 main() 没直接调用 mmap()——可执行文件和共享库的代码就是这样装入的。下面是原书中 pmap 对 tcsh 的（高度删节的）输出，四列分别是虚拟地址、大小、保护位、映射来源：

00007f4e7d2d0000   36K r-x-- libcrypt-2.23.so

tcsh 自己的代码，libc、libcrypt、libtinfo 和动态链接器 ld.so 的代码都被映射进地址空间；还有两个匿名区域：堆（第二行 anon）和栈。内存映射文件为 OS 构造现代地址空间提供了直接而高效的方式。

安全：缓冲区溢出、NX、ROP 与 ASLR

现代 VM 系统（Linux、Solaris、BSD）与古老系统（VAX/VMS）最大的区别，大概就是对安全的重视。机器之间前所未有地互联，开发者实现了各种防御手段来阻止狡猾的攻击者夺取系统控制权。

一大威胁是缓冲区溢出（buffer overflow）攻击，既能针对普通用户程序，也能针对内核。攻击者找到一个 bug，借此把任意数据注入目标的地址空间。这类漏洞往往源于开发者（错误地）假设输入不会太长，于是（信任地）把输入拷进缓冲区；输入其实太长，溢出缓冲区，覆盖了目标内存。看似无害的代码就能出问题：

int some_function(char *input) {
    char dest_buffer[100];
    strcpy(dest_buffer, input); // oops, unbounded copy!
}

很多时候溢出只会让程序崩溃。但恶意程序员可以精心构造溢出输入，注入自己的代码，从而接管系统：在联网的用户程序上成功，就能执行任意计算甚至出租被攻陷机器的算力；在 OS 上成功，就能访问更多资源，这叫特权提升（privilege escalation）（用户代码获得内核权限）。

  • 第一道防线：NX 位（No-eXecute）。AMD 在其 x86 版本中引入（Intel 有类似的 XD 位）：PTE 中设置了该位的页不能执行代码。攻击者注入到栈上的代码就无法运行。
  • 攻击者的回应：面向返回的编程（return-oriented programming，ROP）。程序地址空间里本来就有大量代码片段（ROP 术语叫 gadget），链接了庞大 C 库的程序尤其多。攻击者覆盖栈，让当前函数的返回地址指向某个想要的恶意指令（或指令序列），后面跟一条 return 指令；把大量 gadget 串起来（确保每次 return 都跳到下一个 gadget），就能执行任意代码。其早期形式叫 return-to-libc 攻击。
  • 再防御：地址空间布局随机化（ASLR）。OS 不再把代码、栈、堆放在固定位置，而是随机化它们的位置，使构造 ROP 所需的精确地址序列变得非常困难。多数针对漏洞用户程序的攻击因此只会导致崩溃，而无法控制程序。内核也用了同样的思路，叫 KASLR。

Meltdown、Spectre 与 KPTI

原书写作时（2018 年 8 月），系统安全界被两个相关的新攻击颠覆了：Meltdown 和 Spectre。它们几乎同时被四组研究者/工程师发现，让人们深刻怀疑硬件和 OS 所提供的基本保护。Spectre 被认为更难对付。

两者利用的共同弱点是：现代 CPU 在幕后做各种疯狂的优化。核心之一是推测执行（speculative execution）：CPU 猜测接下来会执行哪些指令并提前执行。猜对了程序更快；猜错了，CPU 撤销它们对架构状态（例如寄存器）的影响，再走正确的路。问题在于推测往往会在系统其他部分留下痕迹，比如处理器缓存、分支预测器等。攻击者由此可以推断出内存内容，甚至是我们以为受 MMU 保护的内存。

加强内核保护的一个途径是：从每个用户进程中尽量移除内核地址空间，为大部分内核数据使用单独的内核页表，这叫内核页表隔离（kernel page-table isolation，KPTI）。进程中只保留最低限度的内核映射；进入内核时需要切换到内核页表。这提升了安全、堵住了一些攻击途径，但有代价：性能，切换页表很昂贵（例如 TLB 中的翻译可能要作废）。安全的代价：便利与性能。

KPTI 并没有解决上面所有安全问题，只解决了一部分。而简单粗暴的办法（比如关闭推测执行）没有意义，系统会慢上千倍。要真正理解这些攻击，得先深入学习现代计算机体系结构（尤其是推测及其实现机制），再去读 Meltdown 和 Spectre 的论文（spectreattack.com），它们其实也包含了不错的推测执行入门。还有哪些问题没被发现？谁知道呢。

先预测再验证

在 VAX 地址拆解器中输入 0x00000000 和 0x00000200。它们的段内 VPN 各是多少？为什么前者会陷入 OS 而后者可能正常？
看答案
页大小 512 = 29 字节，所以 VPN = 地址 >> 9。0x0 的 VPN 为 0，0x200 的 VPN 为 1。VMS 把 P0 的第 0 页标为无效，代码从第 1 页开始，所以空指针解引用在查页表时发现 PTE 无效，陷入 OS。
在分段 FIFO 模拟器中（默认序列，8 个页框，RSS=3，聚集大小 2），预测：第 6 步 P 再次访问 P1 时要不要读磁盘？P2、P3 被移出驻留集后各去了哪里、最后命运如何？
看答案
第 4 步 P 装入第 4 个页，超过 RSS，干净的 P1 进干净链表尾部；第 5 步写过的 P2 被移出，进脏链表。第 6 步访问 P1 时它还在干净链表上，于是被找回，不读磁盘；同时 P3（也写过）被移出进脏链表，脏链表凑够 2 页，P2、P3 被聚集成一次磁盘写，变成干净页挂到干净链表尾部。之后 Q 需要页框：先用空页框，用完后从干净链表头部拿走了 P2 所在的页框，P2 被真正回收（第 14 步 P 再访问 P2 只能读磁盘）；而 P3 在被拿走之前又被 P 访问（第 11 步），再次被找回。整个序列 13 次磁盘读，没有二次机会链表的纯 FIFO 要 15 次。
在 COW 动画中，fork 之后、任何一方写之前，物理内存里有几个页框被使用？父进程写第 1 页之后呢？子进程随后也写第 1 页时，还需要复制吗？
看答案
fork 后仍然只有 4 个页框（代码、数据、堆、按需清零得到的新堆页），全部被两个进程共享，引用计数为 2。父进程写第 1 页 → 复制出第 5 个页框。子进程再写第 1 页时，原页框的引用计数已经降为 1，只有它自己在用，OS 只需把 PTE 改回可写，不必复制（这是 Linux 等系统的常见优化）。
在 x86-64 拆分器中输入 0x7ffd3e55d2b4，先手算 P1～P4 索引再验证。切到 2MB 大页，偏移变成多少位？
看答案
4KB 页：P1 = 255，P2 = 500，P3 = 498，P4 = 349，偏移 = 0x2b4。2MB 大页时最后一级不再需要，偏移变为 21 位（0x15d2b4），只走 PML4 → PDPT → PD 三级。
在 LRU vs 2Q 模拟器中，预测最后三次访问 A、B、C 各自在两种缓存里是否命中。
看答案
LRU：扫描的 8 个页把 A、B、C 全部挤出，最后三次全部未命中。2Q：A、B、C 在第二次访问时已被提升到 active 链表；扫描页只进 inactive 链表并从那里被淘汰，所以最后三次全部命中。
运行实验里的 ./cow。为什么 fork 只花了不到 1 毫秒，而子进程第一遍写 64 MB 却要几十毫秒，第二遍又不到 1 毫秒？
看答案
fork 只复制页表并把可写页标为只读 COW，不复制数据。子进程第一遍写时每页触发一次页错误（16384 次 minor fault），OS 分配新页并复制 4KB；第二遍这些页已经是私有可写的，没有页错误，只剩普通内存写入。smaps 中的 Shared_Dirty 变为 Private_Dirty 也印证了这一点。

动手实验

三个小程序分别观察写时复制、ASLR、按需分页（含按需清零与大页）。

for i in 1 2 3; do ./aslr; done; setarch -R ./aslr
./mmap_touch

  [child  after fork ] smaps: Rss  65536 kB   Shared_Dirty  65536 kB   Private_Dirty      0 kB
child : 1st write pass   46.14 ms, minor faults 16384   <- copy-on-write

fork 后 64 MB 全部是 Shared_Dirty（与父进程共享）；子进程第一遍写触发 16384 次 COW 页错误（正好每页一次），第二遍零次；之后全部变成 Private_Dirty，而父进程看到的数据不受影响。

  minor faults 65536, RSS grew 0 kB, sum of bytes = 0 (all zero)

  after mmap          : RSS    1640 kB
  wrote  25% of pages : RSS   67708 kB   minor faults so far    165   (42.8 ms)
  wrote  50% of pages : RSS  133244 kB   minor faults so far    197   (85.3 ms)
  wrote 100% of pages : RSS  263676 kB   minor faults so far    639   (179.9 ms)

mmap 256 MB 后 RSS 几乎不变——只分配了虚拟空间。写多少页，RSS 就长多少，每页一次 minor fault（按需分配 + 清零）。只读不写时每页也有一次页错误，但 RSS 一点没长：Linux 把所有只读的零页映射到同一个共享的"零页"，读到的全是 0，真正写的时候才分配（又一次懒惰）。用 2MB 透明大页时页错误从 65538 次降到几百次（理想是 256MB/2MB = 128 次；部分区域因对齐或分配失败退回 4KB 页）；每次页错误要清零 2MB，所以这里总时间并没有变短——大页的主要收益在之后的 TLB 命中率。

自测题

VAX-11 的虚拟地址由哪几部分组成？
32 位地址，页大小 512 = 29 字节，所以 9 位偏移、23 位 VPN；VPN 最高两位区分 P0/P1/S 段。D 是 x86-64。
VMS 为什么把用户页表放在内核虚拟内存（S 段）中？
页表从内核虚拟内存分配后，也可以被换出。代价是地址转换可能要先查系统页表。
关于 VMS 的分段 FIFO，哪项是错的？
VAX 的 PTE 根本没有引用位，这正是 VMS 采用 FIFO + 二次机会链表的原因。
按需清零（demand zeroing）在什么时候真正清零一个物理页？
添加页时只放一个不可访问的 PTE；第一次读写触发陷入，OS 才找页、清零、映射。从不访问就不做。
fork() 使用写时复制后，下列哪种情况会真正复制一个页？
共享页在两边都是只读的；写入触发保护陷阱，OS 识别为 COW 页，才分配新页并复制。exec 会丢弃整个旧地址空间，根本不需要复制。
Linux 内核逻辑地址（kmalloc）与内核虚拟地址（vmalloc）的关键区别是？
kmalloc 内存与物理内存开头直接映射（0xC0000000 → 0x0），不可换出；vmalloc 的每页可以映射到任意物理页，更易分配大块，但不适合 DMA。
x86-64 使用 4KB 页时，48 位虚拟地址 0x7ffd3e55d2b4 的最高级索引（P1）是多少？
P1 = 地址 >> 39 的低 9 位 = 0x7ffd3e55d2b4 >> 39 = 0xFF = 255。用模拟器验证。
大页（huge pages）的主要动力是什么？
原书明确说减少映射数"不是驱动力"，主要是 TLB。大页反而会增加内部碎片（A 错），与换页配合也不好（C 错）。
Linux 的 2Q 替换如何应对"反复读一个超大文件"的负载？
只有被再次访问的页才提升到 active。循环扫描的大文件页在被再访问前就从 inactive 被踢走，不会冲掉热页。
ASLR 主要是为了防御哪类攻击？
NX 阻止执行注入的代码后，攻击者转而复用已有代码（ROP）。ASLR 随机化代码、栈、堆的位置，使这些地址难以预测。

常见误区与小结

  • "fork 会复制整个地址空间"——有 COW 后，fork 只复制页表；真正的复制推迟到写入时，并且只复制被写的页。
  • "mmap 一大块内存就立刻占用那么多物理内存"——按需分页：只有被触碰（写）的页才分配物理页框；只读未写的匿名页甚至共享同一个零页。
  • "内核有自己独立的地址空间"——传统上（VMS、KPTI 之前的 Linux）内核被映射进每个进程地址空间的上半部分，靠保护位隔离；KPTI 之后用户态只保留极少内核映射。
  • "大页只有好处"——内部碎片、与换页配合差、某些情况下分配开销大。
  • "有了 NX 就安全了"——ROP 复用程序中已有的代码片段，完全绕过 NX；还需要 ASLR 等防御，而单个地址泄露就可能让 ASLR 失效。
  • "x86-64 用满了 64 位地址"——目前只用低 48 位（四级页表），高 16 位必须是第 47 位的符号扩展。
  • VAX/VMS：32 位地址、512B 小页 → 用分段（P0/P1/S）和把用户页表放在可换出的内核虚拟内存来控制页表大小；第 0 页无效捕获空指针；内核映射进每个地址空间。
  • 没有引用位的 VMS 用分段 FIFO（每进程 RSS）+ 全局干净/脏二次机会链表近似 LRU，并聚集脏页写回。
  • 懒惰优化：按需清零、写时复制（COW 让 fork+exec 几乎不复制数据）。
  • Linux：用户/内核划分（32 位在 0xC0000000）；内核逻辑地址（直接映射，可 DMA）与内核虚拟地址（vmalloc）；x86-64 四级页表，48 位地址 = 4×9 + 12；大页改善 TLB 覆盖，经历了从显式申请到透明大页的渐进过程。
  • 统一页缓存 + 2Q（inactive/active）抵抗大文件扫描；pdflush 后台写回脏页。
  • 安全：缓冲区溢出 → NX → ROP → ASLR/KASLR；Meltdown/Spectre 利用推测执行的痕迹，KPTI 用独立内核页表换取安全，代价是性能。
