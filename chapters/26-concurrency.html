本章要解决什么

如何支持同步？为了构建有用的同步原语，我们需要硬件提供什么支持？需要操作系统提供什么支持？怎样正确、高效地构建这些原语？程序又该怎样使用它们来得到期望的结果？

CRUX: How to support synchronization. What support do we need from the hardware in order to build useful synchronization primitives? What support do we need from the OS? How can we build these primitives correctly and efficiently? How can programs use them to get the desired results?

前两部分里，操作系统做了两件大事：把一个物理 CPU 虚拟成多个 CPU（进程），把物理内存虚拟成每个进程私有的大地址空间。这一章引入单个进程内部的新抽象——线程（thread）：一个程序不再只有一个执行点（一个 PC），而是有多个执行点，它们共享同一个地址空间。

共享带来了方便，也带来了全书"并发"部分的核心麻烦：两个线程同时更新一个变量，结果可能是错的，而且每次运行都不一样。本章用一个只有一行的 counter = counter + 1 把问题彻底拆开，给出四个关键术语，并引出后面几章要造的工具：锁（第 28 章）、条件变量（第 30 章）、信号量（第 31 章）。

核心概念速览

线程（thread）

进程里的一个独立执行流：有自己的 PC 和寄存器，但与同进程的其他线程共享地址空间（代码、全局变量、堆）。

线程控制块（TCB）

类似进程的 PCB。线程切换时把寄存器保存到 TCB；但不用切换页表，因为地址空间没变。

每线程一个栈

局部变量、参数、返回地址放在各自的栈上，称为线程本地存储（thread-local storage）。

为什么用线程

① 并行（parallelism）：多个 CPU 一起干活；② 避免 I/O 阻塞：一个线程等 I/O，另一个继续计算。

不受控的调度

调度程序可以在任意两条指令之间切换线程。一条 C 语句往往是好几条指令，中途被打断就可能出错。

竞态条件（race condition）

结果取决于线程执行的时序。counter 从 50 加两次，可能只得到 51。

原子性（atomicity）

"要么全做，要么全不做"，中间状态对外不可见。我们希望一段指令像一条指令那样原子地执行。

同步原语（synchronization primitive）

用少量硬件指令 + 操作系统支持构造出来的通用工具（锁、条件变量……），用来让临界区原子地执行。

线程是什么：多个 PC，一个地址空间

单线程进程只有一个执行点。多线程程序有多个执行点，每个都在取指、执行。可以把每个线程想成一个"小进程"，区别只有一个：它们共享同一个地址空间，因此可以访问相同的数据。

线程的状态和进程很像：有程序计数器（PC）、有一组私有寄存器。两个线程在同一个 CPU 上轮流运行时，也要做上下文切换（context switch）：保存 T1 的寄存器到它的 TCB，恢复 T2 的寄存器。与进程切换相比有一个大区别：地址空间不变，不需要切换页表（也就不用清 TLB 之类的连带开销）。

状态每个线程私有同一进程的线程共享
程序计数器 PC、通用寄存器（如 %eax）✔ 保存在各自的 TCB
栈（局部变量、参数、返回地址）✔ 每个线程一个栈
代码段✔
全局变量 / 静态变量（如 counter）✔ ← 竞态条件的来源
堆（malloc 出来的数据）✔
页表（地址空间本身）、打开的文件✔

另一个大区别在于栈。经典单线程地址空间里只有一个栈，放在地址空间底部，和堆相向增长。多线程进程里，每个线程独立调用各种函数，所以每个线程都要有自己的栈（图 26.1 右）：

多个栈让原本"堆向下、栈向上、中间都是空闲"的漂亮布局不复存在。好在栈通常不需要很大（大量递归的程序除外），所以这通常不是问题。

为什么要用线程

原书给出两个主要理由：

  1. 并行（parallelism）：比如把两个大数组相加。单 CPU 上只能一个元素一个元素地做；有多个 CPU 时，每个 CPU 负责一部分就能大大加速。把单线程程序改造成能在多 CPU 上干活的程序叫并行化（parallelization），每个 CPU 一个线程是最自然的做法。
  2. 避免因为慢速 I/O 阻塞程序：一个线程在等网络、磁盘或缺页时，调度程序可以切到同一程序的其他线程继续计算或发出更多 I/O。这就像多道程序（multiprogramming）让进程之间重叠 I/O 与计算一样，只不过发生在一个程序内部。Web 服务器、数据库大量使用这种方式。

这两件事用多个进程也能做。但线程共享地址空间，共享数据非常方便，所以写这类程序时线程更自然；而逻辑上彼此独立、几乎不需要共享内存数据结构的任务，用进程更稳妥。

线程创建：谁先跑？说不准

下面是原书的 t0.c（图 26.2）：主线程创建两个线程 T1、T2，分别打印 "A" 和 "B"，然后用 pthread_join() 依次等它们结束。

void *mythread(void *arg) {
    printf("%s\n", (char *) arg);
    return NULL;
}

int main(int argc, char *argv[]) {
    pthread_t p1, p2;
    printf("main: begin\n");
    Pthread_create(&p1, NULL, mythread, "A");
    Pthread_create(&p2, NULL, mythread, "B");
    // join waits for the threads to finish
    Pthread_join(p1, NULL);
    Pthread_join(p2, NULL);
    printf("main: end\n");
    return 0;
}

创建线程有点像函数调用，但系统不是先执行完被调函数再返回，而是为它创建一个新的执行流，它和调用者独立运行：可能在 pthread_create 返回之前就跑，也可能很久以后才跑；先创建的线程也不一定先运行。到底谁先跑，由操作系统调度程序决定。下面这个小模拟器可以重放原书图 26.3、26.4、26.5 三种执行顺序，也可以随机生成别的合法顺序。

更糟的情况：共享数据

上面的例子线程之间没有共享数据。现在看原书的 t1.c（图 26.6）：两个线程都对全局变量 counter 加 1，各加 1000 万次，期望结果是 20,000,000。

static volatile int counter = 0;

void *mythread(void *arg) {
    printf("%s: begin\n", (char *) arg);
    int i;
    for (i = 0; i < 1e7; i++) {
        counter = counter + 1;      // ← 两个线程都在改同一个全局变量
    }
    printf("%s: done\n", (char *) arg);
    return NULL;
}
// main() 创建线程 "A"、"B"，join 两次后打印 counter

问题的核心：不受控的调度

要理解为什么会错，得看编译器为 counter = counter + 1 生成了什么。原书用 objdump -d 反汇编（学会用工具是原书反复强调的技巧），假设 counter 在地址 0x8049a1c：

mov 0x8049a1c, %eax    ; ① 读：把内存里的 counter 装进寄存器 eax
add $0x1, %eax         ; ② 改：eax = eax + 1
mov %eax, 0x8049a1c    ; ③ 写：把 eax 存回内存

一行 C 代码是三条指令。调度程序可以在任意两条指令之间通过定时器中断切换线程。关键在于：每个线程运行时都有自己私有的寄存器（上下文切换时保存/恢复），但 counter 在共享内存里。

原书的故事：counter 初值 50。T1 执行了 ① ②，它的 eax=51；此时定时器中断，OS 把 T1 的 PC 和寄存器存进 TCB。T2 被调度，完整执行 ①②③：读到的仍是 50，写回 51。再切回 T1，它恢复 eax=51，执行 ③——把 51 又写了一遍。代码执行了两次，counter 却只从 50 变成 51，而正确结果应是 52。

原书把代码放在地址 100 处（x86 指令变长：mov 占 5 字节，add 占 3 字节，所以三条指令分别在 100、105、108），并给出了精确的执行轨迹（图 26.7）。表中 PC、eax 是当前正在运行的线程在该指令执行之后的值：

这就是竞态条件（race condition），更具体地说是数据竞争（data race）：结果取决于代码执行的时机。运气不好（在不合时宜的时刻发生上下文切换）就会得到错误结果，而且每次可能不同——我们称这种结果是不确定的（indeterminate）。可能导致竞态条件的这段代码叫临界区（critical section）：访问共享变量（或更一般地，共享资源）的一段代码，它不能被多个线程同时执行。我们真正想要的是互斥（mutual exclusion）：一个线程在临界区内执行时，其他线程被阻止进入。

原子性的愿望

解决这个问题的一种办法是：让硬件提供一条更强大的指令，一步完成我们要做的事，这样就不可能在中间被打断。例如一条"超级指令"：

memory-add 0x8049a1c, $0x1

硬件保证它原子地（atomically）执行：中断发生时，这条指令要么还没执行，要么已经执行完，不存在中间状态。"原子"在这里的意思是"作为一个整体"，也常理解为"全有或全无"（all or none）。我们希望的正是把那三条指令原子地执行。

原子操作是构建计算机系统最强大的底层技术之一，从体系结构、并发代码，到文件系统（日志、写时复制）、数据库（把一组动作打包成一个事务 transaction）、分布式系统都在用。本部分里，我们用同步原语把一小段指令序列变成原子执行的块。

但一般情况下不会有这样的单条指令。想象你在写一棵并发 B 树——难道要让硬件提供一条"原子地更新 B 树"的指令吗？显然不现实。于是真正的路线是：向硬件要少量有用的指令，再加上操作系统的一些帮助，在此之上构建一套通用的同步原语（synchronization primitives），让多线程代码以同步、受控的方式访问临界区。这就是本部分要研究的问题（本页开头的 CRUX）。原书的原话：这是个美妙而困难的问题，应该让你的脑袋疼一点；如果不疼，说明你还没懂。

另一个问题：等待另一个线程

到目前为止，线程之间只有一种交互：访问共享变量，需要让临界区原子执行。实际上还有另一种常见交互：一个线程必须等另一个线程完成某件事后才能继续。例如进程发起磁盘 I/O 后被置为睡眠，I/O 完成时需要把它唤醒。所以后面几章不仅要构建支持原子性的同步原语，还要构建支持这种睡眠/唤醒交互的机制——这就是第 30 章的条件变量（condition variables）。

顺带一提：t0.c 里的 pthread_join() 正是"等另一个线程结束"的一个特例。

四个关键术语（Dijkstra）

原书专门用一个旁注列出这四个术语，它们大多由 Edsger Dijkstra 提出（他因为这些工作获得了图灵奖，1968 年的论文 "Cooperating Sequential Processes" 至今值得一读）。

临界区

CRITICAL SECTION

访问共享资源（通常是一个变量或数据结构）的一段代码。

例：counter = counter + 1 编译出的三条指令，从"读"到"写"整段。

竞态条件

RACE CONDITION（DATA RACE）

多个执行线程大致同时进入临界区，都试图更新共享数据，导致出乎意料（可能不希望的）结果。

例：图 26.7 中 50 加两次得到 51。

不确定性

INDETERMINATE

程序含有一个或多个竞态条件，输出随每次运行而变，取决于哪些线程在何时运行。

例：t1.c 每次输出的 counter 都不同。

互斥

MUTUAL EXCLUSION

用互斥原语保证同一时刻只有一个线程进入临界区，从而避免竞争，得到确定的输出。

例：t1_lock.c 用锁包住 counter++，结果永远正确。

为什么在操作系统课里学并发？

一个词：历史。操作系统是第一个并发程序，许多技术最初就是为 OS 内部发明的；后来有了多线程进程，应用程序员也必须考虑这些问题。

原书的例子：两个进程都调用 write() 向同一个文件末尾追加数据。为此内核要分配一个新块、在文件的 inode 里记录块的位置、修改文件大小……因为中断可能随时发生，更新这些共享结构（分配位图、inode）的代码都是临界区。从引入中断的第一天起，OS 设计者就得操心内核如何更新内部结构。页表、进程列表、文件系统结构——几乎每个内核数据结构都必须用合适的同步原语小心访问。

先预测，再验证

（改编自 Homework 第 7 题）模拟器选"固定时间片 -i"、2 个线程、每线程循环 1 次、counter 初值 0。先预测 i = 1、2、3、4 时最终 counter 分别是多少，哪些 i 能得到正确结果 2？
看答案

i=1：T1 读(0) → T2 读(0) → T1 加 → T2 加 → T1 写 1 → T2 写 1，结果 1。

i=2：T1 读、加 → T2 读(0)、加 → T1 写 1 → T2 写 1，结果 1。

i≥3：每个线程在一个时间片内完整执行三条指令，中断恰好落在临界区之外，结果 2。关键不在于中断频繁与否，而在于中断是否落在读与写之间。

（改编自 Homework 第 7、8 题）把每线程循环次数改为 3（相当于 -a bx=3），期望结果是 6。预测 i = 1…6 中哪些能得到 6？哪个 i 的结果最出乎意料？
看答案

用模拟器实测（初值 0）：i=1 → 3，i=2 → 3，i=3 → 6，i=4 → 4，i=5 → 4，i=6 → 6。

只有 i 是 3 的倍数时，每次切换都恰好落在一次完整的"读-加-写"之后，结果才正确。i=4、5 的时间片比 i=3 更长，结果却错了：中断落在了某次读和写之间。更长的时间片不等于更安全，要看中断落在哪里。（真实的 x86.py 程序还有循环控制指令，具体数字会不同，但结论相同。）

（改编自 Homework 第 6 题）临界区到底是哪几条指令？中断发生在什么位置是"安全"的？
看答案

临界区是从 mov 0x8049a1c,%eax（读）到 mov %eax,0x8049a1c（写）的整段三条指令。中断落在一次完整的读-加-写之前或之后是安全的；落在读之后、写之前（PC=105 或 108 时），只要别的线程在此期间写了 counter，就会丢失更新。在模拟器里注意执行轨迹中标红的写回行。

2 个线程，每线程循环 k 次（k ≥ 2），初值 0。正确结果是 2k。最坏情况下最终 counter 能小到多少？先猜，再点"载入'最小结果'交错"验证（它按 k=2 构造）。
看答案

答案是 2，与 k 无关！构造方法：T1 读到 0 后被打断；T2 连续做完 k−1 次（counter=k−1）；T1 写回 1（抹掉 T2 的全部成果）；T2 读到 1 后被打断；T1 做完剩下 k−1 次（counter=k）；T2 写回 2。一次恶意的交错就能抹掉几乎所有工作——这也解释了为什么 t1.c 在单 CPU 上偶尔会一下子丢掉几百万。

勾选"原子执行"，然后随便换调度方式、时间片、种子、线程数。最终 counter 还会出错吗？"推迟的中断"统计说明了什么？
看答案

永远正确（= 初值 + 线程数 × 循环次数）。原子执行时，若时间片在块中间到期，中断被推迟到块结束，所以任何线程都不可能在另一个线程的"读"和"写"之间写 counter。现实中硬件不会替你推迟中断，我们要用锁在软件层面达到同样的效果（第 28 章）。

示例输出，你的机器上数字会不同（本机 AMD Ryzen 7 8745H，16 个逻辑 CPU，WSL2，gcc 14.2）。

怎么解读：

  • 多核上两个线程真正同时运行，几乎每次读-改-写都可能撞车，所以丢了将近一半（约 1050 万）。
  • 单 CPU 上只有定时器中断恰好落在读和写之间才出错，所以有时完全正确；可一旦出错，被打断的线程恢复后把很旧的值 + 1 写回，抹掉另一个线程整整一个时间片的累加——所以一错就是几百万（正是上面"最小结果"练习的现实版本）。
  • ./t1 1000 "碰巧正确"：线程 A 在 B 启动前就跑完了，根本没有重叠。竞态条件并不是每次都出现，这正是它难以调试的原因。
  • 加锁后永远正确，但慢了一个数量级：互斥换来了正确性，也带来了开销（第 28、29 章的主题）。

自测题

1. 同一进程中的两个线程，下列哪项是每个线程私有的？
线程共享地址空间（代码、全局变量、堆、页表），但每个线程有自己的 PC、寄存器（保存在 TCB）和栈。
2. 同一进程内的线程切换，和进程切换相比最主要的区别是？
线程切换同样要保存/恢复寄存器（到 TCB），但地址空间相同，不用切换正在使用的页表。
3. counter = counter + 1 为什么会产生竞态条件？
每个线程运行时都有自己私有的寄存器，问题在于"读-改-写"是三条指令，中间可以被打断，另一个线程可能在此期间写 counter。
4. 在原书图 26.7 的轨迹中，counter 从 50 开始，两个线程各执行一次 +1，最终是多少？丢了几次更新？
T1 读到 50，被打断；T2 完整执行写入 51；T1 恢复后把自己算出的 51 再写一遍。最终 51，丢失 1 次更新。
5. 下列关于临界区（critical section）的说法，哪个最准确？
原书定义：访问共享变量（或共享资源）的一段代码，必须不能被多个线程并发执行。它可以在用户程序里，也可以在内核里。
6. 在只有一个 CPU 的机器上运行 t1.c，会出现竞态条件吗？
原书强调"even on a single processor"也会出错：并发（交错执行）就足够，不需要真正的并行。实验里 make single 也会出错。
7. 为什么不让硬件为每种需求都提供一条原子指令（比如"原子更新 B 树"）？
原书："would we really want the hardware to support an atomic update of B-tree instruction? Probably not." 我们只向硬件要几条有用的指令，再在其上构建锁、条件变量等。
8. 除了"原子地访问共享变量"，本章提到线程之间还有哪种常见交互，将由条件变量解决？
例如进程等磁盘 I/O 完成时被睡眠、完成后被唤醒。第 30 章的条件变量就是为这种交互设计的。
9. 在 t0.c 中，"main: end" 为什么一定在 A 和 B 之后打印？
join 会等待指定线程结束（若它已结束则立即返回）。A 和 B 之间的顺序不确定，但它们都在 main: end 之前。

常见误区

  • "一行 C 代码就是一步"：不是。counter++ 通常是读、改、写三条指令，任何两条之间都可能切换。
  • "单核机器上没有并发问题"：有。只要有抢占式调度，交错执行就足以引发竞态条件。
  • "先创建的线程先运行"：没有任何保证，谁先运行由调度程序决定（图 26.5 中 B 就先于 A）。
  • "寄存器是共享的，所以会出错"：恰恰相反，寄存器由上下文切换虚拟化，每个线程私有。出错是因为内存中的 counter 是共享的，而线程基于过时的私有副本写回。
  • "跑了几次都对，所以代码没问题"：竞态条件依赖时序，可能很少出现（比如 ./t1 1000 碰巧正确）。正确性要靠推理，而不是靠测试运气。
  • "volatile 能保证原子性"：volatile 只让编译器每次都真的去读写内存，并不让读-改-写成为一个原子操作。

本章小结

  • 线程 = 进程内的独立执行流：私有 PC、寄存器、栈；共享代码、全局数据、堆和页表。线程切换要保存 TCB，但不切换地址空间。
  • 用线程的两个理由：并行加速、以及在 I/O 阻塞时让程序的其他部分继续推进。
  • 线程执行顺序由调度程序决定，不可预测；共享数据时，这种不可预测性会导致竞态条件和不确定的结果。
  • 根源是不受控的调度 + 非原子的多指令临界区。我们需要互斥，让临界区像一条原子指令那样执行。
  • 路线图：第 27 章先认识 pthread API；第 28 章用硬件原语（test-and-set 等）和 OS 支持构建锁；第 29 章把锁用进数据结构；第 30 章用条件变量解决"等待另一个线程"；第 31 章的信号量把两者统一起来。
