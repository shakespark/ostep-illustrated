这一章要解决什么

如何让所有的写都变成顺序写？文件系统怎样才能把所有写操作都变成顺序写？对读来说这不可能——要读的块可能在磁盘任何地方；但对写来说，文件系统总是有选择权（想写到哪儿就写到哪儿），我们要利用的正是这个选择权。

HOW TO MAKE ALL WRITES SEQUENTIAL WRITES? … For reads, this task is impossible … For writes, however, the file system always has a choice, and it is exactly this choice we hope to exploit.

上一章（崩溃一致性）我们学会了用日志（journal）保证更新的原子性；上上章（FFS）我们学会了"按局部性放置数据"。20 世纪 90 年代初，伯克利的 Ousterhout 和 Rosenblum 走得更远：干脆把整个磁盘当成一条日志，所有更新（数据和元数据）先在内存里攒成一大段，再一口气顺序写到磁盘的空闲位置，从不原地覆盖。这就是日志结构文件系统（Log-structured File System，LFS）。

他们的出发点是四个观察：

  • 内存越来越大：读请求越来越多地被缓存吸收，磁盘流量以写为主，文件系统性能主要取决于写性能。
  • 随机 I/O 与顺序 I/O 的差距越来越大：传输带宽涨得快，寻道和旋转延迟降得慢。能顺序使用磁盘，就能获得巨大优势。
  • 已有文件系统在常见负载下表现差：FFS 创建一个一块大小的文件要写 6 次（见下图），都是短寻道 + 旋转等待，远达不到峰值带宽。
  • 文件系统不感知 RAID：RAID-4/5 有"小写问题"，一次逻辑小写要 4 次物理 I/O。

核心概念速览

只追加的日志

所有更新（数据块、inode、目录、imap）都写到日志末尾的空闲位置，从不原地覆盖旧版本。

段（segment）与写缓冲

先在内存里攒满一个几 MB 的段，再一次写下去，把定位开销摊薄到可以忽略。

inode 映射（imap）

inode 号 → inode 最新磁盘地址的间接层。inode 每次都搬家，靠 imap 找到它。

检查点区域（CR）

磁盘上唯一固定位置的结构，记录各 imap 片段的地址；每隔约 30 秒才更新一次。

递归更新问题

inode 搬家若要改目录、目录又搬家……会一路改到根。imap 让目录只存 inode 号，问题消失。

段摘要块（SS）

每段开头记录每个块属于"哪个 inode 的第几块"，清理器据此判断块是否还活着。

清理（cleaning）

读入 M 个半空的段，只把活块压缩写成 N 个新段（N < M），腾出整段空闲空间。

两个 CR + 前滚（roll forward）

CR 交替写、头尾带时间戳保证原子性；重启后从检查点沿日志往后扫，找回之后写入的段。

顺序写：把一切都追加到日志末尾

先看最简单的情况：往文件里写一个数据块 D。LFS 把 D 写在磁盘地址 A0；但光写数据不够，文件的 inode 也要更新、要指向 D。于是 LFS 把 inode 紧挨着 D 写下去（图中 inode 画得和数据块一样大，实际上 inode 通常只有约 128 字节，数据块是 4KB）：

光"顺序"还不够：还得"一次写很多"

假设在时刻 T 往地址 A 写了一块，过了一会儿（T+δ）再写 A+1。地址是连续的，可在这 δ 里盘片已经转过去了：第二次写要等将近一整圈（Trotation − δ）才能落到盘面上。所以要达到峰值性能，必须一次发出大量连续的写（或一次大写）。

为此 LFS 使用一个古老的技术：写缓冲（write buffering）。更新先记在内存里，攒够了再一次写出。LFS 一次写出的这一大块叫做段（segment）（真实系统中是几 MB）。下例把两组更新攒进一个（很小的）段：对文件 j 的 4 个块写，以及给文件 k 追加 1 个块，然后把这 7 个块一次提交：

该缓冲多少？

答案取决于磁盘：定位开销（寻道 + 旋转）相对传输速率有多大。设每次写之前的定位时间是 Tposition，峰值传输率是 Rpeak，一次写出 D MB：

Twrite = Tposition + D / Rpeak　　　(43.1)
Reffective = D / Twrite = D / (Tposition + D / Rpeak)　　　(43.2)

我们希望有效带宽达到峰值的某个比例 F（0 < F < 1，比如 0.9），即 Reffective = F × Rpeak，解出 D：

D = F × Rpeak × (Tposition + D / Rpeak)　⇒　D = F / (1 − F) × Rpeak × Tposition　　　(43.6)

原书的例子：Tposition = 10 ms，Rpeak = 100 MB/s，F = 0.9，则 D = 0.9/0.1 × 100 MB/s × 0.01 s = 9 MB。注意 F/(1−F) 这一项：F 越接近 1，它涨得越猛——这就是"最后那几个百分点最贵"。

找到 inode：inode 映射（imap）

在传统 UNIX 文件系统里找 inode 很容易：inode 放在磁盘固定位置的数组里，地址 = inode 表起始地址 + inode 号 × inode 大小。FFS 稍复杂一点——inode 表被切成块分到各个柱面组——但仍然是简单的算术。

LFS 就麻烦了：inode 被撒满了整个磁盘，而且因为从不原地覆盖，最新版本的 inode 一直在搬家。算术失效了。

解决办法是加一层间接：inode 映射（inode map，imap），输入 inode 号，输出该 inode 最新版本的磁盘地址。可以把它想成一个简单数组，每项 4 字节（一个磁盘指针）。每当 inode 被写到磁盘，imap 就更新为新位置。

"计算机科学中的所有问题都可以通过增加一层间接来解决"——当然有点夸张，但确实能解决大多数问题。虚拟内存、文件本身都是间接；imap 则是 inode 号的虚拟化，让 inode 可以随便搬家而不必改所有引用它的地方。代价是额外开销，Wheeler 补了一句："……除了间接层太多这个问题。"

imap 必须持久化（否则崩溃后找不到 inode）。放在磁盘固定位置？那每次更新文件后都要跑去固定位置写 imap，又回到了寻道地狱。LFS 的做法是：把 imap 切成片段（chunk），和其他新数据一起写进日志。于是给文件 k 追加一个数据块时，实际写下的是：

imap 片段也撒在磁盘上了，那怎么找 imap？没有魔法：文件系统必须在磁盘上有一个固定且已知的起点。LFS 的这个起点叫检查点区域（checkpoint region，CR），它保存所有最新 imap 片段的地址。CR 只是定期更新（比如每 30 秒），所以不影响性能。

回顾：从磁盘读一个文件

  1. 挂载时先读 CR，得到所有 imap 片段的地址，把整个 imap 读进内存缓存。
  2. 给定 inode 号，在内存 imap 里查到 inode 的最新地址，读 inode。
  3. 之后与普通 UNIX 文件系统完全一样：用直接/间接/双重间接指针找数据块。

常见情况下，LFS 读文件的 I/O 次数与传统文件系统相同——imap 整个缓存在内存里，额外的工作只是一次内存查表。

imap 还顺手解决了一个严重问题：递归更新问题（recursive update problem）。任何"从不原地更新"的文件系统都会遇到它：inode 一更新就换了位置；如果目录里存的是 inode 的地址，目录就得跟着改（于是目录也搬家），目录的父目录又得改……一直改到根。

新问题：垃圾回收

LFS 总是把文件的最新版本（数据 + inode）写到新位置，于是磁盘上到处散落着旧版本，我们（很不客气地）称之为垃圾（garbage）。例如文件 k 只有一个数据块 D0，我们覆盖它：

如果是给文件 k 追加一个块，旧 inode 变成垃圾，但旧数据块 D0 仍被新 inode 指着，依然存活：

旧版本可以保留下来，让用户恢复误删、误改的文件——这叫版本化文件系统（versioning file system）。LFS 则只保留最新的存活版本，于是必须在后台定期清理（cleaning）这些旧版本，让空间可以重新写入——这是一种垃圾回收（garbage collection）。

关键在于按段清理。如果清理器只是零星地释放单个块，磁盘上会满是小空洞，LFS 再也找不到大片连续空间来顺序写，性能就崩了。所以清理器周期性地：读入 M 个旧的（部分使用的）段，找出其中的活块，把它们压缩写成 N 个新段（N < M），然后释放那 M 个旧段。

这留下两个问题：机制——怎么知道段里哪个块是活的？策略——多久清理一次、清理哪些段？

机制：用段摘要块判断存活

LFS 在每个段的开头放一个段摘要块（segment summary block，SS），为段中每个数据块记录它的 inode 号 N（属于哪个文件）和偏移 T（是文件的第几块）。判断地址 A 上的块 D 是否存活：

(N, T) = SegmentSummary[A];   // 1. 从段摘要查出：A 是 inode N 的第 T 块
inode  = Read(imap[N]);       // 2. 用 imap 找到 inode N 的最新版本
if (inode[T] == A)            // 3. 最新 inode 认为第 T 块在哪？
    // block D is alive       //    正好是 A → 活
else
    // block D is garbage     //    指向别处（或文件已删）→ 死

第 3 行是关键："活"的定义就是"最新的元数据还指向我"。一个块被覆盖后，新 inode 指向新位置，旧块自然判定为死。

LFS 还有捷径：文件被截断或删除时，LFS 增加它的版本号（version number）并记在 imap 里；段中也记录版本号。清理时先比较版本号，不一致就直接判死，省掉读 inode 的 I/O。

策略：何时清理、清理哪些段

何时比较简单：周期性地、空闲时、或者磁盘满了不得不清理时。清理哪些段更难，是许多论文的主题。原始 LFS 论文尝试区分热段（hot segment）和冷段（cold segment）：

崩溃恢复

LFS 正常运行时把写攒在内存段里，段满（或过了一段时间）就写到磁盘。这些写组织成一条日志：CR 指向日志的头段和尾段，每个段指向下一个要写的段。LFS 还会定期更新 CR。崩溃可能发生在这两类写中的任何一个时刻。

写 CR 时崩溃：两个 CR + 头尾时间戳

为了让 CR 更新是原子的，LFS 维护两个 CR，分别在磁盘两端，交替写。写 CR 时的协议：先写一个带时间戳的头部，再写 CR 主体，最后写一个同样带时间戳的尾块。如果在更新 CR 期间崩溃，头尾时间戳就会不一致；LFS 总是选择时间戳一致且最新的那个 CR。

写段时崩溃：前滚（roll forward）

CR 大约 30 秒才写一次，所以最后一个一致的快照可能已经很旧了。只读 CR 恢复的话，最后那几十秒的更新会丢失。LFS 借用数据库里前滚（roll forward）的技术：从最后一个 CR 出发，找到其中记录的日志末尾，继续往后读后续的段，看里面有没有有效的更新；有就应用到文件系统上，从而找回检查点之后写入的大部分数据和元数据（细节见 Rosenblum 的博士论文）。

总结：LFS 的遗产

LFS 引入了一种新的更新磁盘的方法：不原地覆盖文件，而是总写到磁盘的未使用部分，之后再通过清理回收旧空间。这种方法在数据库里叫影子分页（shadow paging），在文件系统里常叫写时复制（copy-on-write，COW）。

  • 大块写对很多设备都好：机械盘上把定位时间降到最低；RAID-4/5 上完全避开小写问题；研究表明闪存 SSD 也需要大 I/O 才能跑出高性能（下一章 SSD 的 FTL 正是日志结构的）。
  • 缺点是产生垃圾，清理的开销曾是 LFS 最大的争议（Seltzer 等人的对比研究），也许限制了它最初的影响力。
  • 但它的思想活在 NetApp WAFL、Sun ZFS、Linux btrfs 以及闪存 SSD 里。WAFL 甚至把缺陷变成了特性：保留旧版本作为快照（snapshot），用户误删文件时可以找回，同时也不必那么频繁地清理。

LFS 的大思路一句话就能说完，但真要做出能用的系统，必须想清楚所有棘手情况：imap 放哪、CR 如何原子更新、如何判断存活、何时清理。另一方面，当系统有根本缺陷时，想想能不能把它反过来变成有用的功能——WAFL 的快照就是范例。

看答案

存活块一样多：都是 8 个（根目录块、根 inode、foo 的 inode、4 个数据块、1 个 imap 片段），加上 CR。但逐块写 4 次日志里写了 19 块（11 块是垃圾），一次写 4 块只写了 13 块（5 块垃圾）。每次单块写都会多写一个 inode 和一个 imap 片段，前一次的就作废了。这正说明在内存里缓冲更新有多重要：真实 LFS 会把这 4 次写合并成一次。

（作业 Q7）对比 c,/foo:w,/foo,0,1 与 c,/foo:w,/foo,7,1。第二种情况下 inode 的 size 字段是多少？ptrs 长什么样？
看答案

两者都只写 1 个数据块、1 个 inode、1 个 imap 片段。但 w,/foo,7,1 之后 inode 的 size = 8，ptrs[0..6] 全空，只有 ptrs[7] 指向数据块——size 表示"逻辑长度（块数）"，是最大偏移 + 1，而不是真正分配的块数。中间是一个"空洞"（hole），不占磁盘空间。

（作业 Q8/Q9）预设"文件 vs 目录"和"硬链接"：c 和 d 分别写几个块？l（硬链接）写了哪些块？会分配新 inode 号吗？
看答案

c,/foo 写 4 块：新 inode、父目录的新数据块、父目录的新 inode、imap 片段。d,/bar 写 5 块：多一个新目录自己的数据块（含 . 和 ..），且父目录 inode 的 refs 加 1（子目录的 .. 指向它）。硬链接写 4 块：父目录数据块、父目录 inode、被链接文件的 inode（refs + 1）、imap 片段；不分配新 inode 号——目录里多了一个指向同一 inode 号的名字而已。

（作业 Q10）把"inode 号分配"改成"随机"，载入"作业 Q10"预设（连续创建多个文件）。imap 片段的写入有什么变化？这说明选择 inode 号为什么重要？
看答案

本模拟器每个 imap 片段覆盖 16 个 inode 号。顺序分配时新文件的 inode 号都集中在 0～15，每次创建只写 1 个 imap 片段；随机分配时新文件的 inode 号常落在另一个片段，而父目录（inode 0）在片段 0，于是一次创建要写两个 imap 片段，日志里的元数据更多。真实 LFS 中，让相关 inode 的号码聚集，就能让 imap 更新更紧凑。

CR-A 的头部已写成 ts=3，尾部还是 ts=1，头尾不一致，作废；用 CR-B（ts=2）。CR-B 的检查点只包含 S1～S3，所以不前滚会丢掉 S4、S5 里的更新（/c 的创建、b=v2、a=v3、删除 /b）。前滚从 S4 开始读，S4、S5 都完整有效，全部找回，丢失为 0。

自测题

1. imap 已经整个缓存在内存里时，LFS 读一个文件的数据块，与 FFS 相比额外的开销主要是？
CR 只在挂载时读一次，之后整个 imap 缓存在内存。原书：常见情况下 LFS 读文件的 I/O 次数与典型文件系统相同，额外的只是在 imap 里查 inode 地址。
2. 为什么 LFS 不把 imap 放在磁盘的固定位置？
原书 43.5：放在固定位置，每次文件结构更新后都要再写一次 imap，引入更多寻道。LFS 把 imap 片段和其他新数据一起写进日志。
3. 在目录 dir 中创建文件 foo 并写入一个块，这次写出的 imap 片段需要记录哪些 inode 的新位置？
foo 的 inode 是新的，dir 的数据块变了所以 dir 的 inode 也被重写到新位置——两个都搬了家，imap 要同时记录 m[k] 和 m[dir]（图 43-G）。
4. "递归更新问题"指的是什么？
任何从不原地更新的文件系统都会遇到它。LFS 让目录只存 inode 号，位置变化只反映在 imap 中，递归被截断。
5. 清理器检查地址 A 上的数据块：SS 说它是 (inode N, 偏移 T)；imap[N] 指向的 inode 中 ptrs[T] = A'，A' ≠ A。结论是？
存活的定义就是"最新 inode 的第 T 个指针正好指向 A"。指向别处说明这是被覆盖掉的旧版本。版本号只是省 I/O 的捷径，不是必要条件。
6. 按原始 LFS 论文的启发式，热段与冷段应该如何清理？
热段里的块还在不断被覆盖，等得越久死块越多、要搬的越少；冷段的空闲空间不会自己增长，早清早受益。
7. LFS 如何发现 CR 更新到一半就崩溃了？
写 CR 的协议：头（时间戳）→ 主体 → 尾块（时间戳）。头尾不一致即不完整；LFS 选时间戳一致且最新的那个 CR。两个 CR 交替写保证总有一个完整的。
8. Tposition = 10 ms，Rpeak = 100 MB/s，想达到峰值带宽的 99%，每次至少要写多少？
D = F/(1−F) × Rpeak × Tposition = 0.99/0.01 × 100 × 0.01 = 99 MB。对比 90% 只需 9 MB、95% 需 19 MB。
9. 前滚（roll forward）解决的是什么问题？
从最后一个一致 CR 记录的日志尾开始，往后读后续的段，把其中有效的更新应用上去，找回检查点之后的大部分数据和元数据。

常见误区与小结

  • "LFS 读也是顺序的"——不是。LFS 只优化写；读依赖内存缓存，读到的块可能散在磁盘各处。
  • "imap 每次读都要访问磁盘"——imap 在挂载时整体读入内存；写 imap 片段只是为了持久化。
  • "CR 每次写操作都会更新"——真实 LFS 大约每 30 秒更新一次（本页日志模拟器为了便于观察，每条命令都更新）。
  • "覆盖写只让旧数据块变垃圾"——旧 inode 和旧 imap 片段也都成了垃圾；追加写时旧数据块反而仍然存活。
  • "清理只是释放死块"——清理要把活块搬家并重写 inode/imap，本身也在消耗写带宽，还可能让其他段里的元数据作废。
  • "只要按地址顺序写就能跑满带宽"——两次间隔的小写之间盘片已经转走，必须一次写一大段。

本章小结

  • LFS 把所有更新（数据 + 元数据）缓冲成段，顺序写到空闲位置，从不原地覆盖；段大小由 D = F/(1−F) × Rpeak × Tposition 决定。
  • inode 位置不固定，用 imap（inode 号 → 地址）间接定位；imap 片段也写进日志；固定位置的 CR 记录 imap 片段地址。
  • imap 同时解决了递归更新问题：目录只存 inode 号。
  • 旧版本成为垃圾，需要按段清理：段摘要块记录 (inode 号, 偏移)，"最新 inode 还指着我"即存活；策略上先清冷段、后清热段。
  • 崩溃恢复：两个 CR 交替写 + 头尾时间戳保证 CR 原子更新；前滚找回检查点之后的段。
  • 承上启下：写时复制的思想延续到 WAFL、ZFS、btrfs；下一章的闪存 SSD 内部的 FTL 就是一个日志结构系统，同样要面对垃圾回收和写放大。
