1一句话 + 关键问题

如何确保数据完整性？存储系统怎样保证写进去的数据被保护好？需要哪些技术？怎样让这些技术足够高效——空间和时间开销都很低？

How should systems ensure that the data written to storage is protected? What techniques are required? How can such techniques be made efficient, with both low space and time overheads?

一句话：磁盘不只是"要么好、要么整块坏"，它还会悄悄地坏掉某一个块——读不出来（潜在扇区错误），或者读出来的内容是错的（块损坏）。本章的答案是：用校验和（checksum）发现静默损坏，再加上物理 ID、父块中的校验和、磁盘擦洗（scrubbing）去对付错位写入、丢失写入和"没人读的数据慢慢烂掉"这几种更刁钻的情况；发现问题之后，靠 RAID / 镜像等冗余把正确数据找回来。

本章承接第 38 章 RAID（当时只考虑"整盘失效"）和第 40–43 章的文件系统实现：前面几章关心的是快（FFS、LFS）和崩溃后一致（日志），这一章关心的是数据本身对不对。后面的分布式系统章节（第 48 章起）也会反复用到校验和：网络上传输的数据同样会损坏。

2核心概念速览

全盘失效（fail-stop）

磁盘要么完全正常、要么整块坏掉，而且坏了立刻能发现。早期 RAID 只考虑这种模型。

部分失效（fail-partial）

磁盘看起来还在工作，但个别块读不出（非静默）或内容是错的（静默）。

潜在扇区错误（LSE）

扇区物理损坏，磁盘内部 ECC 纠不回来，读时返回错误——容易发现，用冗余恢复即可。

块损坏（block corruption）

固件 bug、总线故障等让块内容变错，磁盘却报告"一切正常"——静默故障，需要校验和才能发现。

校验和（checksum）

对一个块（如 4 KB）算出的小摘要（如 4–8 字节），和数据一起存；读时重算并比较 Cs 与 Cc。

碰撞（collision）

把大数据压成小摘要，必然有不同数据得到相同校验和。好的校验和让碰撞尽量少、计算尽量快。

错位写入 / 丢失写入

写到了错误的位置 / 报告写成功却没落盘。前者靠物理 ID，后者靠写后读或把校验和存到父块（inode）里。

磁盘擦洗（scrubbing）

定期把所有块读一遍核对校验和，趁还有好副本时修复，避免所有副本都慢慢烂掉。

3磁盘故障模式：不只是"整盘坏"

第 38 章讲 RAID 时，我们采用的是全盘失效（fail-stop）模型：磁盘要么正常工作，要么彻底坏掉，而且"坏掉"很容易检测。这让 RAID 的设计相对简单。

但 Bairavasundaram 等人的研究发现，现代磁盘经常大体上还能工作，只是某一个或几个块出问题。常见的单块故障有两类：

  • 潜在扇区错误（latent sector error, LSE）：扇区（或一组扇区）物理损坏。比如磁头碰到盘面（磁头划伤，head crash）弄坏了表面；宇宙射线也可能翻转比特。磁盘内部用纠错码（ECC）判断块里的比特是否完好、有时还能修好；修不好时，读这个块会返回错误。
  • 块损坏（block corruption）：块的内容坏了，而磁盘自己察觉不到。例如有 bug 的磁盘固件把块写到了错误的位置——磁盘 ECC 认为内容没问题，但客户端读到的却是"别的块"；又如数据经过有故障的总线从主机传到磁盘时就已经坏了，磁盘把坏数据老老实实存下来。这类故障是静默故障（silent fault）：返回错误数据时磁盘不给任何提示，所以格外阴险。

Prabhakaran 等人把这种更现代的视角称为部分失效（fail-partial）模型：磁盘仍可能整块失效；也可能看似正常，却偶尔读写某块时报错（非静默部分故障），或者干脆返回错误内容（静默部分故障）。

它们有多常见？

原书 Figure 45.1 汇总了 Bairavasundaram 等人两项研究的结果：在大约 3 年里、超过 150 万块磁盘中，至少出现过一次 LSE 或块损坏的磁盘所占比例。"廉价"盘通常是 SATA，"昂贵"盘通常是 SCSI 或光纤通道（Fibre Channel）。

关于 LSE

· 已有不止一个 LSE 的昂贵盘，和廉价盘一样容易再出新错误
· 对多数磁盘，第二年的年错误率会上升

· 大多数出现 LSE 的盘，LSE 少于 50 个
· 出过 LSE 的盘更容易出更多 LSE
· 存在显著的空间与时间局部性

关于块损坏

· 同一档次内，不同型号的损坏概率差别很大
· 不同型号的老化效应不同
· 工作负载和磁盘容量对损坏影响很小
· 多数出现损坏的盘只有少数几处损坏

· 有空间局部性，也有一定时间局部性
· 与 LSE 有弱相关

结论很清楚：想构建可靠的存储系统，就必须有检测并恢复 LSE 和块损坏的机制。

4处理潜在扇区错误：检测容易，靠冗余恢复

如何处理潜在扇区错误？存储系统该怎样应对 LSE？需要多少额外机制？

How should a storage system handle latent sector errors? How much extra machinery is needed to handle this form of partial failure?

LSE 按定义就很容易检测：访问某块时磁盘直接返回错误。存储系统只需要动用已有的冗余机制拿到正确数据：镜像 RAID 就去读另一份副本；RAID-4/5 就用同一奇偶校验组里的其他块重建出这个块。

但 LSE 越来越常见，也影响了 RAID 设计。一个典型难题出现在 RAID-4/5 上：整盘失效和 LSE 同时发生。一块盘坏了，RAID 要把它重建到热备盘上，就得把奇偶校验组里其他所有盘从头到尾读一遍；如果重建途中在另一块盘上碰到 LSE，这一条带就同时缺了两个块，单个奇偶校验块救不回来——重建无法顺利完成。

为此有的系统增加一层冗余。例如 NetApp 的 RAID-DP 相当于有两块奇偶校验盘：重建时碰到 LSE，额外的校验信息可以把缺失块重建出来。代价照例存在：每个条带要维护两个校验块更贵（不过 NetApp 的 WAFL 文件系统是日志结构式的，很多时候能摊薄这部分开销），剩下的主要代价是空间——多占一块盘来放第二个校验块。

5检测损坏：校验和

在存在损坏的情况下如何保持数据完整性？既然这类故障是静默的，存储系统怎样才能发现损坏已经发生？需要哪些技术？如何高效实现？

Given the silent nature of such failures, what can a storage system do to detect when corruption arises? What techniques are needed? How can one implement them efficiently?

和 LSE 不同，损坏的难点在于检测。一旦知道某块坏了，恢复方法和前面一样：找另一份副本（但愿那份没坏）。所以这里集中讨论检测技术。

现代存储系统保护数据完整性的主要手段是校验和（checksum）：一个函数，输入一块数据（比如 4 KB），输出一个很小的摘要（比如 4 或 8 字节）。把校验和与数据一起存下来，以后访问时重新计算，对比当前数据的校验和与当初存下的值，就能发现数据是否被改动过。

There's No Such Thing As A Free Lunch——看似白得的东西，其实总要付出代价。老式餐馆打出"免费午餐"招揽客人，进去才发现要"免费"午餐得先买几杯酒。校验和也一样：保护越强，通常越贵。

常见的校验和函数

不同校验和函数在强度（保护数据完整性的能力）和速度（计算快慢）上各有取舍。

  • 异或（XOR）：把数据块切成若干等长的单元，全部异或起来。原书的例子：对 16 字节的块算 4 字节校验和，把数据排成每行 4 字节，对每一列求异或。数据 365e c4cd ba14 8a92 ecef 2c3a 40be f666 的结果是 0x201b9403。XOR 的弱点：如果两个比特在各自单元的同一位置同时翻转，校验和不变，检测不到。
  • 加法（addition）：对每个单元做二进制补码加法，忽略溢出。很快，能发现很多改动；但如果数据被移位/重排了就不行（加法和异或都满足交换律，顺序变了结果不变）。
  • Fletcher 校验和：设数据块 D 由字节 d1 … dn 组成，对所有 di 依次计算 s1 = (s1 + di) mod 255，s2 = (s2 + s1) mod 255。s2 是 s1 的累加，隐含了位置信息，所以重排也能发现。原书称它几乎和 CRC 一样强，能检测所有单比特、双比特错误和很多突发错误。
  • 循环冗余校验（CRC）：把数据块 D 看成一个很大的二进制数，除以一个约定好的值 k，余数就是 CRC。这种"二进制取模"可以实现得很高效，所以 CRC 在网络中也很流行。

无论哪种方法，都不存在完美的校验和：内容不同的两个块可能得到相同的校验和，这叫碰撞（collision）。这很直观：把 4 KB 压缩成 4 或 8 字节的摘要，必然有很多输入对应同一个输出。选校验和函数，就是在"碰撞尽量少"和"计算尽量快"之间找平衡。

制造损坏：读回的数据

CRC 的"除法"到底是什么

CRC 的除法是模 2 运算：没有进位和借位，减法就是异或。以上面模拟器用的 CRC-8 为例，除数 k = 1 0000 0111（多项式 x8+x2+x+1，简写 0x07）。实现时维护一个 8 位寄存器，每读入一个字节先异或进寄存器，再逐位处理：

uint8_t crc8(const uint8_t *p, size_t n) {
    uint8_t c = 0;
    for (size_t i = 0; i < n; i++) {
        c ^= p[i];                          // 把下一个字节"拉下来"
        for (int k = 0; k < 8; k++)
            c = (c & 0x80) ? (c << 1) ^ 0x07   // 最高位是 1：够"除"，减去除数（= 异或）
                           : (c << 1);         // 最高位是 0：商这一位为 0，只移位
    }
    return c;                               // 最后剩下的就是余数
}

这和小学的竖式长除法一模一样，只是"减法"变成了异或。每次最高位为 1 时异或上除数，等价于长除法里"够减就减"。实际系统常用 CRC-32（除数 33 位），并用查表法一次处理一个字节（见本章实验）。

校验和放在哪里：布局（layout）

最直接的做法是每个扇区（或块）配一个校验和：给定数据块 D，记其校验和为 C(D)。但校验和很小（如 8 字节），而磁盘只能以扇区（512 字节）为单位写入，怎么放？

磁盘厂商的一种办法是把盘格式化为 520 字节扇区，每扇区多出的 8 字节存校验和。没有这种功能的磁盘，文件系统就得自己把校验和打包进 512 字节的块里：一个校验和扇区存 n 个校验和，后面跟 n 个数据块，然后是下一组。这种方案在所有磁盘上都能用，但效率可能差一些：想覆盖 D1，就得先读入存有 C(D1) 的校验和扇区、更新 C(D1)，再写出校验和扇区和新的 D1——一次读、两次写；而每扇区自带校验和的方案只需一次写。

6使用校验和，以及两个新问题

读块 D 时，客户端（文件系统或存储控制器）同时从磁盘读出它的校验和，称为存储的校验和 Cs(D)；再对读到的块重新算一遍，称为计算的校验和 Cc(D)。相等说明数据很可能没被损坏，可以放心返回；不相等说明数据自存储以来被改动过——校验和帮我们发现了一次损坏。

发现损坏后怎么办？有冗余副本就简单：改用副本。没有副本，多半只能返回错误。要明白，检测损坏不是灵丹妙药：如果没有其他途径拿到未损坏的数据，你就是没辙了。

错位写入（misdirected write）

如何处理错位写入？存储系统或磁盘控制器该怎样发现错位写入？校验和需要额外包含什么？

How should a storage system or disk controller detect misdirected writes? What additional features are required from the checksum?

磁盘和 RAID 控制器有时会把数据正确地写到了错误的位置。单盘系统中，本该写到地址 x 的 Dx 被写到了地址 y（于是"损坏"了 Dy）；多盘系统中，控制器还可能把 Di,x 写到了另一块盘 j 上。

注意：错位写入后，块 y 上是一份完整、自洽的数据——它的内容和它的校验和完全匹配（校验和就是对这份数据算的）。所以单纯的校验和发现不了！答案也很简单：给校验和再加一点信息——物理 ID（physical ID），即块所在的磁盘号和扇区号。读磁盘 10 的块 4（D10,4）时，存储的信息里应该写着"disk=10、block=4"；对不上，就说明发生了错位写入。

从这个磁盘格式可以看到，盘上多了不少冗余信息：每个块都重复记着磁盘号，块的偏移也紧挨着块本身存了一份。这并不奇怪：冗余是错误检测（以及恢复）的关键。对完美的磁盘来说这点额外信息并非必需，但在出问题时能帮大忙。

最后一个问题：丢失写入（lost write）

如何处理丢失写入？存储系统或磁盘控制器该怎样发现丢失写入？校验和需要额外做些什么？

How should a storage system or disk controller detect lost writes? What additional features are required from the checksum?

有些设备会告诉上层"写完了"，实际上数据从未落盘，块上留着的还是旧内容。前面的办法有用吗？没用：旧块的校验和与旧数据完全匹配，物理 ID（磁盘号 + 块偏移）也完全正确。

可行的办法有好几种：

  • 写验证（write verify）/ 写后读（read-after-write）：写完立刻读回来，确认数据确实到达了盘面。缺点是很慢，完成一次写所需的 I/O 翻倍。
  • 在系统的别处再存一份校验和：例如 Sun 的 ZFS 在每个文件的 inode 和间接块里，为文件包含的每个块都存了校验和。即使对数据块的写丢失了，inode 里的校验和也对不上旧数据。只有 inode 和数据块的写同时丢失，这个方案才会失效——不太可能，但遗憾的是确实可能。

7磁盘擦洗与开销

擦洗（scrubbing）：校验和到底什么时候被检查？

应用访问数据时会顺带检查一部分，但大多数数据很少被访问，于是一直没人检查。对可靠的存储系统来说这很危险：比特腐烂（bit rot）最终可能波及同一份数据的所有副本。

补救办法是磁盘擦洗（disk scrubbing）：定期读遍系统中的每一个块，核对校验和是否仍然有效，趁还有好副本时修复坏副本，从而降低某份数据所有副本都坏掉的概率。典型系统每晚或每周扫描一次。（前面的研究也提到：大多数 LSE 就是这样被发现的。）

校验和的开销

和计算机系统中常见的情况一样，开销分空间和时间两种。

  • 空间·磁盘上：每个校验和都占掉本可存用户数据的空间。典型比例是每 4 KB 数据块配 8 字节校验和，磁盘空间开销约 0.19%（8 / 4096 ≈ 0.195%）。
  • 空间·内存中：访问数据时内存里要同时放校验和。如果校验完就丢掉，这个开销很短暂，不必担心；只有为了防范内存损坏而把校验和一直留在内存里时，才看得到这点小开销。
  • 时间·CPU：空间开销很小，时间开销却可能相当明显。CPU 至少要在存储时（算出要存的校验和）和访问时（重算并比较）各算一遍。许多系统（包括网络协议栈）的优化办法是把复制和校验合二为一：数据反正要从内核页缓存复制到用户缓冲区，边复制边算校验和非常划算。
  • 时间·额外 I/O：校验和与数据分开存放时需要额外 I/O（可通过设计减少）；后台擦洗也要额外 I/O（可以调节，比如放在大多数人——并非所有人！——都已上床睡觉的深夜进行）。

9先预测，再验证

在"逐位计算校验和"模拟器里载入原书示例，选 XOR。第 1 组 4 列（每行最左边的 4 位）是 0011 / 1011 / 1110 / 0100。先心算这 4 列各有几个 1、结果的第一个十六进制数字是多少，再单步验证。
看答案

4 列的 1 的个数依次是 2、2、3、1（第 1 列 0,1,1,0；第 2 列 0,0,1,1；第 3 列 1,1,1,0；第 4 列 1,1,0,0）。偶数得 0、奇数得 1 → 0010 = 0x2，正是 0x201b9403 的首位。XOR 本质上就是每一列的奇偶校验。

仍用原书示例，把 k 设为 4，点"同列翻转两位"（第 1 行和第 2 行的第 4 列同时翻转）。预测：XOR、加法、Fletcher、CRC-8、CRC-32 中哪些能发现？再把 k 改成 6 做一次，最后点"交换第 1、2 行"预测一次。
看答案

同列翻转：XOR 两次都发现不了——这一列翻了两次，奇偶不变，这正是原书说的 XOR 局限。加法要看方向：k = 4 时，第 1 行这一位是 0（0→1，+227），第 2 行这一位是 1（1→0，−227），正好抵消，加法也漏检；k = 6 时两行这一位都是 1，同向减少 2×225，加法能发现（本章实验测得随机情况下约一半能发现）。Fletcher 与 CRC 两次都能发现。

交换两行：XOR 和加法都满足交换律，结果不变，全部漏检；Fletcher 的 s2 与位置有关，CRC 更是逐位"除"下去，都能发现。

（改编自原书 Homework 第 7 题）把单元改成"1 字节"，分别载入 1,2,3,4 和 4,3,2,1。先预测两组数据的加法、XOR、Fletcher 校验和，然后验证：它们有什么共同点？Fletcher 好在哪里？
看答案

加法都是 10（0x0a），XOR 都是 1⊕2⊕3⊕4 = 4。Fletcher：1,2,3,4 时 s1 = 1,3,6,10，s2 = 1,4,10,20 → (s2, s1) = (20, 10)；4,3,2,1 时 s1 = 4,7,9,10，s2 = 4,11,20,30 → (30, 10)。s1 一样（它就是模 255 的加法），但 s2 是"前缀和的和"，字节越靠前贡献越大，所以顺序不同 s2 就不同。这就是 Fletcher 比简单加法强的地方。

（改编自 Homework 第 3、4 题）1 字节单元下，找一个不全为 0 的 4 字节数据，使加法和 XOR 校验和相同。一般在什么时候二者相同？什么时候不同？
看答案

例如 01 02 04 08：加法 = 15 = XOR。异或就是"不带进位的加法"，所以只要加的过程中从不产生进位（任意两个字节没有同时为 1 的比特位）且总和不溢出，二者就相等。只要某一位上有两个 1 相加产生进位（例如 01 01 00 00：加法 = 2，XOR = 0），二者就会不同。

在镜像模拟器里点"错位写入"（默认不开物理 ID、不开 inode 校验和）。先预测第 2 条操作 r 3 和第 3 条 r 1 会返回什么、"静默返回错误数据"会变成几；然后依次勾上"物理 ID"、再勾上"inode 校验和"，各预测一次。
看答案

都不开：r 3 读到磁盘 0 块 3 上的 CAFEF00D，校验和自洽 → 静默返回错误数据；r 1 读到磁盘 0 块 1 的旧值，同样自洽 → 又一次静默错误（计数 2）。擦洗时两份副本的块 1、块 3 内容不同，但各自校验和都通过，擦洗无法判断谁对。

开物理 ID：块 3 上记录的是 block=1 ≠ 3 → 发现，改读磁盘 1 并修复；但块 1 仍是旧数据且 ID 正确——对块 1 而言这其实是一次丢失写入，仍静默出错（计数 1）。

再开 inode 校验和：inode 里记着块 1 应为 C(CAFEF00D)，旧数据对不上 → 发现并修复，计数 0。

点"擦洗"预设：磁盘 1 的块 0 翻转、磁盘 1 的块 5 出现 LSE、磁盘 0 的块 3 翻转。如果不擦洗、只做 r 0 和 r 5，这些问题会被发现吗？为什么擦洗这一步能全部修好？
看答案

读操作先读磁盘 0，磁盘 0 的块 0、块 5 都是好的，直接返回——磁盘 1 上的两个问题永远不会被读路径发现，块 3 的问题也要等到有人读块 3 才会暴露。它们就这样潜伏着，直到另一份副本也坏掉。擦洗逐块检查两份副本，此时每个块都至少还有一份好的，于是三个问题全部被修复。这就是原书说"大多数 LSE 是靠擦洗发现的"的原因。

10动手实验：实现并比较四种校验和

改编自原书 Homework (Code) 第 1–4 题：labs/45-data-integrity/csum.c 实现了 XOR、加法、Fletcher（朴素版和推迟取模版）、CRC32（逐位版和查表版），程序分三段：① 自检（原书示例 XOR 必须是 0x201b9403，CRC32("123456789") 必须是 0xCBF43926）；② 64 MB 数据测速；③ 对 4 KB 随机块施加 10 万次各类损坏，统计检测率。

cd labs/45-data-integrity && make && ./csum

核心代码（Fletcher 与 CRC32 查表）：

// Fletcher（原书定义）：每个字节都取模
for (size_t i = 0; i < n; i++) { s1 = (s1 + p[i]) % 255; s2 = (s2 + s1) % 255; }

// 推迟取模：64 位累加器足够大，每 4096 字节才取一次模，结果完全相同
for (size_t i = 0; i < k; i++) { s1 += p[i]; s2 += s1; }
s1 %= 255; s2 %= 255;

// CRC32 查表：T[] 预先存好"一个字节经过 8 次移位/异或"的结果
for (size_t i = 0; i < n; i++) c = T[(c ^ p[i]) & 0xFF] ^ (c >> 8);

示例输出（本机 WSL2 + gcc 14 实际运行；测速数字取决于 CPU 和负载，你的机器上会不同，检测率由固定种子生成，应基本一致）：

怎么读这组数字：

  • 没有免费的午餐：XOR 最快，CRC32 查表版慢了一个多数量级，逐位版更慢；但 CRC32 在所有测试里都是 100%。Fletcher 把取模推迟后快了约 5 倍，强度几乎不变——"算法相同、实现不同"对开销影响巨大。
  • XOR 的死穴：同一列的两个比特翻转 0% 检出，交换两个字也 0%；但奇数个比特翻转它一定能发现（至少有一列的奇偶变了）。
  • 加法对同列翻转约有一半能发现：两位翻转方向相反（一个 0→1、一个 1→0）时正好抵消。
  • Fletcher 偶尔漏掉双比特错误：原书说 Fletcher 能检测所有双比特错误——对这种按字节模 255 的版本，这在数据不超过 255 字节时成立。4 KB 块里，若两个相距 255 字节整数倍的字节在同一比特位上一个 0→1、一个 1→0，s1 和 s2 的变化恰好都是 255 的倍数，就漏了。实际系统会用更宽的 Fletcher（如 Fletcher-32/64）或 CRC 来避免。

11自测题

潜在扇区错误（LSE）和块损坏最本质的区别是？
LSE 时磁盘 ECC 修不回来会主动报错，所以很容易检测，靠冗余恢复即可；块损坏（固件写错位置、总线损坏）磁盘毫无察觉，是静默故障，需要校验和才能发现。两类故障在两档磁盘上都会出现，只是昂贵盘少一个数量级。
按原书 Figure 45.1，约 3 年内至少出现一次 LSE 的廉价盘比例约为？
廉价盘 LSE 9.40%、昂贵盘 1.40%；块损坏分别为 0.50% 和 0.05%。更好的盘大约降低一个数量级，但仍不可忽略。
以 4 字节为单元的 XOR 校验和，下列哪种损坏一定检测不到？
XOR 就是每一列的奇偶。同一列翻两次，奇偶不变 → 漏检（原书指出的局限）。A、D 是奇数个翻转，必然至少有一列奇偶改变；C 中两个比特在不同列，两列都会变。
在校验和旁边加入物理 ID（磁盘号 + 扇区号），主要是为了发现哪种问题？
错位写入后，目标位置上的数据和它的校验和是自洽的，但记录的"应在何处"对不上当前位置。丢失写入时旧块的校验和与物理 ID 都正确，物理 ID 帮不上忙；LSE 本身就会报错。
关于丢失写入（lost write），下列说法正确的是？
丢失写入后盘上是旧数据 + 旧校验和 + 正确的物理 ID，一切自洽。ZFS 在父块中存子块的校验和，就能对不上；写后读也能发现，但它使写的 I/O 次数翻倍，很慢。
采用"一个校验和扇区 + n 个数据块"的打包布局时，覆盖写数据块 D1 需要？
先读入包含 C(D1) 的校验和扇区，更新其中的 C(D1)，再写出校验和扇区和新 D1。520 字节扇区的方案只需 1 次写。
每 4 KB 数据块配 8 字节校验和，磁盘空间开销约为？
8 / 4096 ≈ 0.195%，原书写作 0.19%。空间开销很小；真正明显的是 CPU 时间开销（以及校验和分开存放、后台擦洗带来的额外 I/O）。
为什么需要磁盘擦洗（scrubbing）？
读路径也会检查，但只覆盖被访问的数据。擦洗定期读遍所有块，通常每晚或每周一次，最好安排在深夜。
关于校验和碰撞，下列说法正确的是？
原书："there is no perfect checksum"。输出空间远小于输入空间，必然存在不同数据同一校验和的情况。
RAID-5 一块盘整盘失效后重建时，另一块盘出现 LSE，会发生什么？
单奇偶校验只能容忍一处缺失。NetApp 的 RAID-DP 相当于两块校验盘，代价是维护两份校验和多一块盘的空间。

12常见误区与本章小结

  • "校验和能纠错"：不能。校验和只负责发现问题，恢复靠冗余（镜像、奇偶校验）。没有好副本就只能返回错误。
  • "磁盘有 ECC，文件系统就不用校验和了"：ECC 管得了盘面比特错误，却管不了固件把块写错位置、总线上传坏的数据——这些在磁盘看来都是"正确"的数据。
  • "加了物理 ID 就万无一失"：物理 ID 只对付错位写入；丢失写入时旧块处处自洽，需要写后读或父块中的校验和。
  • "XOR / 加法就够用了"：它们满足交换律，对重排完全无感；XOR 对同列的偶数次翻转也无感。
  • "买昂贵的盘就不会出问题"：只是少一个数量级（LSE 9.40% → 1.40%，损坏 0.50% → 0.05%），150 万块盘的规模下依然常见。
  • "读的时候会检查，所以不需要擦洗"：大多数数据很少被读，问题会一直潜伏到所有副本都坏掉。

本章要点

  • 现代磁盘是部分失效的：除了整盘失效，还有 LSE（非静默）和块损坏（静默）。
  • LSE 容易检测，直接用 RAID/镜像冗余恢复；但它会让 RAID-5 重建失败，于是有了 RAID-DP 这类双校验方案。
  • 静默损坏靠校验和检测：存储 Cs，读时重算 Cc 并比较。XOR、加法快但弱；Fletcher 带位置信息；CRC 最强也最贵。没有完美的校验和。
  • 布局：520 字节扇区（1 次写）或打包的校验和扇区（覆盖写要 1 读 2 写）。
  • 错位写入 → 在校验和旁加物理 ID；丢失写入 → 写后读或把校验和存到 inode/间接块里（ZFS）。
  • 擦洗定期检查所有块，防止比特腐烂波及所有副本。
  • 开销：空间很小（8 B / 4 KB ≈ 0.19%），CPU 时间明显，可用"复制与校验合一"来降低；额外 I/O 可以通过设计和调度来控制。

与后续章节的联系：下一部分进入分布式系统（第 48 章）。网络和磁盘一样会丢包、损坏数据包，校验和几乎原样出现在网络协议里，而"端到端"地检查完整性也会是分布式系统的核心思想。回头看，第 42 章的日志提交块里也可以放校验和（ext4 的做法），第 43 章 LFS 那样的写时复制设计（如 WAFL、ZFS）正是"父块存子块校验和"最自然的载体。
