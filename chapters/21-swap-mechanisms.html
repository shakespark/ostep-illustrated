这一章要解决什么

如何超越物理内存？操作系统如何利用一个更大、更慢的设备，透明地提供"巨大虚拟地址空间"的假象？

How can the OS make use of a larger, slower device to transparently provide the illusion of a large virtual address space?

到目前为止（第 13～20 章）我们一直假设：每个进程的地址空间都很小，并且所有进程的所有页都能放进物理内存。这显然不现实。本章放宽这个假设：要支持许多同时运行的大地址空间，就需要在存储层次中再加一层——容量更大但更慢的磁盘（或 SSD），把暂时不用的页"藏"到那里。

为什么要给进程一个大地址空间？因为方便：程序员只管自然地分配内存，不必操心内存够不够。对比早年的内存覆盖（memory overlays）：程序员要在调用函数或访问数据之前，手动把相应的代码或数据搬进内存——想想就头疼。再加上多道程序（multiprogramming）需要同时容纳许多进程，"用比物理内存更多的内存"成了所有现代 VM 系统的标配。本章讲机制（present 位、页错误、交换空间），下一章（第 22 章）讲策略（踢出哪个页）。

核心概念速览

交换空间（swap space）

磁盘上预留的区域，以页为单位把页换出（swap out）到这里、再换入（swap in）回来。

present 位（present bit）

PTE 中的一位：1 = 页在物理内存；0 = 页在磁盘上某处。

页错误（page fault）

访问一个合法但不在内存中的页。硬件抛出异常，交给 OS 处理（其实更该叫 page miss）。

页错误处理程序

OS 代码：找空闲页框（没有就先淘汰一页），从磁盘读入页，更新 PTE，重试指令。

替换策略（page-replacement policy）

内存满时决定踢出哪一页。选错了程序会慢 1 万～10 万倍，下一章详谈。

高/低水位线（HW/LW）

空闲页少于 LW 时唤醒后台线程，一直换出到空闲页达到 HW 再睡。

交换守护进程（swap daemon）

也叫 page daemon，在后台成批换出页，还能把写操作聚集（cluster）起来提高磁盘效率。

透明（transparency）

这一切对进程完全不可见：它只看到自己私有、连续的虚拟内存。

交换空间：内存之下的一层

首先在磁盘上预留一块空间，用来来回移动页，这就是交换空间（swap space）。我们假设 OS 能以页为单位读写交换空间，为此 OS 需要记住每个被换出的页在磁盘上的地址。交换空间的大小很重要：它最终决定了系统某一时刻最多能使用多少个内存页。这里先假设它非常大。

原书 Figure 21.1 是一个很小的例子：4 个页框的物理内存，8 个块的交换空间。三个进程（Proc 0、1、2）共享物理内存，但每个进程都只有一部分有效页在内存里，其余在磁盘上；Proc 3 的页全部被换出，所以它显然没有在运行。交换空间还剩 1 个空闲块。

还要注意：交换空间并不是换页流量唯一的磁盘位置。比如程序二进制（ls 或你编译的程序）的代码页一开始就在磁盘的可执行文件里，运行时才被载入内存（一次全部载入，或像现代系统那样用到一页载入一页）。如果系统需要腾出内存，可以放心地直接丢弃这些代码页（不用写到交换空间），因为以后还能从文件系统里的二进制文件重新读回来。

这个"更大更慢的设备"不一定是机械硬盘，也可以是更现代的基于闪存的 SSD（第 44 章）。现在只需假设有一个大而相对慢的设备，用来帮我们构造"比物理内存更大的虚拟内存"这一假象。

present 位：页在内存里吗？

先回顾一次内存访问（假设 硬件管理的 TLB）：硬件从虚拟地址中取出 VPN，查 TLB；命中就直接得到物理地址去访存（常见情况，快）。TLB 未命中时，硬件用页表基址寄存器（PTBR）找到内存中的页表，以 VPN 为索引取出 PTE；如果页有效且在物理内存中，就取出 PFN 装入 TLB，然后重试指令，这次 TLB 命中。

允许页被换到磁盘后，硬件查 PTE 时可能发现页不在物理内存中。判断依据是 PTE 中新增的一位：present 位（present bit）。

"页错误（page fault）"这个词有点奇怪：访问一个映射在地址空间里、只是暂时不在内存中的页，是完全合法的，本该叫 page miss。之所以叫"fault"，大概是因为处理机制相同：硬件遇到自己处理不了的情况，就抛出异常把控制权交给 OS——这和进程做了非法操作时一模一样。更广义地，"page fault"有时也指非法内存访问。人们说程序"在大量 page fault"，通常指它在访问被 OS 换到磁盘上的部分。

页错误：谁来处理、怎么处理

无论 TLB 由硬件还是软件管理，页不在内存时都由 OS 接管：运行页错误处理程序（page-fault handler）。几乎所有系统都用软件处理页错误，即使 TLB 由硬件管理。

硬件设计者一向不太信任 OS，为什么这件事却交给 OS？两点原因：一是性能——访问磁盘本来就极慢，OS 多执行一些指令的开销相比之下微不足道；二是简单——硬件要处理页错误，就得懂交换空间、懂如何向磁盘发 I/O 等一大堆它本不关心的细节。

OS 如何知道页在磁盘哪里？页表是存放这个信息的天然位置：PTE 中原本存 PFN 的那些位可以改存磁盘地址。处理流程：

  1. OS 从 PTE 中找到磁盘地址，向磁盘发请求，把页读进内存；
  2. 磁盘 I/O 期间，进程处于阻塞（blocked）状态，OS 可以运行其他就绪进程——I/O 与计算重叠，这是多道程序充分利用硬件的又一方式；
  3. I/O 完成后，OS 更新页表：present 置 1，PFN 字段记录新页框号；
  4. 重试指令。这次可能 TLB 未命中，查页表后装入 TLB（也可以在处理页错误时顺便更新 TLB，省掉这一步）；最后一次重试 TLB 命中，取到数据。

内存满了怎么办？

上面的流程假设有空闲内存可以放换入的页。可内存可能已经满了（或接近满）。这时 OS 需要先换出（page out）一个或多个页腾出空间。挑选踢出哪个页的过程叫页替换策略（page-replacement policy）。踢错了页代价巨大：程序可能以磁盘速度而不是内存速度运行，按当前技术这意味着慢 1 万到 10 万倍。策略是下一章的主题；现在只需知道它建立在本章的机制之上。

完整控制流：一次内存访问的所有可能

现在可以回答"程序从内存取一个数据时到底发生了什么"。原书用两段伪代码描述：Figure 21.2 是硬件在地址转换时做的事，Figure 21.3 是 OS 处理页错误时做的事。

Figure 21.2 硬件控制流

1  VPN = (VirtualAddress & VPN_MASK) >> SHIFT
2  (Success, TlbEntry) = TLB_Lookup(VPN)
3  if (Success == True)   // TLB Hit
4      if (CanAccess(TlbEntry.ProtectBits) == True)
5          Offset   = VirtualAddress & OFFSET_MASK
6          PhysAddr = (TlbEntry.PFN << SHIFT) | Offset
7          Register = AccessMemory(PhysAddr)
8      else
9          RaiseException(PROTECTION_FAULT)
10 else                   // TLB Miss
11     PTEAddr = PTBR + (VPN * sizeof(PTE))
12     PTE = AccessMemory(PTEAddr)
13     if (PTE.Valid == False)
14         RaiseException(SEGMENTATION_FAULT)
15     else
16         if (CanAccess(PTE.ProtectBits) == False)
17             RaiseException(PROTECTION_FAULT)
18         else if (PTE.Present == True)
19             // assuming hardware-managed TLB
20             TLB_Insert(VPN, PTE.PFN, PTE.ProtectBits)
21             RetryInstruction()
22         else if (PTE.Present == False)
23             RaiseException(PAGE_FAULT)

Figure 21.3 软件（OS）控制流

1 PFN = FindFreePhysicalPage()
2 if (PFN == -1)              // no free page found
3     PFN = EvictPage()       // replacement algorithm
4 DiskRead(PTE.DiskAddr, PFN) // sleep (wait for I/O)
5 PTE.present = True          // update page table:
6 PTE.PFN     = PFN           // (present/translation)
7 RetryInstruction()          // retry instruction

TLB 未命中时有三种情况：

  • 有效且 present（第 18–21 行）：从 PTE 取 PFN 装入 TLB，重试，TLB 命中。
  • 有效但不 present（第 22–23 行）：合法访问，但页不在内存 → 页错误，运行页错误处理程序。
  • 无效（第 13–14 行）：比如程序 bug 访问了未分配的页。其他位都不重要了，硬件陷入 OS，进程多半被终止。

软件部分：OS 先为即将换入的页找一个物理页框；没有就等替换算法踢出一些页。拿到页框后发 I/O 读入页；这个慢操作完成后更新页表并重试指令——重试先导致一次 TLB 未命中，再重试才 TLB 命中。下面的模拟器把这两段控制流合在一起，一步一步走给你看。

替换何时真正发生：高低水位线与交换守护进程


前面的描述假设 OS 等到内存完全满了才替换（淘汰）一页，这不太现实。OS 有很多理由主动保持一小部分内存空闲。为此，大多数操作系统设置高水位线（high watermark，HW）和低水位线（low watermark，LW）：


    
  
  • 当 OS 发现可用页少于 LW 时，一个负责释放内存的后台线程开始运行；
    • 
  
  • 它不断淘汰页，直到可用页达到 HW，然后心满意足地去睡觉。
    • 



这个后台线程叫交换守护进程（swap daemon）或页守护进程（page daemon）。（"daemon"读作"demon"，是后台进程的老称呼，源自 Multics 项目组借用的物理学"麦克斯韦妖"。）一次替换多个页还带来新的优化：许多系统会把一批页聚集（cluster）起来一次写入交换分区，减少磁盘寻道和旋转开销，显著提高效率。


配合后台线程，Figure 21.3 的控制流要稍作修改：处理程序不再直接替换页，而是检查有没有空闲页；没有就通知后台分页线程"需要空闲页"，等它释放出一些页后再唤醒原线程，继续换入所需的页。

把工作放到后台做。OS 经常在后台做事：例如先把文件写缓存在内存里，稍后再写到磁盘。好处包括：磁盘可以一次收到很多写请求、更好地调度（效率）；应用觉得写操作很快就完成了（延迟）；有些写可能根本不用做，比如文件很快被删除（减少工作）；后台工作可以利用系统空闲时间（更好地利用硬件）。

把物理页框改成 6，再跑同样的序列。哪些步骤消失了？总耗时如何变化？


看答案
FindFreePhysicalPage() 直接找到空闲页框，不再执行 EvictPage()，也就不需要把牺牲页写回磁盘。每次页错误少一次磁盘写（约 10 ms），这正是交换守护进程要"预先保持一些空闲页"的动机：把淘汰和写回移出页错误的关键路径。



序列最后访问 VPN 3。PTE 的 present 位此时是什么值重要吗？


看答案
不重要。VPN 3 的 valid 位为 0，硬件在第 13–14 行就抛出 SEGMENTATION_FAULT，根本不会看 present 位（原书："no other bits in the PTE really matter"）。OS 通常会终止该进程。



在守护进程模拟器里把聚集大小从 1 改为 8，预测"磁盘写次数"怎样变化？LW 和 HW 靠得很近（比如 LW=4、HW=5）会怎样？


看答案
被换出的页数不变，但写操作被打包成更少、更大的 I/O，磁盘写次数大约变为原来的 1/8（每次唤醒至少一次写）。LW 与 HW 太近时，守护进程每次只腾出一两页，于是频繁醒来、每次写得很少，无法有效聚集；两者拉开，每次唤醒成批工作，但会有更多内存闲置。这是一个权衡。



（改编自 Homework 2、5）运行下面实验中的 ./mem 1024。第 0 轮和之后几轮的速度为什么差了约 10 倍？如果分配量超过物理内存又会怎样？


看答案
第 0 轮每页首次被触碰都会产生一次 minor page fault（OS 找一个页框、清零、建立映射），1024 MB 就是 26 万多次页错误；之后页都已 present，只剩纯内存访问。如果分配量超过物理内存，第 1 轮起页会被换出又换入，vmstat 的 si/so 列变为非零，带宽跌到磁盘/SSD 的水平。

解读：mmap 之后一页都没有（按需分配）；写入触发页错误后页变为 present；换出后 PTE 的 present 位清零、改记交换位置（S）；再读时每页一次页错误把页换回，数据完好。为什么记成 minor 而不是 major？因为刚换出的页还留在内核的交换缓存（swap cache）里，处理程序不必真的读磁盘；只有需要实际磁盘 I/O 的才算 major fault。

自测题




PTE 中 present 位为 0、valid 位为 1，访问该页会发生什么？




有效但不在内存：合法访问，硬件抛出 PAGE_FAULT，OS 的页错误处理程序负责换入。硬件不懂磁盘，不会自己去读（D 错）。



为什么即使 TLB 由硬件管理，页错误也由 OS（软件）处理？




原书给出的两点：性能（磁盘太慢，软件额外开销微不足道）和简单性（硬件不必懂交换空间、磁盘 I/O）。



OS 在处理页错误时如何知道页在磁盘上的位置？




许多系统就把磁盘地址存在 PTE 里：present=0 时 PFN 字段没用，正好复用。



页错误处理期间（磁盘 I/O 进行中），发生页错误的进程处于什么状态？




I/O 期间进程被阻塞，CPU 转去运行别的进程；I/O 完成后它才回到就绪态。这种重叠是多道程序提高利用率的方式之一。



一次需要从磁盘换入的页错误，从第一次 TLB 查找到最终取到数据，一共要做几次 TLB 查找（假设处理页错误时不顺便更新 TLB）？




第一次未命中 → 页错误；OS 处理后重试 → 第二次未命中，查页表装入 TLB；再重试 → 第三次命中。在模拟器里数一数就能验证。



关于高低水位线，哪项描述正确？




LW 触发，HW 停止。两者之间的间隔让守护进程可以一次成批工作，并把写操作聚集起来。



程序二进制中的代码页被踢出内存时，通常：




交换空间不是换页流量唯一的磁盘位置：代码页在磁盘的二进制文件里本来就有一份，可以放心复用它们占用的内存。



"page fault"这个名字为什么有点名不副实？




这是合法访问，只是页暂时在磁盘上。叫"fault"是因为处理机制和非法访问相同：硬件抛异常，把控制权交给 OS。



常见误区与小结



  
    
    
  • "页错误就是程序出错"——绝大多数页错误是正常的：按需分配、换入页，程序完全感觉不到。非法访问导致的是段错误/保护错误。
    • 
    
  • "present=0 就是无效页"——valid 和 present 是两回事：valid=0 表示地址空间里根本没有这一页；present=0 表示页有效但在磁盘上。
    • 
    
  • "页错误处理完就直接返回数据"——处理程序只是更新页表，然后重试引起错误的那条指令，硬件重新走一遍地址转换。
    • 
    
  • "OS 等内存满了才开始换出"——现实系统用 LW/HW 和后台守护进程主动保持空闲页，并聚集写操作。
    • 
    
  • "页错误期间 CPU 在等"——阻塞的是发生页错误的进程，CPU 会去运行其他进程。
    • 
  





  
    
    
  • 为了访问比物理内存更多的内存，页表需要 present 位：页不在内存时，PTE 里可以存它在交换空间中的磁盘地址。
    • 
    
  • 访问不 present 的页触发页错误；OS 的页错误处理程序找空闲页框（必要时先按替换策略淘汰一页），发起磁盘读、让进程阻塞，I/O 完成后更新 PTE，再重试指令。
    • 
    
  • TLB 未命中时有三种情况：present（装入 TLB 重试）、有效但不 present（页错误）、无效（段错误）。
    • 
    
  • 现实中 OS 通过 LW/HW 与交换守护进程在后台成批换出，并用聚集提高磁盘效率。
    • 
    
  • 这一切对进程透明：它看到的仍是私有、连续的虚拟内存；只是最坏情况下一条指令可能要花好几毫秒。
