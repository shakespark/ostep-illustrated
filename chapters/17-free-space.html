1一句话 + 关键问题

如何管理空闲空间？当要满足的请求大小各不相同时，空闲空间应该怎样管理？有哪些策略能把碎片降到最少？不同做法的时间和空间开销分别是多少？

原文：How should free space be managed, when satisfying variable-sized requests? What strategies can be used to minimize fragmentation? What are the time and space overheads of alternate approaches?

这一章是虚拟内存部分的一段"插曲"：暂时不谈地址转换，转而讨论所有内存管理系统都绕不开的问题：空闲空间怎么记、怎么分。无论是用户态的 malloc 库（管理进程堆里的空间），还是 OS 本身（用分段实现虚拟内存时管理物理内存），面对的都是同一个问题。

如果空间被切成固定大小的单元（下一章的分页就是这样），管理很简单：维护一张单元列表，有请求就给第一个。难的是变长请求，这时会出现外部碎片（external fragmentation）：空闲空间被切成大小不一的小块，总量明明够，却找不到一块连续的空间满足请求。

上一章的分段正是这种变长分配的典型场景；下一章的分页则用"只发固定大小的块"彻底绕开它。本章介于两者之间：看清楚变长分配到底难在哪里，以及几十年来人们想出的各种应对办法。

2核心概念速览

空闲链表（free list）

记录堆中所有空闲块的数据结构。不一定真是链表，但通常是。

外部碎片 vs. 内部碎片

外部碎片：空闲空间碎在块与块之间；内部碎片：发出去的块比请求大，浪费在块内部。

分割（splitting）

请求比空闲块小：把空闲块切成两半，前一半交出去，剩下的留在链表里。

合并（coalescing）

释放时检查地址上相邻的空闲块，把它们并成一个更大的块，防止堆"碎成渣"。

头块（header）

放在每个已分配块前面的小结构，至少记录大小（常加魔数）。free(ptr) 就靠它知道要释放多少。

嵌入式空闲链表

分配器不能 malloc 链表节点，于是把节点（size + next）直接写在空闲块自己的开头。

适配策略

最优（best）、最差（worst）、首次（first）、下次（next）适配：在"碎片多少"和"搜索多快"之间权衡。

分离链表 / slab / 伙伴

为常见大小单开链表；slab 缓存预初始化的内核对象；伙伴系统只发 2 的幂大小，合并极其简单。

3图解：底层机制

3.1 基本假设

  • 接口：void *malloc(size_t size) 返回一块至少 size 字节的空间；void free(void *ptr) 只接收指针，不告诉库大小。所以库必须能仅凭指针查出块有多大（见 3.3）。
  • 被管理的空间历史上叫堆（heap），管理它的通用数据结构叫空闲链表（free list）。
  • 主要关心外部碎片。如果分配器发出的块比请求大，块内多出来的部分是内部碎片（internal fragmentation），本章大多略过。
  • 不能搬家：一块内存交给程序后，直到被 free 之前都归程序所有，库不能挪动它。因此用户态分配器无法紧凑（compaction）。（C 程序的指针可能藏在任何变量甚至寄存器里，库无从修改；OS 实现分段时倒是可以紧凑。）
  • 分配器管理一段连续的字节区域。实际的库可以用 sbrk 让它变大（3.5 节），但讨论时先假设大小固定。

3.2 分割与合并

还是那个 30 字节的堆。它的空闲链表有两个元素：一个描述 0–9 字节，另一个描述 20–29 字节。

请求大于 10 字节会失败（返回 NULL）；正好 10 字节，任一块都行。比 10 小呢？比如只要 1 字节，分配器会做分割（splitting）：找一块能满足请求的空闲块，一分为二，前一块还给调用者，后一块留在链表里。如果选中第二个元素，malloc 返回 20，链表变成下图第二行：几乎没变，只是第二块从 21 开始、长度变成 9。

与之配套的是合并（coalescing）。回到"空闲 10 / 已用 10 / 空闲 10"的堆，如果程序调用 free(10) 归还中间那块，而库只是不假思索地把它插到链表头部，链表会变成 10 → 0 → 20 三个元素。整个堆明明全空了，看起来却是三块各 10 字节，20 字节的请求照样失败。

合并的思路很简单：归还一块时，仔细看它的地址和附近空闲块的地址，如果新释放的块紧挨着一个（或像这里一样两个）空闲块，就把它们并成一个更大的块。合并之后链表只剩一个元素 [0, 30]，正是最初什么都没分配时的样子。有了合并，分配器才能尽量保证应用能拿到大的连续空闲区域。

3.3 记录已分配块的大小：头块

free(void *ptr) 不带大小参数，库怎么知道要回收多少？大多数分配器在交出去的内存块前面放一个头块（header），里面至少有块的大小，还可能有加速释放用的指针、做完整性检查的魔数（magic number）等。原书的简单头块：

typedef struct {
    int size;    // 用户区的大小（不含头块）
    int magic;   // 魔数，用来检查 free 收到的指针是否合法
} header_t;
void free(void *ptr) {
    header_t *hptr = (header_t *) ptr - 1;   // 指针运算：往回退 sizeof(header_t) 字节
    assert(hptr->magic == 1234567);          // 完整性检查
    // 这块空闲区域的总大小 = hptr->size + sizeof(header_t)
    ...
}
  • (header_t *) ptr - 1：把 ptr 当作 header_t * 减 1，按 C 的指针运算规则正好后退 8 字节，落到头块起点。
  • magic 对不上，说明传进来的不是 malloc 发出的指针（或者头块被越界写坏了）。
  • 关键细节：释放区域的大小 = 头块大小 + 用户区大小。反过来，用户请求 N 字节时，库要找的不是 N 字节的空闲块，而是 N + 头块大小。

3.4 把空闲链表嵌进空闲空间里

普通链表要新节点时会调用 malloc()，可我们就是 malloc，没法这么做。办法是：直接在空闲空间里构建链表。每个空闲块的开头放一个节点：

typedef struct __node_t {
    int              size;   // 这个空闲块中可用的字节数（不含节点本身）
    struct __node_t *next;   // 下一个空闲块
} node_t;

// mmap() 返回一块空闲空间的指针；假设这块 4KB 的堆从虚拟地址 16KB 开始
node_t *head = mmap(NULL, 4096, PROT_READ|PROT_WRITE, MAP_ANON|MAP_PRIVATE, -1, 0);
head->size = 4096 - sizeof(node_t);   // 4088
head->next = NULL;

运行后链表只有一个元素，大小 4088（4096 减去 8 字节的节点）。接下来依次：

  1. malloc(100)：唯一的空闲块被选中并分割。连头块共 108 字节交出去，返回的 ptr = 16384 + 8 = 16392；剩下的空闲块缩小为 4088 − 108 = 3980，节点挪到 16492。
  2. 再分配两次 100 字节：前 324 字节（3 × 108）都被占用，空闲块只剩 3764。
  3. free(16500)：归还中间块（16384 + 前一块的 108 + 本块头块 8 = 16500）。库从头块得知大小，把这块插到链表头部：head → 16492（100 字节）→ 16708（3764 字节）。链表终于不止一个元素，空闲空间开始碎了。
  4. 再释放剩下两块、不合并：链表变成 head → 16600 → 16384 → 16492 → 16708。所有内存都空闲了，却被切成四块。解决办法很简单：遍历链表，合并相邻块，堆就重新完整了。

下面的 malloc.py 模拟器里点"原书 4KB 堆"可以逐步重放这个过程。注意 malloc.py 的空闲链表记的 sz 是空闲块的总字节数（含节点头），比原书节点里的 size 字段多 8：3988 对应书中的 3980，3772 对应 3764，每块 108 对应 100。

3.5 堆不够了：让堆增长

堆空间耗尽时怎么办？最简单的做法是直接失败，返回 NULL，这完全正当（"你尽力了"）。但大多数传统分配器一开始只要一个小堆，不够时再向 OS 要：调用 sbrk（多数 UNIX 系统）之类的系统调用让堆变大，然后从新空间里分配。为了服务 sbrk，OS 找到空闲的物理页，把它们映射进请求进程的地址空间，并返回新的堆末尾。

4图解：基本策略

有了机制，再看策略：有多个空闲块能满足请求时选哪一个？理想的分配器既快又少碎片；可惜请求序列由程序员决定、可以是任意的，任何策略遇到"合适"的坏输入都会表现很差。所以没有"最好"的策略，只有各自的利弊。

策略怎么选好处代价
最优适配（best fit）遍历整张表，在够大的块里选最小的返回的块最接近请求，试图减少浪费要完整遍历；常常留下很多小碎片
最差适配（worst fit）遍历整张表，选最大的块，切下需要的部分想让剩余的块依然很大要完整遍历；多数研究表明碎片反而更多、开销也高
首次适配（first fit）从表头找，第一个够大的就用快，不必遍历全部表头容易堆满小碎块；链表顺序变得重要（按地址排序利于合并、碎片往往更少）
下次适配（next fit）像首次适配，但从上次停下的位置接着找把搜索分散到整个链表，避免表头被切碎性能与首次适配相近

5图解：其他方法

5.1 分离空闲链表（segregated lists）与 slab 分配器

如果某个应用有一种（或少数几种）特别常见的请求大小，就单独为这个大小维护一个链表，其他请求交给通用分配器。好处很明显：专门服务一种大小，碎片几乎不是问题；而且大小正合适的请求无需复杂搜索，分配和释放都很快。

新的难题：该拿多少内存给专用池、多少留给通用池？Jeff Bonwick 为 Solaris 内核设计的 slab 分配器（slab allocator）处理得很漂亮：

  • 内核启动时，为经常请求的内核对象（锁、文件系统 inode 等）建立若干对象缓存（object cache），每个缓存就是某个大小的分离空闲链表。
  • 某个缓存空闲空间不足时，向通用分配器要一些 slab（总大小是页大小和对象大小的倍数）。
  • 反过来，某个 slab 里所有对象的引用计数都归零时，通用分配器可以把它收回，通常发生在 VM 系统需要更多内存时。
  • 更进一步：空闲对象保持在已初始化状态。Bonwick 发现数据结构的初始化和析构很昂贵，保持预初始化状态可以省掉每个对象频繁的初始化/析构循环，明显降低开销。

Jeff Bonwick 不仅写了 slab 分配器，还领导了 ZFS 文件系统的开发。原书借这个例子说：几乎每个伟大的产品或技术背后，都有一个（或一小群）天赋、能力和投入远超常人的人。努力成为这样的人；如果做不到，就想办法和这样的人一起工作，你一天学到的会比大多数人一个月还多。

5.2 伙伴系统（buddy allocation）

合并对分配器至关重要，于是有些方案专门围绕"让合并变简单"来设计，二分伙伴分配器（binary buddy allocator）就是一例。空闲内存一开始被看成一整块大小为 2N 的空间。有请求时，把空闲空间递归地一分为二，直到再分一次就放不下请求为止，然后把这块交出去。下图是 64KB 空间为 7KB 请求一路分割的过程：

因为只能发 2 的幂大小的块，伙伴系统会有内部碎片。它的妙处在释放时：归还 8KB 块时，分配器检查它的"伙伴"8KB 是否空闲，是就合并成 16KB；再检查这个 16KB 的伙伴，空闲就再合并……这个递归合并一直沿树向上，要么恢复出整块空间，要么在遇到正被使用的伙伴时停下。

为什么找伙伴这么容易？看看地址：每对伙伴的地址只差一位，差的是哪一位由它们在树中的层级决定。大小为 2k 的块，伙伴地址 = 地址 XOR 2k。

5.3 其他想法

  • 扩展性：上面很多方法的大问题是缺乏扩展性，尤其是链表搜索可能很慢。高级分配器用更复杂的数据结构换性能，比如平衡二叉树、伸展树（splay tree）、偏序树（partially-ordered tree）。
  • 多处理器：现代系统多核、跑多线程负载，因此很多工作致力于让分配器在多处理器上表现良好，两个经典例子是 Berger 等人的 Hoard 和 Evans 的 jemalloc（用于 FreeBSD、Firefox、Facebook 等）。
  • 真实世界：想知道真实分配器有多复杂，可以读读 glibc 分配器的工作原理（下面的实验就偷看了 glibc 的头块）。

7先预测，再验证

（作业 1）点"作业 1"预设（-n 10 -H 0 -p BEST -s 0，堆 100 字节、基址 1000）。先别点下一步：看操作序列（跟踪框里的 ptr[k] = Alloc(n)），预测每次分配返回什么、链表怎样变化。随着时间推移，链表有什么特点？
看答案

Alloc(3) → 1000，链表 [1003:97]；Free(ptr[0]) → [1000:3][1003:97]；Alloc(5) → 1003（3 太小，97 是唯一够大的）；Free → [1000:3][1003:5][1008:92]；Alloc(8) → 1008；Free → 4 个元素；Alloc(8) → 1008（8 正好完全匹配，不分割，链表少一个元素）；Free → 又是 4 个；Alloc(2) → 1000（最优适配选大小 3 的块，剩 [1002:1]）；Alloc(7) → 1008（选 8，剩 [1015:1]）。

特点：没有合并，链表只增不减，开头堆积了 3、5、1、1 这样的小块，每次搜索都要把它们全看一遍（最优适配本来就要遍历整张表）。

（作业 2、3）同样的种子，把策略换成 WORST，再换成 FIRST（点预设"作业 2 / 作业 3"）。哪一步开始和 BEST 不同？"本次搜索元素数"有什么变化？
看答案

WORST：第 4 次分配 Alloc(8) 不再复用 1008 的 8 字节块，而是去切最大的 84 字节块，返回 1016；之后 Alloc(2)、Alloc(7) 也从大块切（1024、1026）。结果最大块从 84 缩到 67，链表涨到 5 个元素，碎片更多。

FIRST：返回地址和 BEST 完全相同（这个负载下恰好一样），但搜索更少：Alloc(8) 第二次只看了 3 个元素，Alloc(2) 只看了 1 个。平均每次分配搜索的元素数：BEST 3.00、WORST 3.33、FIRST 2.17。点"用当前参数比较四种策略"可以直接看到这张表。

（作业 4）在作业 1 的参数上分别试 -l ADDRSORT / SIZESORT+ / SIZESORT-。对 BEST、WORST 来说，链表顺序会改变结果吗？对 FIRST 呢？FIRST + SIZESORT− 相当于什么策略？
看答案

BEST 和 WORST 总是遍历整张表，顺序只影响平局时选谁，这个负载里结果和搜索数都不变。FIRST 就不同了：SIZESORT− 让最大块永远在表头，首次适配第一个元素就命中，行为等同于最差适配，但每次只搜索 1 个元素（平均 1.00）；SIZESORT+ 让最小块在前面，首次适配找到的第一个够大的块就是最优适配的那一块，相当于"不用遍历全表的最优适配"。代价是：释放时要维持有序（插入变慢），而且按大小排序会妨碍合并（见下一题）。

（作业 5）把 -n 改成 1000（BEST、ADDRSORT），分别在不勾选和勾选"合并 -C"时运行，看最后的空闲块数和失败次数。然后保持 -C，把顺序改成 SIZESORT+，合并还有效吗？
看答案

不合并：591 次分配中 177 次失败，大请求（≥ 8 字节）几乎都失败，最后链表有 31 个元素、最大块只有 6 字节。合并：515 次分配只失败 29 次，最后链表只剩 1 个 98 字节的块。WORST 不合并更惨：堆最终碎成 100 个 1 字节的块，658 次失败。

顺序很重要：malloc.py 的合并只检查链表中相邻的两个元素地址是否连续。按大小排序时地址相邻的块通常不在链表里挨着，于是 BEST + SIZESORT+ + -C 仍有 163 次失败、28 个空闲块，几乎等于没合并。这就是原书说"按地址排序让合并更容易"的原因。

（作业 6、7）回到作业 1 的参数、-n 1000 -C，把分配比例 -P 改成 90、再改成 10，会发生什么？然后点"制造碎片"预设：怎样的请求序列会让空闲空间高度碎片化，即使开了合并也没用？
看答案

-P 90：分配远多于释放，堆很快被占满，904 次分配里 753 次失败，最后只剩 2 字节空闲。-P 10：几乎每次分配后都会释放，堆大部分时间是空的，一次失败都没有，合并后空闲链表只有 1 个元素。

"制造碎片"：先连续分配 10 个 10 字节把堆填满，再释放第 0、2、4、6、8 块。空闲 50 字节，但五个洞互不相邻（中间隔着仍在使用的块），合并也无能为力，+20 失败。规律：交替释放，让每个空闲块都被已分配块夹住。

（伙伴系统）64KB、最小块 1KB，依次执行 +7K,+8K,+3K,+16K，然后 -1。先预测：四个块分别落在哪个地址？释放 #1 时能合并吗？再释放 #0 呢？
看答案

#0：7K → 8K 块，64→32→16→8 分割后得到 [0, 8K)；#1：8K 正好用掉 #0 的伙伴 [8K, 16K)；#2：3K → 4K，分割 [16K, 32K) 后得到 [16K, 20K)；#3：16K，分割 [32K, 64K) 得到 [32K, 48K)。

释放 #1：伙伴 = 8192 XOR 8192 = 0，也就是 #0，正在使用 → 不能合并。再释放 #0：伙伴 0 XOR 8192 = 8K 空闲 → 合并为 [0, 16K)；新块的伙伴 = 0 XOR 16384 = 16K，即 [16K, 32K)，它已被分割、里面还有 #2 → 停止。内部碎片：#0 浪费 1K、#2 浪费 1K。

8动手实验：嵌入式空闲链表与 glibc 的头块

实验目录 labs/17-free-space/：

看点：malloc(100) 返回 16392 而不是 16384，因为前 8 字节是头块；三次分配后空闲块是 3764（4088 − 3 × 108）。全部释放却不合并时，空闲总量有 3 × 100 + 3764 + 3 × 8 = 4088 字节，malloc(3900) 仍然失败，因为没有一块单独够大；合并之后立刻成功。

glibc_header 的输出（示例输出，你的机器上地址会不同）：

a=0x5e2b8f7552a0 b=0x5e2b8f755310 c=0x5e2b8f755380
b - a = 112 bytes  (请求 100，实际每块占 112)
malloc_usable_size(a) = 104
header size field of a = 0x71 -> chunk size 112, flags 1
after free(b): d = malloc(100) = 0x5e2b8f755310  (same as b)

在 64 位 glibc 上，malloc(100) 实际占 112 字节：请求加上头部开销，再向上对齐到 16 字节。用户指针前 8 字节存着"块大小 | 标志位"：0x71 = 112 | 1，最低位是 PREV_INUSE 标志（前一块正在使用）。由于块大小总是 16 的倍数，低 3 位本来就是 0，glibc 便拿它们存标志。free(b) 后再 malloc(100) 拿回了同一块：glibc 为常见的小尺寸维护了按大小分开的缓存链表（tcache/fastbin），这正是 5.1 节"分离空闲链表"的思想。

9自测题

原书的 4KB 堆，初始空闲块 size 字段为 4088，头块 8 字节。执行 malloc(100) 后，剩下的空闲块 size 字段是多少？
库要找 100 + 8 = 108 字节，4088 − 108 = 3980。3988 是只减了 100、忘了头块。（malloc.py 模拟器显示的 sz:3988 是另一种记法：它把空闲块自己的 8 字节节点头也算进 sz 里。）
free(ptr) 不带大小参数，库是怎么知道要释放多少字节的？
头块放在交出去的内存之前，释放时往回退一个头块就能读到大小，魔数还能做完整性检查。已分配块本来就不在空闲链表里（A 不对）。
空闲链表依次为 10、30、20（忽略头块），请求 15 字节。最优适配（best fit）之后的链表是？
最优适配在够大的块（30、20）里选最小的 20，切下 15，留下 5。B 是最差适配和首次适配的结果。
下列哪种策略不需要每次都遍历整个空闲链表？
首次适配找到第一个够大的块就停；最优和最差适配都要看完所有元素才能确定最小/最大的那个（除非链表按大小排好序）。
64KB 的二分伙伴系统收到 7KB 的请求，调用者实际占用多大的块？
伙伴系统只发 2 的幂大小的块：64 → 32 → 16 → 8，再分就是 4KB，放不下 7KB，所以停在 8KB。多出的 1KB 是内部碎片。
伙伴系统中，一个 8KB 块位于地址 16384（16KB）。它的伙伴在哪里？
伙伴地址 = 地址 XOR 块大小 = 16384 XOR 8192 = 24576（24KB）。两者只在第 13 位（8192）上不同。8192 是 [0, 16K) 那个 16KB 块的右半，和它不在同一个父块下。
下列哪一项属于内部碎片？
内部碎片是发出去的块内部没被请求的部分。A、C 都是外部碎片（空闲空间被切碎在块之间）。
slab 分配器比一般的分离空闲链表多做了什么？
Bonwick 发现初始化和析构数据结构很昂贵；slab 让空闲对象保持预初始化状态，降低了每个对象的开销。另外，缓存不足时它向通用分配器要 slab，slab 全空时可以被收回。

10常见误区与小结

误区 1："malloc(N) 只占 N 字节。"还有头块（原书例子 8 字节，glibc 上 malloc(100) 实际占 112 字节），可能还有对齐填充。分配器找的是 N + 头块大小的空闲块。

误区 2："最优适配浪费最少，所以碎片最少。"它常常留下大量很小、几乎没用的碎块，还要遍历整张表。没有任何策略在所有负载下都最好。

误区 3："释放了就不会碎片。"不合并时，即使所有内存都空闲，也可能被切成很多块（图 17.7）。而且合并只能合并地址相邻的空闲块；被使用中的块隔开的洞无论如何都合并不了。

误区 4："空闲链表节点另外 malloc 出来。"分配器不能调用自己；节点就写在空闲块自己的开头。

误区 5："碎片多了就紧凑一下。"用户态分配器不能移动已交出去的内存，C 程序的指针可能在任何地方。紧凑只在 OS 管理分段（或有 GC 的语言）里可行。

误区 6："伙伴系统没有碎片。"它有内部碎片（只发 2 的幂），也有外部碎片：两个空闲块如果不是伙伴，就不能合并（模拟器预设"不是伙伴就不能合并"）。

本章小结

  • 变长分配会产生外部碎片：总空闲足够，却没有足够大的连续块。这是本章所有技术要对付的问题。
  • 两个基本机制：分割（请求小于空闲块时切下一部分）和合并（释放时并起地址相邻的空闲块）。
  • 头块放在每个已分配块之前，记录大小（和魔数），free(ptr) 用 ptr − 1 找到它；因此 malloc(N) 实际需要 N + 头块大小。
  • 空闲链表嵌入空闲空间本身：每个空闲块开头放 size + next。原书数字：4KB 堆 → 4088 → malloc(100) 后 3980 → 三次后 3764。
  • 堆不够时可以失败，也可以用 sbrk 让 OS 扩大堆。
  • 基本策略 best / worst / first / next fit 各有取舍；链表的排序方式（按地址利于合并）与策略同样重要。
  • 更进一步：分离链表和 slab 专门服务常见大小；伙伴系统让合并变成一次异或，代价是内部碎片；高级分配器用树结构、针对多处理器优化。
  • 与后续章节的联系：第 18 章的分页只分配固定大小的页，从根本上避开外部碎片；OS 内核内部仍然大量使用 slab、伙伴这类分配器管理自己的数据结构和物理页。
