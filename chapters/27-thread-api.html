本章要解决什么

如何创建和控制线程？操作系统应该提供什么样的线程创建和控制接口？这些接口如何设计才能既好用又实用？

CRUX: How to create and control threads. What interfaces should the OS present for thread creation and control? How should these interfaces be designed to enable ease of use as well as utility?

上一章我们知道了线程是什么、为什么共享数据会出现竞态条件（race condition）。这一章是一次"插叙"（interlude）：先把 POSIX 线程库（pthreads）里最常用的几组接口过一遍——创建与等待（pthread_create / pthread_join）、锁（pthread_mutex_*）、条件变量（pthread_cond_*）。

原书说这一章更适合当"参考手册"：锁会在第 28 章详细讲怎么实现，条件变量在第 30 章细讲。本页的重点放在最容易写错的地方：参数和返回值的生命周期、忘记初始化锁、不检查返回码、用 if 而不是 while 等待条件。两个模拟器让你亲眼看到这些错误是怎么发生的。

核心概念速览

pthread_create

创建一个新线程，从你指定的函数（start routine）开始执行，拥有自己的调用栈，与其他线程共享地址空间。

pthread_join

等待某个线程结束，并通过 void ** 拿回它的返回值（一个 void *）。

void * 参数与返回值

用"无类型指针"让线程函数能接收和返回任何类型；代价是你必须自己负责类型转换和内存生命周期。

每个线程有自己的栈

线程函数里的局部变量只属于该线程，线程一结束就被回收——绝不能把它们的地址返回出去。

互斥锁（mutex）

pthread_mutex_lock/unlock 保护临界区（critical section）；必须先初始化，调用后要检查返回码。

条件变量（condition variable）

一个线程等待另一个线程"做完某事"的机制：wait 睡眠并释放锁，signal 唤醒等待者。

用 while 重新检查

被唤醒只是"条件可能变了"的提示，不是保证；醒来后必须在 while 里重新检查。

-pthread

包含 <pthread.h>，编译链接时加 -pthread：gcc -o main main.c -Wall -pthread。

创建线程：pthread_create

POSIX 里创建线程只需要一个调用：

#include <pthread.h>
int pthread_create(pthread_t             *thread,
                   const pthread_attr_t  *attr,
                   void *               (*start_routine)(void *),
                   void                  *arg);

第一次看到这个声明可能有点吓人（尤其是没用过函数指针的话），其实只有四个参数，逐个拆开就很简单：

为什么是 void *？读懂函数指针签名

第三个参数 void *(*start_routine)(void *) 读法是：start_routine 是一个指针，指向一个"接收一个 void * 参数、返回 void *"的函数。原书举了两个对照：

如果线程函数……声明会变成
接收 int，返回 void *void *(*start_routine)(int), int arg
接收 void *，返回 intint (*start_routine)(void *), void *arg
实际的 pthreadsvoid *(*start_routine)(void *), void *arg

之所以都用 void *：参数用 void * 就能传任何类型的数据（传它的地址即可）；返回值用 void * 就能返回任何类型的结果。代价是 C 编译器帮不了你做类型检查，线程函数里要自己把 void * 转回真实类型。

传多个参数：打包成结构体（Figure 27.1）

typedef struct {
    int a;
    int b;
} myarg_t;

void *mythread(void *arg) {
    myarg_t *args = (myarg_t *) arg;     // ① 把 void* 转回真实类型
    printf("%d %d\n", args->a, args->b);
    return NULL;
}

int main(int argc, char *argv[]) {
    pthread_t p;
    myarg_t args = { 10, 20 };           // ② 两个参数装进一个结构体
    int rc = pthread_create(&p, NULL, mythread, &args);  // ③ 传结构体的地址
    ...
}
  • ①：线程函数拿到的永远是 void *，第一件事就是转换成自己期待的类型再"拆包"。
  • ③：这里传的是 main 栈上 args 的地址。之所以安全，是因为 main 之后会 join 等线程结束——参数的寿命必须覆盖线程使用它的整个期间。

线程一旦创建，就是另一个活生生的执行实体：有自己的调用栈，与现有的所有线程运行在同一个地址空间里。

等待线程：pthread_join 与返回值

int pthread_join(pthread_t thread, void **value_ptr);

第一个参数指定等哪个线程（就是 pthread_create 帮你填好的那个 pthread_t）。第二个参数是指向返回值的指针。线程函数返回的是 void *；pthread_join 要修改调用者的一个 void * 变量，所以必须拿到这个变量的地址——于是就成了 void **。

返回一个结构体（Figure 27.2）

 1  typedef struct { int a; int b; } myarg_t;
 2  typedef struct { int x; int y; } myret_t;

 5      myret_t *rvals = Malloc(sizeof(myret_t));   // 在堆上分配
 6      rvals->x = 1;

 8      return (void *) rvals;

13      myret_t *rvals;

注意原书这里用的是首字母大写的包装函数（Malloc、Pthread_create、Pthread_join）：它们只是调用同名小写版本，并确认没有返回意外结果。几点值得记住：

  • 不需要参数时，pthread_create 的 arg 传 NULL 即可；不关心返回值时，pthread_join 的第二个参数也传 NULL。
  • 只传一个值（例如 long long int）时，不必打包，直接把值塞进 void *（Figure 27.3，见下面模拟器的第三个场景）。
  • 绝对不要返回指向线程调用栈上变量的指针。线程返回时，它的栈帧被自动回收（这正是栈好用的原因），留给 main 的就是一个悬空指针。
void *mythread(void *arg) {
    myarg_t *args = (myarg_t *) arg;
    printf("%d %d\n", args->a, args->b);
    myret_t oops;               // ALLOCATED ON STACK: BAD!
    oops.x = 1;
    oops.y = 2;
    return (void *) &oops;
}

原书说：打印你以为返回了的值时，你"很可能（但不一定）"会大吃一惊——未定义行为就是这个意思：有时碰巧正确，有时是垃圾，有时崩溃。好在 gcc 往往会对这种代码发出警告，这也是要认真看编译警告的又一个理由。下面的模拟器把这件事一步步画出来。

什么时候用 join？先 pthread_create 再立刻 pthread_join 其实是一种很奇怪的写法——有个更简单的方法能完成完全相同的事，叫过程调用（procedure call）。实际程序通常会创建多个线程再等它们。也并非所有多线程程序都 join：例如多线程 Web 服务器可能创建一批工作线程，由主线程不停接收请求分发给它们，永不结束；而并行计算程序通常要用 join 确保所有工作完成后再退出或进入下一阶段。

锁：pthread_mutex

除了创建和等待，pthreads 最有用的一组函数就是通过锁为临界区提供互斥（mutual exclusion）：

int pthread_mutex_lock(pthread_mutex_t *mutex);
int pthread_mutex_unlock(pthread_mutex_t *mutex);

用法一看就懂：

pthread_mutex_t lock;
pthread_mutex_lock(&lock);
x = x + 1;          // 或者任何临界区代码
pthread_mutex_unlock(&lock);

语义：如果调用 lock 时没有别的线程持有锁，调用者获得锁并进入临界区；如果锁已被别人持有，调用者不会从 lock 调用返回，直到它拿到锁为止（即持有者 unlock 之后）。可能有很多线程同时卡在 lock 里，但只有持有锁的那个线程应该调用 unlock。

然而原书指出，上面这段代码有两个重要错误：

错误 1：没有初始化锁

所有锁都必须正确初始化，才能保证它一开始处于正确状态。POSIX 提供两种方式：

方式代码说明
静态初始化pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;把锁设为默认值，适合全局/静态锁
动态初始化（运行时）int rc = pthread_mutex_init(&lock, NULL);
assert(rc == 0); // always check success!		第二个参数是可选属性，NULL＝默认；原书作者通常用这种。用完要调用 pthread_mutex_destroy()

错误 2：没有检查返回码

和 UNIX 里几乎所有库函数一样，lock 和 unlock 也可能失败！不检查错误码，失败就会悄无声息——在这里可能意味着多个线程同时进入了临界区。最低限度，用包装函数断言调用成功（Figure 27.4）：

// Keeps code clean; only use if exit() OK upon failure
void Pthread_mutex_lock(pthread_mutex_t *mutex) {
    int rc = pthread_mutex_lock(mutex);
    assert(rc == 0);
}

更成熟的（非玩具）程序不能简单地退出，就应该在失败时做恰当的处理。

另外两个获取锁的函数

int pthread_mutex_trylock(pthread_mutex_t *mutex);
int pthread_mutex_timedlock(pthread_mutex_t *mutex, struct timespec *abs_timeout);
函数锁空闲时锁被占用时
lock获得锁，返回 0一直等（阻塞），直到拿到
trylock获得锁，返回 0立即返回失败（EBUSY）
timedlock获得锁，返回 0等到拿到锁或超时，先到者为准；超时为 0 时就退化成 trylock

这两个通常应当避免使用；但在某些场合（比如后面第 32 章讲的死锁）避免无限期卡在获取锁上是有用的。

lock/unlock 接收一个锁变量作为参数，因为不同的数据可以用不同的锁保护。一把大锁保护所有临界区是粗粒度（coarse-grained）加锁；为不同数据结构各配一把锁是细粒度（fine-grained）加锁，能让更多线程同时处于加锁代码中。第 28、29 章会深入这个话题。

条件变量：等待另一个线程

任何线程库的另一个主要组成部分是条件变量（condition variable）。当线程之间需要某种信号——一个线程要等另一个线程做完某事才能继续——就用它。两个基本函数：

int pthread_cond_wait(pthread_cond_t *cond, pthread_mutex_t *mutex);
int pthread_cond_signal(pthread_cond_t *cond);

使用条件变量还必须有一把与之关联的锁；调用上面任一函数时都应当持有这把锁。典型用法：

// 等待方
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t  cond = PTHREAD_COND_INITIALIZER;

Pthread_mutex_lock(&lock);
while (ready == 0)
    Pthread_cond_wait(&cond, &lock);
Pthread_mutex_unlock(&lock);
// 通知方（另一个线程）
Pthread_mutex_lock(&lock);
ready = 1;
Pthread_cond_signal(&cond);
Pthread_mutex_unlock(&lock);

要点逐条看：

  1. 通知方修改 ready 和调用 signal 时都持有锁，这样就不会意外引入竞态条件。
  2. wait 的第二个参数是锁，signal 却没有。因为 wait 在让调用者睡眠的同时会释放这把锁——否则通知方怎么拿得到锁去 signal 呢？而 wait 在被唤醒、返回之前会重新获取锁。所以等待方在"开头 lock"到"结尾 unlock"之间运行的任何时刻，都持有锁。
  3. 用 while 而不是 if 重新检查条件。有些 pthread 实现可能虚假唤醒（spurious wakeup）一个等待中的线程；如果不重新检查，它会以为条件已经变了。原书的说法是：把"被唤醒"看成"某些东西可能变了"的提示（hint），而不是确定的事实。第 30 章还会看到另一个原因：别的线程可能抢先把条件"用掉"。

别用裸 flag 代替条件变量

有时很想省事，用一个简单的标志变量在两个线程之间传信号：

// 等待方
while (ready == 0)
    ; // spin
// 通知方
ready = 1;

原书的态度很明确：永远不要这样做。理由有二：第一，性能往往很差——长时间自旋就是白白烧 CPU；第二，容易出错——研究 [X+10] 发现，这种"临时凑合"（ad hoc）的同步大约一半有 bug。别偷懒，即使觉得不用也能行，也要用条件变量。本章实验 cond_wait.c 在本机量出了两者的差距：

编译与运行，以及使用指南

本章所有例子都很容易跑起来：代码里包含头文件 pthread.h，链接时加上 -pthread 标志：

gcc -o main main.c -Wall -pthread

只要 main.c 包含了 pthreads 头文件，你就成功编译了一个并发程序。至于它能不能正确工作——照例，那完全是另一回事。

原书在本章末尾的旁注"线程 API 指南"（Thread API Guidelines）值得逐条记住：

  1. 保持简单（Keep it simple）。线程之间加锁或发信号的代码越简单越好，复杂的线程交互会带来 bug。
  2. 尽量减少线程之间的交互（Minimize thread interactions）。每一种交互方式都要深思熟虑，用久经考验的方法构建（后面几章会学很多）。
  3. 初始化锁和条件变量。否则代码会"有时能跑、有时以非常奇怪的方式失败"。
  4. 检查返回码。不检查会导致怪异、难以理解的行为，让你（a）尖叫、（b）揪头发，或者（c）两者兼有。
  5. 小心传参和返回值的方式。特别是：只要你在传递一个指向栈上变量的引用，你很可能做错了什么。
  6. 每个线程都有自己的栈。函数里的局部变量本质上是该线程私有的，其他线程（很难）访问到。要在线程间共享数据，值必须放在堆上或其他全局可访问的位置。
  7. 总是用条件变量在线程之间发信号。虽然用简单的 flag 很诱人，但别这么做。
  8. 使用手册页（man pages）。在 Linux 上 pthread 的手册页信息量很大，讨论了很多本章提到的细节。man -k pthread 能看到构成整个接口的一百多个 API。

先预测再验证

在"返回值的生命周期"模拟器中选择 oops 场景，取消勾选"内存被复用"。先预测：main 最后打印什么？这说明代码是正确的吗？
看答案
会打印 returned 1 2——因为那块已回收的栈内存恰好还没被别人写过。但这不说明代码正确：读已回收的栈是未定义行为，结果取决于之后有没有别的调用复用那块内存、线程库会不会把线程栈归还（unmap）。勾选"被复用"再跑一次，就会读到垃圾；本章实验 bad_return 在本机实际读到的是 8392704 0，ASan 版本则直接 SEGV。
在 Figure 27.2 场景中，线程退出那一步之后，main 的 args 还"活着"吗？T1 的 arg 指针呢？如果 main 在 pthread_create 之后不 join 就直接从一个函数返回（args 的栈帧被弹出），会发生什么？
看答案
args 在 main 的栈上，main 还没返回，所以活着；T1 的 arg 本身随 T1 栈帧一起回收了，但这无所谓——它只是个指向别处的指针。如果创建线程的函数不等线程就返回，&args 就变成了悬空指针，而新线程可能稍后才读取它（线程何时运行取决于调度器）——同样是"传递指向栈上变量的引用"错误的变种。常见修法：给每个线程 malloc 一份参数，或保证创建者 join 之后才离开作用域。
在 cond 模拟器里选 W2 抢先，分别用 while 和 if 跑到底。先预测：if 版本的"错误"计数是多少？while 版本里 W1 最终处于什么状态？
看答案
if 版本：W1 醒来后不再检查，直接"取走"数据，但 ready 已经被 W2 取走变回 0，错误计数为 1。while 版本：W1 重新检查发现 ready==0，于是再次 wait，最终停在睡眠状态（等下一次生产）——这才是正确行为：数据只被取走一次。
改编自 Homework 6–8（main-signal.c vs main-signal-cv.c）：父线程用 while (done == 0) ; 等子线程，子线程要运行很久。父线程把时间花在了哪里？换成条件变量版本，好处是正确性、性能，还是两者兼有？
看答案
父线程在空转，把一整个 CPU 烧在反复读 done 上（本章实验测得等待 0.5 秒就消耗约 0.5 秒 CPU）。条件变量版本两者兼有：性能上，等待者睡眠不占 CPU；正确性上，done 的读写都在锁保护下，没有数据竞争（helgrind / ThreadSanitizer 对裸 flag 版本会报告竞争，对 cv 版本则不会——本章实验里的 cond_wait_tsan 可以验证）。
改编自 Homework 3–5：线程 1 先 lock(m1) 再 lock(m2)，线程 2 先 lock(m2) 再 lock(m1)。能找到一种调度让两个线程都永远卡住吗？如果两段代码外面再套一把全局锁 g，还会出问题吗？
看答案
能：线程 1 拿到 m1 后被切走，线程 2 拿到 m2，然后各自等对方持有的锁——这就是死锁（第 32 章细讲）。套一把全局锁后，同一时刻只有一个线程能进入这段"先后加两把锁"的代码，死锁不会发生；但像 helgrind 这类工具只看"加锁顺序不一致"，可能仍然报告——说明工具报告的是潜在问题，需要人来判断。

自测题

1. pthread_create 的第一个参数为什么是 pthread_t * 而不是 pthread_t？
pthread_create 需要初始化调用者的 pthread_t 变量，之后调用者用它来 join 这个线程。要修改调用者的变量就得拿到它的地址。传 NULL 表示默认的是第二个参数 attr。
2. 下面哪种从线程返回结果的方式是错误的？
线程返回时它的栈帧被回收，局部变量的地址变成悬空指针（原书的 oops 例子）。C 是 Figure 27.2 的做法，B 是 Figure 27.3 的做法（在 64 位系统上 void* 足够装下 long long），D 也可行（全局变量不在栈上）。
3. pthread_join(p, (void **) &rvals) 中第二个参数为什么是二级指针？
"要修改一个变量，就传它的地址"。被修改的变量类型是 void *（或其他指针），它的地址自然是 void **。join 不负责释放任何内存。
4. 原书指出 "pthread_mutex_t lock; pthread_mutex_lock(&lock); ..." 这段代码有两个问题，是哪两个？
锁必须用 PTHREAD_MUTEX_INITIALIZER 或 pthread_mutex_init() 初始化；lock/unlock 可能失败，不检查的话失败是静默的，可能让多个线程同时进入临界区。
5. 为什么 pthread_cond_wait 要接收一个锁作为参数，而 pthread_cond_signal 不用？
如果 wait 睡眠时不释放锁，通知方就永远拿不到锁去修改条件并 signal。wait 返回前重新获取锁，保证等待方检查条件时总是持锁。原书建议 signal 时也持有锁（B 错）。
6. 等待条件时为什么要写 while (ready == 0) wait(...) 而不是 if？
原书：有些 pthread 实现可能虚假唤醒等待线程；把唤醒看作"某些东西可能变了"的提示而不是事实。重新检查的代价只是一点点开销。可以在本页 cond 模拟器里对比两种写法。
7. 关于 pthread_mutex_trylock 和 pthread_mutex_timedlock，哪句正确？
trylock 在锁被持有时立即返回失败；timedlock 在超时或获得锁时返回（先到者为准），不会夺走别人的锁。原书说两者通常应避免，但在死锁相关场景中能派上用场。
8. 编译一个使用 pthreads 的程序 main.c，正确的命令是？
原书 27.5 节：包含 pthread.h，并在链接时显式加 -pthread 标志。
9. 两个线程要共享一个计数器，应该把它放在哪里？
每个线程有自己的栈，局部变量本质上是线程私有的；要共享数据，值必须放在堆上或其他全局可访问的位置（原书 Thread API Guidelines）。D 会得到两个互不相干的变量；寄存器是每个线程私有、上下文切换时保存恢复的。

常见误区

  • "打印出来是对的，所以返回栈上指针没问题。"错。那是未定义行为碰巧表现正常，换个编译选项、换个时机就是垃圾或崩溃。用 -Wall 看警告，用 -fsanitize=address 捕获。
  • "在循环里用同一个局部变量的地址给多个线程传参。"例如 for (i…) pthread_create(…, &i)：所有线程拿到的是同一个地址，读到的值取决于调度，经常大家都读到最后的 i。每个线程给一份独立的参数。
  • "pthread_create 返回时新线程已经跑过了 / 还没开始跑。"两者都不能假设：新线程可能立刻运行，也可能很久以后才运行（第 26 章的 Figure 26.3–26.5）。
  • "声明了 pthread_mutex_t 就能用。"必须初始化（静态 PTHREAD_MUTEX_INITIALIZER 或 pthread_mutex_init），条件变量同理。
  • "lock/unlock 不会失败，不用检查。"任何库调用都可能失败，失败时静默继续可能让多个线程进入临界区。
  • "被 signal 唤醒就说明条件满足了，用 if 就够。"要用 while：虚假唤醒、别的线程抢先都会让条件在你醒来时不成立。
  • "用一个 volatile flag 自旋等待更简单高效。"又浪费 CPU 又容易错；用条件变量。

本章小结

  • 创建：pthread_create(&p, attr, func, arg)，新线程从 func(arg) 开始，有自己的栈、共享地址空间；多个参数打包成结构体传地址，单个值可以直接塞进 void *。
  • 等待：pthread_join(p, &ret) 等线程结束并取回 void * 返回值。返回值要指向堆或全局数据，永远不要指向线程栈。
  • 锁：pthread_mutex_lock/unlock 保护临界区；必须初始化、必须检查返回码；trylock/timedlock 一般少用。
  • 条件变量：pthread_cond_wait(&c, &m) 睡眠时释放锁、返回前重获锁；pthread_cond_signal(&c) 唤醒等待者；修改条件和 signal 时持锁；等待用 while；别用裸 flag。
  • 编译：gcc … -Wall -pthread。
  • 原书结语：写出健壮高效的多线程代码，除了这些 API 之外，你只需要耐心和极大的细心。难的不是 API，而是如何构建并发程序的那些微妙逻辑。
