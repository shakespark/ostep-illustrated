本章要解决什么问题

如何等待一个条件？在多线程程序中，一个线程常常需要等某个条件成立（比如"子线程已经结束""缓冲区里有数据了"）之后才能继续执行。最简单的做法是自旋，一直检查直到条件成立。但这样极其低效，白白浪费 CPU 周期，某些情况下甚至是错的。那么，线程应该怎样等待一个条件？

原文：How should a thread wait for a condition?

上一章之前我们一直在研究锁（lock）。锁解决的是互斥：同一时刻只让一个线程进入临界区。但并发程序还有另一类同样常见的需求，就是等待与通知。比如父线程要等子线程结束（join），消费者要等缓冲区里有数据，生产者要等缓冲区有空位。这些需求都不能只靠锁来完成。

本章引入第二个同步原语：条件变量（condition variable，CV）。它和锁搭配，能优雅地解决 join、生产者/消费者（有界缓冲区）以及内存分配器这类"覆盖条件"问题。本章的几个结论会反复用到：永远用 while 检查条件、调用 wait/signal 时持有锁、不同的等待者用不同的条件变量。下一章的信号量（semaphore）能同时充当锁和条件变量；第 32 章里的"顺序违反（order violation）"类 bug，修复方法正是本章的条件变量。

核心概念速览

条件变量（condition variable）

一个显式的等待队列：状态不如意时线程把自己挂上去睡觉，另一个线程改变状态后把它叫醒。

wait(c, m)

调用时必须持有锁 m；它原子地释放 m 并睡眠；被唤醒后，返回前会重新获取 m。

signal(c)

唤醒一个睡在 c 上的线程（如果有）。没人在等就什么也不做：信号不会被记住。

状态变量（state variable）

如 done、count。条件变量本身没有记忆，睡眠、唤醒和加锁都要围绕状态变量来做。

Mesa 语义（Mesa semantics）

signal 只是一个"提示"：被唤醒的线程真正运行时，状态可能已经又变了，所以要用 while 重新检查。

生产者/消费者（bounded buffer）

经典同步问题。最终解法是 while 加两个条件变量 empty/fill，再加多槽循环缓冲区。

覆盖条件（covering condition）

不知道该唤醒谁时，用 broadcast 把所有等待者都叫醒，各自重新检查。代价是一些线程白醒一场。

伪唤醒（spurious wakeup）

某些实现里一次 signal 可能唤醒两个线程。这又是一个必须用 while 的理由。

定义与接口：wait() 和 signal()

条件变量最早可以追溯到 Dijkstra 的"私有信号量"，后来 Hoare 在管程（monitor）的工作里给了它"条件变量"这个名字。在 POSIX 里这样声明和使用：

pthread_cond_t c = PTHREAD_COND_INITIALIZER;   // 需要正确初始化
pthread_cond_wait(pthread_cond_t *c, pthread_mutex_t *m);
pthread_cond_signal(pthread_cond_t *c);

注意 wait() 多带了一个互斥锁参数。它假定调用时 m 已经被锁住，然后做两件事：①原子地释放锁并让调用者睡眠；②被别的线程 signal 唤醒后，在返回调用者之前重新获取锁。所以从调用者的角度看，wait() 前后自己都持有锁。之所以设计得这么复杂，是为了防止线程"准备去睡"的那一刻出现竞态条件，下面的 join 例子会讲清楚。

用条件变量实现 join

我们希望 Figure 30.1 的程序总是输出 parent: begin → child → parent: end。正确的写法（Figure 30.3）如下：

int done = 0;                                   // 状态变量
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t  c = PTHREAD_COND_INITIALIZER;

void thr_exit() {                  // 子线程结束时调用
    Pthread_mutex_lock(&m);
    done = 1;                      // 先改状态……
    Pthread_cond_signal(&c);       // ……再通知
    Pthread_mutex_unlock(&m);
}
void thr_join() {                  // 父线程等待
    Pthread_mutex_lock(&m);
    while (done == 0)              // 条件不满足才睡；用 while
        Pthread_cond_wait(&c, &m);
    Pthread_mutex_unlock(&m);
}

要考虑两种情况：

  • 父线程先运行：它拿锁，发现 done == 0，调用 wait() 睡下，同时释放锁。子线程之后运行，打印 child，拿锁，把 done 置 1，signal 叫醒父线程。父线程从 wait() 返回时已持有锁，解锁后打印 parent: end。
  • 子线程先运行完：它把 done 置 1 并 signal，但此时没人在等，signal 什么也不做。父线程之后调用 thr_join()，看到 done == 1，根本不睡，直接返回。

为什么需要状态变量 done？

去掉 done，只用锁和条件变量（Figure 30.4）：

✗ 没有状态变量（Figure 30.4） 
void thr_exit() {
    Pthread_mutex_lock(&m);
    Pthread_cond_signal(&c);
    Pthread_mutex_unlock(&m);
}
void thr_join() {
    Pthread_mutex_lock(&m);
    Pthread_cond_wait(&c, &m);
    Pthread_mutex_unlock(&m);
}
✗ 不持锁（Figure 30.5，假想的接口） 
void thr_exit() {
    done = 1;
    Pthread_cond_signal(&c);
}
void thr_join() {
    if (done == 0)
        Pthread_cond_wait(&c);
}

没有状态变量：如果子线程先运行，它 signal 的时候没人在等，这个信号就丢了。父线程随后调用 wait()，会永远睡下去，因为再也没有人会叫醒它。状态变量记录的正是线程们关心的那个事实；睡眠、唤醒和加锁都是围绕它建立的。

不持锁：这里有一个微妙的竞态。父线程检查 done，看到 0，正要调用 wait() 去睡，恰好在这一刻被中断。子线程运行，把 done 置 1 并 signal，可此时父线程还没进入等待队列，所以没有线程被唤醒。父线程恢复运行后照原计划去睡，从此永远睡下去。"检查条件"和"去睡"之间必须没有缝隙，而 wait() 在持锁状态下原子地"释放锁并入睡"，正是为了堵住这条缝。

发信号时总是持有锁（Always hold the lock while signaling）。严格说并非所有情况都必须持锁，但持锁发信号最简单，也最不容易出错。而"调用 wait 时持有锁"不只是建议，它是 wait 语义强制要求的：wait 假定调用时持锁，睡眠时释放锁，返回前重新获取锁。所以把两条合起来记：调用 signal 或 wait 时都持有锁，就不会出问题。

join 的三种写法：交错执行器

选一种实现，用线程按钮决定父、子线程的交错顺序。看看哪种写法在哪种交错下会让父线程"永远睡下去"。

生产者/消费者（有界缓冲区）问题

生产者/消费者问题也叫有界缓冲区（bounded buffer）问题，由 Dijkstra 提出。正是为了解决它，Dijkstra 和同事发明了通用的信号量。设想有一个或多个生产者线程往缓冲区里放数据，一个或多个消费者线程从里面取数据。多线程 Web 服务器就是这样工作的：生产者把 HTTP 请求放进工作队列，消费者线程取出来处理。管道也一样：grep foo file.txt | wc -l 中，grep 是生产者，wc 是消费者，中间的 UNIX 管道就是内核里的有界缓冲区。

先用最简单的单槽缓冲区（Figure 30.6）：put() 断言缓冲区为空，放入数据并令 count = 1；get() 断言缓冲区为满，令 count = 0 并返回数据。同步代码的职责很清楚：只在 count == 0 时 put，只在 count == 1 时 get。如果写错，断言就会触发。

int buffer;
int count = 0;              // 一开始为空

void put(int value) {
    assert(count == 0);
    count = 1;
    buffer = value;
}
int get() {
    assert(count == 1);
    count = 0;
    return buffer;
}

put 和 get 显然含有临界区，但只加一把锁不够：消费者发现缓冲区为空时，拿着锁自旋是没用的。我们需要让它睡下去，等生产者叫醒它，这就用到了条件变量。

第一次尝试：if + 单个条件变量（Broken v1）

cond_t  cond;
mutex_t mutex;

void *producer(void *arg) {
    for (int i = 0; i < loops; i++) {
        Pthread_mutex_lock(&mutex);            // p1
        if (count == 1)                        // p2
            Pthread_cond_wait(&cond, &mutex);  // p3
        put(i);                                // p4
        Pthread_cond_signal(&cond);            // p5
        Pthread_mutex_unlock(&mutex);          // p6
    }
}
void *consumer(void *arg) {
    for (int i = 0; i < loops; i++) {
        Pthread_mutex_lock(&mutex);            // c1
        if (count == 0)                        // c2
            Pthread_cond_wait(&cond, &mutex);  // c3
        int tmp = get();                       // c4
        Pthread_cond_signal(&cond);            // c5
        Pthread_mutex_unlock(&mutex);          // c6
        printf("%d\n", tmp);
    }
}

生产者在 p1–p3 等缓冲区变空，消费者在 c1–c3 等缓冲区变满，两边逻辑对称。只有一个生产者和一个消费者时，这段代码是对的。但只要有两个消费者（或两个生产者），就会暴露两个严重问题。先看第一个，它和 if 有关。

设有两个消费者 Tc1、Tc2 和一个生产者 Tp（Figure 30.9）：

  1. Tc1 先运行：拿锁（c1），发现没数据（c2），wait 睡下（c3），同时释放了锁。
  2. Tp 运行：拿锁（p1），发现不满（p2），放入数据（p4），signal（p5）。这让 Tc1 从睡眠变为就绪，但它还没有运行。Tp 继续循环，发现缓冲区满了，于是睡下（p6, p1–p3）。
  3. Tc2 插队：它恰好这时运行，走 c1、c2（有数据，不用等）、c4 把唯一的数据取走、c5、c6。
  4. Tc1 终于运行：从 wait() 返回前重新拿到锁，接着执行 c4 的 get()。但缓冲区已经空了，断言触发！

Mesa 语义与 Hoare 语义

问题的根源很简单：生产者叫醒 Tc1 之后、Tc1 真正运行之前，缓冲区的状态被 Tc2 改变了。signal 只是把线程唤醒，它是一个提示（hint）：告诉对方"世界的状态变了"，但不保证对方运行时状态仍然如它所愿。对 signal 的这种解释叫 Mesa 语义（Mesa semantics），得名于第一个这样实现条件变量的研究（Lampson 和 Redell 用 Mesa 语言做的 Pilot 系统）。与之相对的 Hoare 语义（Hoare semantics）提供更强的保证：被唤醒的线程会立即运行。Hoare 语义更难实现，几乎所有实际系统都采用 Mesa 语义。

下方的交错执行器提供了一个 Hoare 语义开关：signal 时把锁直接交给被唤醒者，并强制它下一步运行。你会看到"if + 两个 CV"在 Hoare 下完全正确（对小规模配置穷举所有交错，一次都没出错），在 Mesa 下却会被插队；而"if + 单个 CV"即使在 Hoare 下也会出错，因为消费者可能叫醒另一个消费者，被叫醒的那个会立刻对空缓冲区 get()。这说明 Hoare 语义只解决"被插队"，不解决"叫错人"。

第二次尝试：while + 单个条件变量（Broken v2）

修复第一个问题很容易：把 if 换成 while（Figure 30.10）。这样 Tc1 醒来后（持有锁）会立即重新检查共享变量（c2），如果缓冲区是空的，就再睡回去（c3）。生产者里的 if 也同样换成 while（p2）。

    Pthread_mutex_lock(&mutex);            // c1
    while (count == 0)                     // c2
        Pthread_cond_wait(&cond, &mutex);  // c3
    int tmp = get();                       // c4

由于 Mesa 语义，用条件变量时要记住一条简单规则：永远用 while 循环。有时不重新检查也没事，但重新检查总是安全的。

可这段代码仍然有 bug，也就是前面说的第二个问题，它和"只有一个条件变量"有关（Figure 30.11）：

  1. Tc1、Tc2 先后运行，都发现没数据，都睡在 cond 上。
  2. Tp 放入一个数据，signal 唤醒一个消费者（假设是 Tc1），然后继续循环，发现缓冲区满了，于是也睡在 cond 上。现在 cond 的队列里有 Tc2 和 Tp。
  3. Tc1 醒来，重新检查（c2），发现有数据，于是取走（c4），然后 signal（c5），只叫醒一个。该叫谁？缓冲区刚被取空，显然应该叫生产者。可是如果叫醒的是 Tc2（完全可能，取决于等待队列的管理方式）……
  4. Tc2 醒来发现缓冲区是空的（c2），又睡回去（c3）。Tp 手里还有数据要放，却一直睡着。Tc1 也回到循环开头睡下。三个线程全部睡着了。

正确方案：两个条件变量 + 多槽缓冲区

解法同样很小：用两个条件变量，在状态变化时准确地通知该醒的那一类线程（Figure 30.12）。生产者在 empty 上等待、在 fill 上发信号；消费者正好相反，在 fill 上等待、在 empty 上发信号。这样从设计上就排除了第二个问题：消费者永远不会误叫醒消费者，生产者也不会误叫醒生产者。

最后一步是提高并发度和效率：把单槽缓冲区换成 MAX 个槽的循环队列（Figure 30.13），让生产者能连续放入多个数据后才睡，消费者也能连续取多个数据。只有一个生产者和一个消费者时，这能减少上下文切换；有多个生产者或消费者时，还能让生产和消费并发进行。相应地，生产者只在所有槽都满时才睡（p2），消费者只在所有槽都空时才睡（c2）。

int buffer[MAX];
int fill_ptr = 0;
int use_ptr  = 0;
int count    = 0;

void put(int value) {
    buffer[fill_ptr] = value;
    fill_ptr = (fill_ptr + 1) % MAX;
    count++;
}
int get() {
    int tmp = buffer[use_ptr];
    use_ptr = (use_ptr + 1) % MAX;
    count--;
    return tmp;
}
cond_t empty, fill;
mutex_t mutex;

void *producer(void *arg) {
  for (int i = 0; i < loops; i++) {
    Pthread_mutex_lock(&mutex);           // p1
    while (count == MAX)                  // p2
      Pthread_cond_wait(&empty, &mutex);  // p3
    put(i);                               // p4
    Pthread_cond_signal(&fill);           // p5
    Pthread_mutex_unlock(&mutex);         // p6
  }
}
void *consumer(void *arg) {
  for (int i = 0; i < loops; i++) {
    Pthread_mutex_lock(&mutex);           // c1
    while (count == 0)                    // c2
      Pthread_cond_wait(&fill, &mutex);   // c3
    int tmp = get();                      // c4
    Pthread_cond_signal(&empty);          // c5
    Pthread_mutex_unlock(&mutex);         // c6
    printf("%d\n", tmp);
  }
}

检查条件时用 while，不要用 if。在多线程程序里检查条件，用 while 循环总是正确的；用 if 只是可能正确，取决于信号的语义。另外，有些线程库由于实现细节，一次 signal 可能唤醒两个线程，这叫伪唤醒（spurious wakeup）。这是重新检查所等条件的又一个理由。

说明：为了简化，消费者像 Figure 30.7 那样无限循环（while (1)），所以生产者全部完成、缓冲区取空、消费者都睡着时算"正常结束"；如果有生产者还没完成而所有线程都睡着了，就是 Figure 30.11 那种 bug。一次 signal 只唤醒一个线程；被唤醒的线程下次被调度时，会先重新拿锁，再执行 wait 之后的那一行（if 版本是 c4/p4，while 版本是 c2/p2），这和原书表格一行的粒度一致。

覆盖条件（covering condition）

再看一个例子，它来自 Lampson 和 Redell 关于 Pilot 系统的论文，也就是最早实现 Mesa 语义的那群人。设想一个多线程内存分配库（Figure 30.15）：

int bytesLeft = MAX_HEAP_SIZE;   // 堆里还剩多少字节
cond_t c;  mutex_t m;

void *allocate(int size) {
    Pthread_mutex_lock(&m);
    while (bytesLeft < size)
        Pthread_cond_wait(&c, &m);
    void *ptr = ...;             // 从堆里拿内存
    bytesLeft -= size;
    Pthread_mutex_unlock(&m);
    return ptr;
}
void free(void *ptr, int size) {
    Pthread_mutex_lock(&m);
    bytesLeft += size;
    Pthread_cond_signal(&c);     // 叫醒谁？？
    Pthread_mutex_unlock(&m);
}

场景：堆里 0 字节空闲。Ta 调用 allocate(100)，接着 Tb 调用 allocate(10)，两者都不够，都睡下。然后 Tc 调用 free(50)。signal 只叫醒一个线程，可它不知道该叫谁。如果叫醒了 Ta，Ta 发现 50 < 100，又睡回去；而本来能满足的 Tb（只要 10 字节）却继续睡着。

Lampson 和 Redell 的解法很直接：把 pthread_cond_signal() 换成 pthread_cond_broadcast()，唤醒所有等待的线程，这就保证了该醒的线程一定会醒。缺点是可能有性能损失：一些本不该醒的线程被白白叫醒，它们醒来、重新检查条件、再去睡。这样的条件叫覆盖条件（covering condition），因为它（保守地）覆盖了所有需要唤醒线程的情况。

细心的读者会发现，前面单个条件变量的生产者/消费者也可以用 broadcast 修好。但那里有更好的解法（两个 CV），所以我们用了更好的。一般来说，如果你发现程序只有把 signal 改成 broadcast 才能工作（而你觉得本不需要），那多半是有 bug，去修它！不过对于上面这种内存分配器，broadcast 可能就是最直接的方案。

模拟器

覆盖条件：内存分配器的 signal vs broadcast

三个线程共用一个条件变量 c。比较 free() 用 signal 和用 broadcast 时，谁醒了、谁白醒、谁被遗忘。

先预测，再验证

在生产者/消费者模拟器里选 v1（if + 单个 CV），1 个生产者、1 个消费者、MAX = 1。先预测：无论怎样调度，它会不会出错？然后点「批量随机 500 次」验证，再改成 2 个消费者重做一次。
看答案

1 生产者 1 消费者时不会出错，500 次全部正常结束（我们还用 node 穷举了 loops = 3 时的全部交错，同样没有一次出错）。原因是：能被唤醒的只可能是"另一类"线程，而同类线程只有自己一个，没有人能插队改掉状态。

改成 2 个消费者后，大部分随机调度都会触发 get() 断言失败（本页用 node 跑出的结果是 500 次中 443 次）。这正是原书说的"只有一个生产者和一个消费者时 Figure 30.8 能工作"。

点「Figure 30.9 调度 × while」：还是原书那 17 步调度，只是版本换成了 v2（while）。先预测：最后一步 Tc1 会执行哪一行？结果如何？
看答案

Tc1 从 wait() 返回后执行的是 c2（while 的重新检查），而不是 c4。它发现 count == 0，于是准备回到 c3 继续睡。模拟器会把这一步标成"白醒一次"。断言不再触发，这就是 while 修复的第一个问题。

载入「Figure 30.11 调度 × 最终版」（原书的调度用在两个 CV 的版本上）。预测：第 17 步 Tc1 执行 c5 时，会叫醒谁？之后原书的调度还能继续吗？
看答案

c5 现在是 signal(&empty)，empty 队列里只有 Tp，所以叫醒的是 Tp。Tc2 睡在 fill 上，不受影响。第 22 步原书要运行 Tc2，但 Tc2 在最终版里仍在睡眠，不能被调度，模拟器会提示轨迹从这里分叉。此时 Tp 已经就绪，继续运行它，一切正常。

（改编自作业第 8、9 题）v2 在"1 个生产者 + 1 个消费者 + MAX = 1"时能出问题吗？2 个消费者呢？用批量随机和手动调度分别试试。
看答案

1P1C 时 v2 不会出问题：队列里最多只有一个等待者，而且一定是对方那一类。2 个消费者时，Figure 30.11 那种"全体睡着"就可能出现（本页 node 批量结果：500 次随机调度里 233 次全体睡眠）。反过来，2 个生产者、1 个消费者时也会出现对称的问题：生产者叫醒了生产者。

点「Figure 30.11 调度 × LIFO 唤醒」：还是 v2 和原书的调度，只是 signal 改为唤醒队尾的线程。预测：第 17 步 Tc1 的 signal 叫醒了谁？这能说明 v2 是对的吗？
看答案

LIFO 下，第 17 步 Tc1 的 signal 取的是队尾的 Tp，这一次碰巧避开了 bug。但这绝不能说明 v2 是对的：POSIX 并不保证 signal 唤醒哪一个等待者，正确性不能依赖唤醒顺序这种实现细节。原书的说法是"如果它唤醒了 Tc2（这完全可能，取决于等待队列的管理方式）"，这就足以判定代码有 bug。

载入「Figure 30.9 调度 × Hoare」。预测：生产者 p5 发信号之后，还能按原书调度接着运行 Tp 吗？手动继续运行，if 版本这次会出错吗？再把版本改成"if + 两个 CV"，用 Hoare 批量随机 500 次，和 Mesa 对比。
看答案

不能。Hoare 语义要求被唤醒的 Tc1 立刻运行，锁也直接交给它，所以原书的下一步（Tp 执行 p6）不被允许，模拟器提示分叉。手动运行 Tc1，它直接执行 c4，缓冲区里确实有数据，这一轮不会出错。

"if + 两个 CV"在 Hoare 下批量 500 次全部正常，在 Mesa 下却经常断言失败（node 结果：1 生产者 2 消费者时 500 次中 271 次失败）。这说明 if 的正确性依赖 Hoare 那种"醒来即运行"的保证，而真实系统几乎都是 Mesa，所以要用 while。

自测题

关于 pthread_cond_wait(&c, &m)，下列说法正确的是：
wait 假定调用时已持锁；它把"释放锁 + 睡眠"做成一个原子动作，醒来后先重新拿到锁才返回。如果睡眠时仍持锁，其他线程就无法改变条件，也就永远不会有人来叫醒它。
join 的实现里去掉状态变量 done（Figure 30.4），会在什么情况下出错？
条件变量没有记忆。没人在等时，signal 什么也不做。done 的作用就是把"孩子已经结束"这件事记下来。
"Mesa 语义"指的是：
Mesa 语义下，被唤醒只是从睡眠变为就绪，之后什么时候运行由调度器决定，中间别的线程可能已经改变了状态。B 描述的是 Hoare 语义。几乎所有真实系统都用 Mesa 语义，所以要用 while。
v2（while + 单个条件变量）在 2 个消费者、1 个生产者时的 bug，根本原因是：
v2 已经用了 while。问题在于生产者和消费者睡在同一个队列里，signal 没有方向。解法是两个条件变量：消费者只 signal(empty)，生产者只 signal(fill)。
在最终的正确方案里，生产者在哪个条件变量上等待、在哪个上发信号？
生产者等"有空槽"（empty），放完数据后通知"有数据了"（fill）；消费者正好相反。
Figure 30.8（if + 单个 CV）在只有 1 个生产者和 1 个消费者时：
原书明确说，单生产者单消费者时这段代码能工作。插队和叫错人都需要至少两个同类线程。模拟器的批量随机和穷举都能验证这一点。
关于覆盖条件（covering condition），下列说法正确的是：
覆盖条件保守地覆盖所有需要唤醒的情况。被唤醒的线程仍然必须用 while 重查，不满足就回去睡。对生产者/消费者，两个 CV 是更好的解法；要是程序"只有改成 broadcast 才能工作"，多半有 bug。
除了 Mesa 语义之外，下列哪一项也是"用 while 而不用 if"的理由？
原书的 TIP 提到，在某些线程库里，由于实现细节，一个 signal 可能唤醒两个线程。重新检查条件可以应对这种情况。
单 CPU 上，父线程用 while (done == 0) ; 自旋等子线程（Figure 30.2），主要问题是：
自旋"一般能工作"，但极其低效。原书的 CRUX 也说，自旋在某些情况下甚至可能不正确。条件变量让父线程睡下，把 CPU 让给子线程。

常见误区

  • 把条件变量当成"事件标志"，以为先 signal、后 wait 也能收到。实际上 CV 没有记忆，必须配合状态变量（done、count、bytesLeft……）。
  • 用 if 检查条件。Mesa 语义下，醒来时条件可能又不成立了，而且还有伪唤醒。永远用 while。
  • 不持锁就检查条件或调用 wait/signal。"检查"和"入睡"之间的缝隙会造成丢失唤醒。
  • 以为 signal 会唤醒"正确的"线程。一个 CV 上睡着两类等待者时，signal 可能叫错人。给不同的条件用不同的 CV。
  • 把 broadcast 当万能药。它能掩盖设计错误，还会带来大量白醒。只在确实无法判断该叫谁时（覆盖条件）才用。
  • 以为"被唤醒"就等于"马上运行"。被唤醒只是进入就绪队列，还要重新竞争锁。

本章小结

  • 条件变量是一个显式的等待队列。wait(c, m) 原子地释放锁并睡眠，返回前重新获取锁；signal(c) 唤醒一个等待者，没人等就什么也不做。
  • 条件变量没有记忆，必须配合状态变量，并在持锁时检查和修改它，否则会丢失唤醒（join 的两个错误版本）。
  • Mesa 语义下 signal 只是提示，所以永远用 while 重新检查条件（修复 Figure 30.9）。
  • 不同的等待条件用不同的条件变量，让 signal 有方向（修复 Figure 30.11）。生产者/消费者的标准写法是 while + empty/fill + 循环缓冲区。
  • 不知道该叫醒谁时，用 broadcast 形成覆盖条件，以白醒为代价换取正确性。
  • 后续章节：第 31 章的信号量把"锁"和"条件变量"统一成一个原语，并会用它重新解决生产者/消费者问题；第 32 章里的顺序违反（order violation）bug，正是用本章的条件变量修复的；第 33 章则换一种思路，用事件循环在不使用线程的情况下实现并发。
