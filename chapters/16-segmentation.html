1一句话 + 关键问题

怎样支持大地址空间？栈和堆之间可能有大量空闲空间，怎样才能支持这样的大地址空间？在我们的"玩具"例子里浪费看起来不严重；但想象一个 32 位（4GB）的地址空间：典型程序只用几 MB，却要求整个地址空间都驻留在内存里。

原文：How do we support a large address space with (potentially) a lot of free space between the stack and the heap?

第 15 章的基址/界限把整个地址空间连续放进物理内存，堆和栈之间没用的空间也白白占着物理内存；地址空间比物理内存大时甚至根本跑不起来。本章的办法很自然：不要只给一对 base/bounds，给每个逻辑段一对——这就是分段（segmentation），一个至少可以追溯到 20 世纪 60 年代初的想法。

分段解决了稀疏地址空间的浪费，还顺带支持代码共享；但它引入了新问题外部碎片（external fragmentation），这把我们引向第 17 章的空闲空间管理和第 18 章的分页。

2核心概念速览

段（segment）

地址空间中一段连续的部分，有特定长度。经典的三段：代码、堆、栈。

每段一对 base/bounds

MMU 里放三对寄存器，每段可以独立放到物理内存的任意位置，只为真正使用的部分分配物理内存。

显式方式（explicit）

用虚拟地址的最高几位选择段、其余位做段内偏移。VAX/VMS 用过；本章例子用 14 位地址的高 2 位。

隐式方式（implicit）

根据地址怎么产生来判断：来自 PC → 代码段；基于栈指针/基址指针 → 栈段；其他 → 堆。

反向增长（negative growth）

栈向低地址增长。硬件多存一位"是否正向增长"，反向段用负偏移计算物理地址。

保护位（protection bits）

每段加读/写/执行位。代码段设为只读+执行，就能在多个进程间安全共享。

粗粒度 vs. 细粒度

少量大段（代码/堆/栈）是粗粒度；Multics、Burroughs B5000 支持成千上万个小段，需要内存中的段表。

外部碎片 & 紧凑

变长的段把物理内存切成许多小洞，总空闲够却找不到连续空间。紧凑（compaction）可以缓解，但代价高。

3.1 为什么要分段

回顾这个 16KB 的地址空间：代码在 0–2KB，堆在 4KB–7KB，栈在 14KB–16KB，中间 7KB–14KB 全是空闲。用一对 base/bounds 就要为整个 16KB 分配物理内存。

3.2 两个转换例子：先求段内偏移

虚拟地址 100 在代码段。硬件把段内偏移（这里就是 100）加上代码段基址：100 + 32KB = 32868；检查 100 < 2KB，合法，访问物理地址 32868。

虚拟地址 4200 在堆里。如果直接加堆的基址 34KB，得到 39016——错了。必须先求出堆内偏移：堆从虚拟地址 4KB（4096）开始，偏移 = 4200 − 4096 = 104，再加基址：104 + 34KB（34816）= 34920。

访问 7KB 或更大的地址（超过堆的末尾）呢？硬件发现越界，陷入 OS，进程很可能被终止。这就是所有 C 程序员都害怕的术语段错误（segmentation violation / segmentation fault）的由来。

"segmentation fault / violation"一词源于在分段机器上访问非法地址。有趣的是，即使在完全不支持分段的机器上，这个词也沿用至今。如果你搞不清代码为什么总是段错误，那就不那么有趣了。

3.3 硬件怎么知道是哪个段？显式方式：看最高几位

一种常见的显式（explicit）做法：用虚拟地址的最高几位选段（VAX/VMS 这样做）。例子里有三段，需要 2 位。14 位虚拟地址的高 2 位是段号，低 12 位是段内偏移：00 → 代码段，01 → 堆。以 4200 为例：

用偏移做界限检查也更方便：只要检查偏移是否小于 bounds。如果 base 和 bounds 是以段号为下标的数组，硬件做的事相当于：

1 // get top 2 bits of 14-bit VA
2 Segment = (VirtualAddress & SEG_MASK) >> SEG_SHIFT
3 // now get offset
4 Offset  = VirtualAddress & OFFSET_MASK
5 if (Offset >= Bounds[Segment])
6     RaiseException(PROTECTION_FAULT)
7 else
8     PhysAddr = Base[Segment] + Offset
9     Register = AccessMemory(PhysAddr)

在我们的例子里 SEG_MASK = 0x3000、SEG_SHIFT = 12、OFFSET_MASK = 0xFFF。第 2 行取高 2 位并右移成 0–3 的段号；第 4 行取低 12 位；第 5 行只需比较偏移和该段的大小；第 8 行才加基址。

两点代价：(1) 只有三个段却用了 2 位，有一个段号（10）空着没用——有些系统把代码和堆放进同一个段，只用 1 位选段；(2) 每个段的最大尺寸被限制为 16KB ÷ 4 = 4KB，程序想让堆或栈长得更大就没办法了。

另一种隐式（implicit）做法：硬件看地址是怎么产生的——来自程序计数器（取指）就是代码段；基于栈指针或基址指针的就是栈段；其他都是堆。

3.4 栈怎么办？反向增长与负偏移

栈被放在物理地址 28KB，但它向低地址增长：在物理内存中它从 28KB "开始"，长到 26KB，对应虚拟地址 16KB 到 14KB。硬件需要多知道一位：该段是否正向增长（1 = 正向，0 = 反向）：

段基址大小（最大 4K）正向增长？保护
Code0032K2K1Read-Execute
Heap0134K3K1Read-Write
Stack1128K2K0Read-Write

图 16.4 / 16.5 带反向增长位和保护位的段寄存器

例子：访问虚拟地址 15KB，应该映射到物理地址 27KB。二进制是 11 1100 0000 0000（0x3C00）：高 2 位 11 → 栈段；剩下的偏移是 3KB。要得到正确的负偏移，用它减去段的最大尺寸：3KB − 4KB = −1KB；把负偏移加到基址上：28KB + (−1KB) = 27KB。界限检查：负偏移的绝对值必须 ≤ 段的当前大小（1KB ≤ 2KB，合法）。

3.5 共享与保护位

为了节省内存，有时在地址空间之间共享某些段很有用，尤其是代码共享，今天的系统仍在使用。为此硬件要给每个段加几个保护位（protection bits）：能否读、能否写、能否执行。把代码段设为只读（读+执行），同一份代码就能被多个进程共享而不破坏隔离：每个进程仍以为自己在访问私有内存，OS 却在暗中共享不能被修改的内存。

有了保护位，硬件算法除了检查界限，还要检查这次访问是否被允许。用户进程试图写只读段、或执行不可执行的段，硬件都应引发异常。

3.6 细粒度与粗粒度分段

只有代码、栈、堆寥寥几段属于粗粒度（coarse-grained）分段。一些早期系统（如 Multics）更灵活，允许一个地址空间由大量小段组成，这叫细粒度（fine-grained）分段，需要在内存中存放某种段表（segment table）。Burroughs B5000 支持数千个段，期望编译器把代码和数据切成独立的段。当时的想法是：有了细粒度的段，OS 能更好地了解哪些段在用、哪些没用，从而更有效地利用内存。

3.7 OS 要操心的事：切换、增长、空闲空间

  1. 上下文切换：段寄存器必须保存和恢复，每个进程有自己的虚拟地址空间。
  2. 段的增长（或收缩）：malloc() 在现有堆里找不到空间时，内存分配库会调用系统调用（传统 UNIX 的 sbrk()）来扩大堆。OS 通常会提供更多空间并更新段大小寄存器；但如果物理内存不够，或它认为进程已经拿得太多了，也可以拒绝。
  3. 管理物理内存中的空闲空间（最重要）：以前每个地址空间一样大，物理内存可以看成一组槽；现在每个进程有好几个段，每段大小不同。物理内存很快会布满小洞，难以分配新段或让现有段增长。这就是外部碎片（external fragmentation）。

解决办法之一是紧凑（compact）物理内存：OS 停下正在运行的进程，把它们的数据拷贝到一块连续区域，修改段寄存器指向新位置，于是得到一大块空闲内存。但紧凑代价很高：拷贝段是内存密集操作，占用相当多的处理器时间；而且（讽刺的是）紧凑后现有段想增长更难了，可能又要重新排列。

更简单的办法是用空闲链表管理算法尽量保留大块空闲内存：最优适配（best-fit）、最差适配（worst-fit）、首次适配（first-fit），以及更复杂的伙伴算法（buddy algorithm）。可惜不管算法多聪明，外部碎片都依然存在，好的算法只是尽量减少它。

如果有 1000 种解法，说明没有一种好解法。有这么多算法试图减少外部碎片，恰恰说明没有"最好"的办法。我们只能选一个合理的，希望它足够好。唯一真正的解决办法是从根本上避免这个问题：永远不要以变长的块来分配内存（第 18 章分页）。

看答案
0x3800 = 11 1000 0000 0000：栈段，偏移 2048，负偏移 2048 − 4096 = −2048，|−2048| ≤ 2048 合法，PA = 28672 − 2048 = 26624（26KB）。0x37FF = 11 0111 1111 1111：偏移 2047，负偏移 −2049，|−2049| > 2048，越界。注意栈段的界限检查用的是 ≤，正向段用的是 <。

7自测题

图 16.3 的段表下，虚拟地址 4200 的物理地址是？
先求堆内偏移：4200 − 4096 = 104，再加堆基址 34816，得 34920。直接加基址（D）是原书特意指出的错误。
14 位虚拟地址、高 2 位选段，每个段的最大大小是？
16KB 地址空间被高 2 位切成 4 块，每块 4KB。想让堆或栈长过 4KB 就无能为力了。
栈段 base = 28KB、size = 2KB、反向增长、最大段 4KB。虚拟地址 15KB 的物理地址是？
偏移 3KB，负偏移 3KB − 4KB = −1KB，28KB − 1KB = 27KB；|−1KB| ≤ 2KB 合法。
分段相比单一基址/界限的主要好处是？
分段避免了堆栈之间空洞的浪费、转换开销小、还能共享代码。它反而引入了外部碎片，段大小也受限。
要让多个进程安全地共享同一个代码段，硬件还需要什么？
把代码段设为 Read-Execute，任何进程都改不了它，共享就不会破坏隔离。
关于外部碎片，哪项正确？
D 是内部碎片。任何算法都只能减少外部碎片，不能消除；唯一根治是不再用变长块分配（分页）。
关于紧凑（compaction），下列哪项不正确？
原书："compaction also (ironically) makes requests to grow existing segments hard to serve"——段被紧挨着排在一起，没有增长余地了。
"隐式（implicit）"判断段的方式是指？
C 是显式方式；隐式方式由硬件观察地址是怎样形成的。

8常见误区与小结

误区 1："把虚拟地址直接加上段基址。"必须先减去段在虚拟地址空间中的起点（或者用低位取偏移）。4200 + 34KB = 39016 是错的。

误区 2："栈段的 base 是栈的最低地址。"反向增长段的 base 指向顶端（28KB），物理地址 = base + 负偏移；负偏移 = 偏移 − 最大段大小（不是当前大小）。

误区 3："分段没有碎片。"分段消除了（大部分）内部碎片，却带来外部碎片。

误区 4："分段让稀疏地址空间完全不浪费。"如果一个很大的堆只用了零星几处，整个堆段仍必须驻留内存。分段的灵活性还不够。

本章小结

  • 分段是广义的基址/界限：每个逻辑段（代码、堆、栈）一对 base/bounds，各自独立放置，避免了段之间空洞的物理内存浪费。
  • 硬件用虚拟地址的高几位（显式）或地址的产生方式（隐式）确定段；段内偏移做界限检查；反向增长段用负偏移。
  • 保护位支持代码共享；细粒度分段需要内存中的段表。
  • OS 要在切换时保存/恢复段寄存器、处理段的增长（sbrk），并管理物理内存中的空闲空间。
  • 两大问题：外部碎片（下一章讨论各种空闲空间管理策略）和对稀疏使用的大段仍不够灵活（第 18 章的分页用固定大小的页来根治）。
