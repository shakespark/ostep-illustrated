1一句话 + 关键问题

如何高效地、可控地虚拟化 CPU？OS 必须以高效的方式虚拟化 CPU，同时保持对系统的控制。为此既需要硬件支持，也需要操作系统支持；OS 往往会巧妙地借助一点硬件支持来有效地完成工作。

THE CRUX: HOW TO EFFICIENTLY VIRTUALIZE THE CPU WITH CONTROL

一句话：让程序直接在 CPU 上跑（快），但事先由 OS 和硬件设好"围栏"——用户模式限制它能做的事、陷阱表规定它能进入内核的入口、时钟中断保证 OS 总能拿回 CPU（可控）。这就是受限直接执行（limited direct execution，LDE）。

第 4 章说 OS 靠时分共享虚拟化 CPU：运行一个进程一会儿，再运行另一个。本章讲实现这件事的底层机制，面对两大挑战：性能（如何不增加过多开销）和控制（如何在高效运行进程的同时保持对 CPU 的控制——没有控制，进程可以永远霸占机器，或访问它不该访问的信息）。机制就绪后，第 7 章起讨论策略：该运行哪个进程。

2核心概念速览

直接执行（direct execution）

把程序直接放到 CPU 上运行，速度与裸机一样快。

用户模式 / 内核模式

用户模式（user mode）下的代码受限，不能直接发 I/O；内核模式（kernel mode）下 OS 可以做任何事。

系统调用与 trap

用户程序执行特殊的 trap 指令：跳入内核并提升特权级；完成后 return-from-trap 返回并降级。

陷阱表（trap table）

OS 在开机时告诉硬件：发生系统调用、中断、异常时各跳到哪段代码。设置它是特权操作。

内核栈（kernel stack）

每个进程一个。陷入内核时，硬件把用户寄存器（PC、标志等）压到这里，返回时弹出。

时钟中断（timer interrupt）

定时器每隔若干毫秒打断 CPU，运行 OS 预设的处理程序——OS 重新获得控制权。

协作式 vs 非协作式

协作式：等进程自己通过系统调用交出 CPU；非协作式：靠时钟中断强行拿回。

上下文切换（context switch）

保存当前进程的寄存器，恢复另一个进程的寄存器，让 return-from-trap "返回"到另一个进程。

让程序跑得快的想法很简单：直接在 CPU 上运行它。OS 想启动程序时，在进程列表里建一项、分配内存、把程序代码从磁盘加载进内存、找到入口点（main() 之类），跳过去运行用户代码。原书图 6.1：

听起来简单，但问题有两个：① 如果只是直接运行程序，OS 怎么保证它不做我们不希望它做的事，同时仍然高效？② 程序运行时，OS 怎么让它停下来、切换到另一个进程，从而实现时分共享？没有这些限制，OS 什么也控制不了，只是个"库"——对一个有抱负的操作系统来说，这可太惨了。这就是名字里"受限（limited）"的由来。

4问题 1：受限制的操作

如何执行受限制的操作？进程必须能执行 I/O 和其他一些受限操作，但又不能让它完全控制系统。OS 和硬件如何协作做到这一点？

THE CRUX: HOW TO PERFORM RESTRICTED OPERATIONS

让进程想做什么就做什么（比如随意发 I/O）是不行的：要建一个在授权访问前检查权限的文件系统，就不能允许任何用户进程直接向磁盘发 I/O，否则它可以读写整个磁盘，一切保护都失效了。

办法是引入新的处理器模式：用户模式（user mode）下运行的代码受限，比如不能发 I/O 请求，否则处理器会引发异常（exception），OS 很可能就此杀掉这个进程。与之相对的是内核模式（kernel mode），OS（内核）在这种模式下运行，可以执行包括 I/O 在内的所有特权操作。

那用户进程想读磁盘怎么办？几乎所有现代硬件都允许用户程序执行系统调用（system call）——这种设计在 Atlas 等古老机器上首创。系统调用让内核小心地向用户程序开放一些关键功能：访问文件系统、创建和销毁进程、与其他进程通信、分配更多内存等。多数 OS 提供几百个系统调用（见 POSIX 标准），早期 UNIX 只有大约二十个。

要点逐条：

  • trap 指令同时做两件事：跳入内核、把特权级升到内核模式。完成后 OS 执行 return-from-trap，返回调用程序，同时把特权级降回用户模式。
  • trap 时硬件要保存足够多的调用者寄存器，才能正确返回。x86 上处理器会把程序计数器、标志和其他几个寄存器压入该进程的内核栈（kernel stack）；return-from-trap 把它们弹出，恢复用户程序的执行。
  • trap 怎么知道该运行 OS 里的哪段代码？调用者不能指定地址（那样就能跳到内核任意位置——比如恰好跳过权限检查之后——这是个非常糟糕的主意）。内核在开机时设置陷阱表（trap table）：机器以内核模式启动，OS 告诉硬件发生硬盘中断、键盘中断、系统调用时各运行哪段代码（陷阱处理程序，trap handler）；硬件记住这些位置，直到下次重启。
  • 每个系统调用有一个系统调用号（system-call number）。用户代码把它放进约定的寄存器或栈位置；OS 在陷阱处理程序中检查它是否合法，合法就执行对应代码。
  • 告诉硬件陷阱表在哪的指令本身也是特权指令。在用户模式下试图执行它？硬件不允许，你大概能猜到结果（再见了，违规程序）。想一想：如果能安装自己的陷阱表，你能对系统做出什么可怕的事？

即使所有进入 OS 的调用都经过硬件陷阱机制，系统调用边界上的参数也必须检查。例如 write() 的用户缓冲区地址：若用户（无意或恶意）传入一个位于内核地址空间的"坏"地址，OS 必须发现并拒绝，否则用户就能读出全部内核内存——而内核（虚拟）内存通常包含全部物理内存，这个小疏忽会让程序读到系统里任何进程的内存。安全的系统必须以极大的怀疑对待用户输入。

LDE 协议分两个阶段。第一阶段（开机时），内核初始化陷阱表，CPU 记住它的位置——这要通过特权指令完成（表中粗体即特权指令）。第二阶段（运行进程时），内核先做好准备（进程列表、内存），再用 return-from-trap 启动进程，切换到用户模式；进程要发系统调用时 trap 回 OS，OS 处理完再 return-from-trap。进程最后从 main() 返回到一段桩代码，它调用 exit() 系统调用陷入 OS，OS 清理，结束。下面的模拟器逐行重现原书图 6.1、6.2、6.3：

5问题 2：在进程之间切换

切换进程应该很简单吧？OS 决定停下一个、启动另一个就是了。但这其实有点棘手：如果一个进程正在 CPU 上运行，按定义 OS 就没有在运行。OS 不运行，它又怎么能做任何事？（提示：它做不到。）这听起来像哲学问题，却是实实在在的难题。

如何重新获得 CPU 的控制权？OS 如何重新获得对 CPU 的控制，以便在进程之间切换？

THE CRUX: HOW TO REGAIN CONTROL OF THE CPU

协作方式：等待系统调用

一些早期系统（如早期的 Macintosh OS、Xerox Alto）采用协作（cooperative）方式：OS 相信进程会合理行事，运行太久的进程会定期交出 CPU。怎么交？多数进程经常做系统调用（打开文件、读文件、发消息、创建进程……），这就把控制交给了 OS；这类系统通常还提供一个 yield 系统调用，除了把控制交给 OS 别的什么也不干。进程做了非法的事（除以零、访问不该访问的内存）也会陷入（trap） OS，OS 重获控制（很可能终止它）。

可这种被动方式有个大问题：如果一个进程（恶意的，或者只是有 bug）陷入死循环、从不做系统调用，OS 能怎么办？

如何在没有协作的情况下获得控制权？即使进程不合作，OS 如何获得 CPU 的控制？OS 如何确保流氓进程不会霸占机器？

THE CRUX: HOW TO GAIN CONTROL WITHOUT COOPERATION

非协作方式：OS 主动夺回控制

没有硬件的额外帮助，OS 在进程拒绝做系统调用（或出错）时几乎无能为力；协作式系统里，进程死循环时唯一的办法是计算机系统中解决所有问题的古老方法——重启。答案其实很简单，多年前就被许多人发现：时钟中断（timer interrupt）。时钟设备可以编程为每隔若干毫秒产生一次中断；中断发生时，正在运行的进程被暂停，OS 中预先配置好的中断处理程序（interrupt handler）开始运行。此时 OS 重新获得了 CPU 的控制权，想做什么都可以：停止当前进程，启动另一个。

和系统调用一样，OS 必须在开机时告诉硬件时钟中断发生时运行哪段代码；开机过程中 OS 还必须启动时钟——这当然也是特权操作。时钟一旦开始计时，OS 就可以放心地运行用户程序，因为控制权迟早会回到它手里。（时钟也可以关闭，同样是特权操作，第 26 章起讨论并发时会用到。）中断发生时，硬件要保存被打断程序的足够状态，以便之后的 return-from-trap 能正确恢复它——这和系统调用陷入内核时硬件的行为非常相似。

保存与恢复上下文

OS 重新获得控制后（无论是通过系统调用协作地，还是通过时钟中断强制地），要做一个决定：继续运行当前进程，还是切换到另一个？这个决定由 OS 中的调度器（scheduler）做出（接下来几章的主题）。如果决定切换，OS 就执行一段底层代码——上下文切换（context switch）。概念上很简单：为当前正在执行的进程保存几个寄存器的值（比如存到它的内核栈上），再为即将执行的进程恢复几个寄存器的值（从它的内核栈上）。这样，当最后执行 return-from-trap 时，系统不再返回原来那个进程，而是恢复执行另一个进程。

具体说，OS 用一些底层汇编代码保存当前进程的通用寄存器、PC 和内核栈指针，然后恢复即将运行进程的寄存器、PC，并切换到它的内核栈。通过切换栈，内核在一个进程（被中断的那个）的上下文中调用切换代码，却在另一个进程（即将执行的那个）的上下文中返回。

两种寄存器保存/恢复，千万别混：

  1. 时钟中断发生时：正在运行进程的用户寄存器由硬件隐式保存，存到该进程的内核栈上。
  2. OS 决定从 A 切换到 B 时：内核寄存器由软件（OS）显式保存，存到该进程的进程结构（proc 结构）里。这一步把系统从"好像刚从 A 陷入内核"变成"好像刚从 B 陷入内核"。

原书图 6.4 是 xv6 的上下文切换代码 swtch。结构 old 和 new 分别位于旧进程和新进程的进程结构中：

# void swtch(struct context *old, struct context *new);
#
# 把当前寄存器上下文保存到 old，再从 new 载入寄存器上下文。
.globl swtch
swtch:
  # 保存旧寄存器
  movl 4(%esp), %eax   # old 指针放进 eax
  popl 0(%eax)         # 保存旧的 IP（返回地址）
  movl %esp, 4(%eax)   # 以及栈指针
  movl %ebx, 8(%eax)   # 以及其他寄存器
  movl %ecx, 12(%eax)
  movl %edx, 16(%eax)
  movl %esi, 20(%eax)
  movl %edi, 24(%eax)
  movl %ebp, 28(%eax)

  # 载入新寄存器
  movl 4(%esp), %eax   # new 指针放进 eax
  movl 28(%eax), %ebp  # 恢复其他寄存器
  movl 24(%eax), %edi
  movl 20(%eax), %esi
  movl 16(%eax), %edx
  movl 12(%eax), %ecx
  movl 8(%eax), %ebx
  movl 4(%eax), %esp   # 栈在这里切换！
  pushl 0(%eax)        # 把返回地址放到位
  ret                  # 最终"返回"到新上下文中

关键在倒数第三行 movl 4(%eax), %esp：一旦栈指针换成新进程的内核栈，接下来的 ret 就返回到新进程当初调用 swtch 的地方。从新进程的角度看，它只是调用了一个函数、然后返回了——它的内核栈上还躺着当初被中断时硬件保存的用户寄存器，随后的 return-from-trap 会把它们恢复出来。

6担心并发吗？

细心的读者可能会问："系统调用处理到一半，时钟中断来了怎么办？""处理一个中断时，又来了另一个中断呢？这在内核里不是很难处理吗？"好问题！答案是：是的，OS 确实需要考虑中断或陷阱处理期间发生另一个中断的情况——这正是本书第二部分并发的主题。先透露一点：一个简单的做法是在处理中断时禁用中断（disable interrupts），保证处理一个中断时不会有别的中断被送到 CPU——但要小心，禁用太久可能丢失中断，这（用技术术语说）很糟。OS 还发展出了各种精巧的加锁（locking）方案来保护内部数据结构的并发访问，让内核里可以同时进行多项活动，这在多处理器上尤其有用；但正如第 28 章会看到的，加锁可能很复杂，并引出各种有趣且难找的 bug。

有个叫 lmbench 的工具专门测量这些。结果大致随处理器性能提升：1996 年在 200 MHz P6 CPU 上运行 Linux 1.3.37，系统调用约 4 微秒，上下文切换约 6 微秒；现代系统快了几乎一个数量级，2–3 GHz 处理器上可以做到亚微秒级。不过并非所有 OS 操作都随 CPU 性能提升：Ousterhout 指出，许多 OS 操作是内存密集型的，而内存带宽的提升远不如处理器速度——换上最新最快的处理器，OS 未必如你期望的那样变快。下面的实验让你在自己的机器上测一测。

重启很有用（Reboot is useful）。协作式系统里死循环的唯一解药是重启，你可能对此嗤之以鼻。但研究表明，重启（或者说让某个软件重新开始）是构建健壮系统的极有用的工具：它让软件回到一个已知的、通常测试更充分的状态；回收泄漏或陈旧的资源（如内存）；而且易于自动化。大规模集群互联网服务的管理软件定期重启一批机器，并不罕见。

7先预测，再验证

在 LDE 时间线模拟器里载入图 6.2。数一数：从开机到程序结束，CPU 一共切换了几次特权级（用户 ⇄ 内核）？哪几行是特权操作？
看答案
用户 → 内核：系统调用 trap 一次、exit() 的 trap 一次，共 2 次；内核 → 用户：启动程序时的 return-from-trap、系统调用返回时的 return-from-trap，共 2 次。特权操作：开机时初始化陷阱表、两次 return-from-trap（trap 指令本身在用户模式下执行，但它进入的是事先规定的入口）。
为什么 OS 启动一个新进程时，要先往它的内核栈里"填入寄存器和 PC"（Fill kernel stack with reg/PC），再执行 return-from-trap，而不是直接 call main()？
看答案
因为要同时完成"跳到 main"和"切换到用户模式"两件事，而只有 return-from-trap 能原子地做到：它从内核栈弹出 PC 等寄存器并降低特权级。OS 事先把"假装是从用户态陷入时保存的"寄存器值（PC = main 的地址、用户栈指针等）放进内核栈，return-from-trap 就会"返回"到 main。直接 call 的话程序会在内核模式下运行——那就回到了没有限制的图 6.1。
在"协作式 vs 时钟中断"中选协作式、B 死循环。预测：B 第一次获得 CPU 之后，A 和 C 还能运行吗？换成时钟中断、间隔 5 ms 呢？
看答案
协作式下，B 一旦拿到 CPU，就再也不做系统调用，OS 永远拿不回控制权，A、C 饿死——唯一的办法是重启。时钟中断下，每 5 ms OS 都能拿回控制权，B 最多连续运行 5 ms 就被换下，三者轮流运行。
在上下文切换模拟器里，第 3 步硬件保存的是谁的寄存器、存到哪里？第 6 步 switch() 保存的是谁的寄存器、存到哪里？两者有何不同？
看答案
第 3 步：硬件把 A 的用户寄存器（用户 PC、用户栈指针、eax 等）隐式压到 A 的内核栈。第 6 步：OS 软件把 A 此刻的内核寄存器（在内核里运行到 switch 时的 eip、内核栈指针 esp、ebx…）显式存进 proc_t(A) 的 context 字段。前者让 A 日后能回到用户态的断点，后者让 A 日后能回到内核里 switch 的调用点。
假设系统调用约 0.3 µs、上下文切换约 5 µs、时钟中断每 10 ms 一次且每次都切换。上下文切换占用了多少 CPU 时间？如果把时钟间隔缩短到 1 ms 呢？
看答案
10 ms 时约 5 µs / 10 ms = 0.05%；1 ms 时约 0.5%。间隔越短，响应越及时，但切换开销（以及切换后缓存变"冷"的间接代价）占比越大——这是调度中"时间片长度"的权衡，第 7 章会再遇到。

./ctxsw 200000 0     # 两个进程绑在 CPU 0 上，用两根管道打乒乓
./ctxsw 200000 -1    # 对照：不绑定 CPU

测系统调用：反复调用一个简单的系统调用（如读 0 字节的 read()）并计时，总时间除以次数就是估计值。但要先了解计时器的精度：gettimeofday() 返回自 1970 年以来的微秒数，却不代表它真能精确到微秒——连续调用它测一测就知道要重复多少次才能测准；不够精确时可以用 x86 的 rdtsc 指令。

测上下文切换：lmbench 的做法是在同一个 CPU 上运行两个进程，用两根 UNIX 管道把它们连起来。第一个进程往管道 1 写，然后从管道 2 读——此时无数据可读，OS 把它阻塞并切换到第二个进程；第二个进程从管道 1 读、往管道 2 写，再去读管道 1 时阻塞……如此往复。多 CPU 的系统上必须确保两个进程在同一个 CPU 上，Linux 上用 sched_setaffinity() 绑定。

示例输出（WSL2、16 核，与其他程序同时运行；你的机器上数字会不同，多跑几次也会波动）：

$ ./timer

clock_gettime: 声称分辨率 1 ns，最小非零差值 10 ns
rdtsc        : 连续两次最小差值 1 个时钟周期

$ ./syscall

$ ./ctxsw 200000 0

观察：① 连续两次 gettimeofday 98% 的时候读数相同——它的精度配不上几百纳秒的系统调用，必须重复上百万次；② 真正的系统调用比普通函数调用贵约 100 倍，而 clock_gettime 借助 vDSO 在用户态完成、根本不陷入内核；③ WSL2 运行在 Hyper-V 虚拟机里，外加各种安全缓解措施，系统调用和切换都比书中说的"亚微秒"慢；④ 不绑定 CPU 时，唤醒另一个 CPU 上的进程要额外的跨核通信，结果反而更慢、波动更大——这也说明为什么测量要把两个进程放在同一个 CPU 上。

9自测题

1. "受限直接执行"中的"直接执行"是为了解决什么？
直接执行快；"受限"则保证 OS 保持控制。两者合起来回答了本章的关键问题：高效且可控。
2. 用户程序执行 trap 指令时，跳转目标由谁决定？
用户程序只能提供系统调用号，不能指定地址，否则可以跳到内核任意位置（例如恰好跳过权限检查）。
3. 在 x86 上发生 trap 时，硬件把用户程序的 PC、标志等寄存器保存在哪里？
每个进程有自己的内核栈；return-from-trap 从这里弹出寄存器，恢复用户程序执行。
4. 以下哪个操作不需要处于内核模式？
trap 指令本来就是给用户程序进入内核用的；它进入的入口由陷阱表规定。其余三项都是特权操作，用户模式下执行会引发异常。
5. 在协作式调度的系统里，一个进程进入死循环且不做任何系统调用，会怎样？
协作式系统完全依赖进程主动交出控制（系统调用、yield 或非法操作）。没有时钟中断，也就没有"时间片"。
6. 关于上下文切换中的两次寄存器保存，正确的是？
原书："The first is when the timer interrupt occurs; ... user registers ... implicitly saved by the hardware, using the kernel stack... The second is when the OS decides to switch from A to B; ... kernel registers are explicitly saved by the software ... into memory in the process structure."
7. xv6 的 swtch 中，是哪一步让"返回"落到了新进程里？
切换栈之后，内核"在 A 的上下文中调用 switch，在 B 的上下文中返回"。之后 B 的 return-from-trap 从 B 的内核栈恢复用户寄存器。
8. OS 为什么必须检查系统调用的参数（例如 write 的缓冲区地址）？
陷阱机制只保证"从正门进来"，门后的代码仍要以极大的怀疑对待用户输入。
9. 测量上下文切换开销时，为什么要用 sched_setaffinity() 把两个进程绑到同一个 CPU？
原书："By ensuring both processes are on the same processor, you are making sure to measure the cost of the OS stopping one process and restoring another on the same CPU."

10常见误区与本章小结

  • "OS 一直在后台运行，监视着进程"：单个 CPU 上，进程运行时 OS 根本不在运行；OS 只有在系统调用、异常、中断时才重新获得控制。
  • "系统调用就是普通的函数调用"：外表是（调用 C 库），内核里是 trap：切换特权级、按陷阱表跳转、保存/恢复寄存器，开销大得多。
  • "用户程序可以指定跳进内核的哪个地址"：不行，只能给出系统调用号。
  • "上下文切换只保存一次寄存器"：有两次：硬件把用户寄存器存到内核栈，OS 把内核寄存器存到 proc 结构。
  • "有了时钟中断，OS 随时都会切换进程"：时钟中断只是让 OS 拿回控制权；切不切、切给谁由调度器决定。
  • 受限直接执行：让程序直接在 CPU 上运行，但先设置好硬件来限制进程在没有 OS 帮助时能做的事——就像给房间做"婴儿防护"：锁好装危险品的柜子、盖住电源插座，然后放心地让宝宝自由活动。
  • CPU 至少支持两种模式：受限的用户模式和特权的内核模式。用户程序通过系统调用陷入内核请求服务。
  • trap 指令保存寄存器状态、切换到内核模式、跳到陷阱表指定的位置；return-from-trap 降低特权级并返回 trap 之后的指令。陷阱表必须由 OS 在开机时设置，且不能被用户程序修改。
  • OS 用时钟中断（非协作方式）确保用户程序不会永远运行下去。
  • 在时钟中断或系统调用期间，OS 可能决定切换进程，执行上下文切换：保存 A 的寄存器，恢复 B 的寄存器并切换到 B 的内核栈。
